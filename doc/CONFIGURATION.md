# Конфигурация первого линейного прогона

Задача № 11, дата завершения 2026-10-20. Контракты и проверка находятся в `src/engine/config.ts`, контракты изменяемого состояния и создание снимка в `src/engine/state.ts`. Дополнение № 12 описано в [INVENTORY.md](INVENTORY.md): состояние запаса теперь содержит происхождение, снимок имеет собственную схему 2, версия движка 0.4.0. Конфигурация по-прежнему имеет схему 1. Симулятор пока не запускается: здесь определена граница между данными редактора, параметрами расчёта и данными для UI.

## Четыре представления

| Представление | Назначение |
|---|---|
| EditorConfig | Изменяемые исходные данные с ID, названиями, цветами, языком, десятичными строками и явно заданными буферами |
| RunConfig | Независимая глубоко замороженная копия исходника и нормализованные расчётные значения, версии и хеш |
| EngineState | Изменяемые данные времени, состояний постов и запасов; учётные переходы stocks реализованы в № 12, календарные переходы ещё отсутствуют |
| Snapshot | Независимая глубоко замороженная копия состояния, пригодная для JSON; стоимость выражена строками целых микроединиц |

`compileConfig` принимает unknown, проверяет структуру и значения и возвращает RunConfig. Исходные данные не изменяются. После проверки исходник отдельно копируется через structuredClone; resolved создаётся из проверенных значений. Object.freeze применяется ко всем вложенным объектам и массивам. TypeScript дополнительно запрещает запись через DeepReadonly.

`createSnapshot` копирует известные поля состояния и не передаёт ссылки на движок. Изменение исходного состояния после получения снимка не меняет снимок. Вызов в согласованной точке станет обязанностью событийного движка; этот модуль сам не выполняет переходы модели.

## Поддерживаемый формат

Корневая конфигурация содержит schemaVersion: 1, id, name, language, необязательный displayOrder, seed, durationMs, policy, calendar, materials, recipes, stations, sources, routes и initialStocks. Полный технический пример с двумя постами находится в функции line в `test-fixtures.ts`; это проверочный вход, а не готовый урок.

Стабильные ID задаются вызывающим кодом. Компилятор их не создаёт и не перенумеровывает. Они уникальны во всей конфигурации, включая строки планов и начальные записи запаса. Допустимы ASCII-буквы, цифры, _ и -. ID market и warehouse зарезервированы для рынка и общего склада сырья. Перевод и порядок отображения не влияют на ID.

Материал имеет роль raw, intermediate или finished, название и цвет. Для сырья нужна purchasePrice, для конечного изделия salePrice. Все цены и затраты в редакторской конфигурации являются десятичными строками условных денежных единиц. В resolved они переводятся в bigint микроединиц по правилам ARITHMETIC.md. Количества также задаются строками и переводятся в безопасные целые микроединицы number.

Рецепт содержит один вход с положительным количеством и один выход с целым положительным количеством. Тип только production. Пост содержит одну строку плана с ID, recipeId, batches: 1 и processing. Поддерживаются mode: sequential, repetitions: 1, cv: 0 и положительное целое timeMs. Выход рецепта может быть больше единицы. Это позволяет впоследствии проверить частичную выгрузку выпуска без внедрения обработки сложных партий.

У поста явно заданы priority, inputBuffer, outputBuffer, setupMs: 0, maintenance.enabled: false, lunchReplacement: false и costs с perShift, perLunchHour и capital. Ёмкость буфера имеет вид `{kind: 'quantity', quantity: '6'}` или `{kind: 'infinite'}`. Числовой Infinity не используется. Вход должен вмещать один полный комплект рецепта. Выход может быть нулевым или меньше выпуска: это допустимая прямая либо частичная выгрузка, а не ошибка конфигурации.

Глобальные буферы, наследование и норматив по доле смены пока отклоняются. Никакого скрытого глобального значения вместо явно заданной ёмкости нет. Эти настройки по плану добавляются на этапе 5; тогда исходные правила наследования и разрешённые значения также должны храниться раздельно.

Один источник содержит materialId сырья, положительные quantity и intervalMs и availability: virtual либо warehouse. Виртуальный источник закупает сырьё при допуске; конечный общий сырьевой склад адресуется ID warehouse. Алгоритм закупки, попыток и общего остатка относится к следующим задачам. Маршрут содержит стабильный ID, fromId, toId и materialId. Сейчас допускается только одна связная цепочка «источник → посты → market». Весь набор постов, рецептов и материалов должен участвовать в ней. Слияния, развилки, циклы, лишние маршруты и неиспользуемые сущности отклоняются.

Начальный запас содержит ID, ownerId, location (warehouse, input или output), materialId, положительное количество и явную стоимость. Материал должен соответствовать владельцу и месту хранения. Сумма записей должна помещаться в ёмкость; количества и общая стоимость проверяются на переполнение. Складской запас разрешён только для конечного сырьевого склада источника. Порядок исходного массива не задаёт FIFO: нормализованные записи отсортированы по стабильному ID. Атрибуты возраста и происхождения и операции FIFO реализованы в № 12, см. INVENTORY.md.

Календарь задаёт границы смены и обеда в целых миллисекундах от начала суток. Обед строго внутри одной смены, ночные смены пока не поддерживаются. durationMs задаёт полный горизонт от начала первой смены до конца последней и проверяется календарём из № 13; произвольный конец посреди дня не принимается. Календарные API описаны в CALENDAR.md. Seed является целым числом от 0 до 4294967295. Его формат фиксируется уже сейчас, хотя случайность ещё не применяется.

## Нормализация и идентичность

Нормализованные сущности сортируются по ID обычным лексикографическим сравнением без зависимости от локали. Десятичные строки переводятся в микроединицы, поэтому `0.3` и `000.300000` дают одинаковый расчёт. Порядок ключей исходного JSON не имеет значения.

В хеш включены нормализованные параметры, стабильные ID сущностей, seed, календарь, горизонт, цены, затраты, ёмкости, запасы, маршруты и версии. Название и ID самой редакторской копии, названия сущностей, цвета, language, displayOrder и порядок массивов исключены. Неизменяемые для текущего подмножества правила представлены engineVersion. Реальная последовательность многорецептного плана пока не поддерживается, поэтому её порядок нельзя случайно потерять при сортировке.

Версии сейчас: schemaVersion 1, engineVersion 0.4.0 и rngVersion none-1. Последняя явно указывает отсутствие случайных выборок, а не обещает реализацию RNG. При добавлении вычислительных правил нужно менять соответствующую версию. Изменения сохраняемого формата требуют версии и миграции; сохранения и миграций в этой задаче нет.

Хеш имеет префикс fnv1a64 и 16 шестнадцатеричных цифр. Он вычисляется синхронно из канонической JSON-записи нормализованных данных, без DOM, системных часов, сети и crypto.subtle. Внутренние bigint кодируются десятичными строками. Это воспроизводимый технический отпечаток для сравнения, не защита данных и не математическая гарантия уникальности. Для точного повторения нужны сами параметры и совместимые версии.

## Ошибки и ограничения

ConfigError содержит code, path, objectId при доступном ID и messages с причинами на ru и en. Возвращается первая обнаруженная ошибка. Пример пути: config.stations.0.plan.0.processing.timeMs. Неизвестные поля отклоняются, чтобы неподдерживаемые механики не принимались молча. Неизвестная версия схемы не интерпретируется как текущая. Пользовательские названия остаются строковыми данными и не исполняются.

Сборка нескольких входов, несколько источников, распределение потока, многорецептные планы, CV больше нуля, одновременные и многократные партии, переналадки, обслуживание, подмена на обеде, транспортные пороги и DBR пока отклоняются. Полноценный редактор, импорт, storage и миграции не добавлялись. Учётные переходы и происхождение реализованы отдельно в inventory.ts; событийная очередь реализована в № 14, метрик и RNG ещё нет.

## Проверка

Прошли `npm test` (121 тест: 38 арифметики и 83 конфигурации/снимков) и `npm run build`, включая строгую проверку TypeScript. Проверены независимость и глубокая заморозка RunConfig, стабильность хеша при изменениях оформления и его изменение для расчётных полей, нормализация дробей, ссылки, ID, входные комплекты, начальные запасы и переполнение. Проверены линейная модель с одним постом, двухпостовая модель с выпуском десяти изделий, явный бесконечный буфер, конечный склад и обнаружение достижимого цикла.

Отдельно проверены JSON-совместимость снимка и отсутствие ссылок на изменяемое состояние. Браузерная проверка не повторялась: новые модули ещё не подключены к странице, production JS/CSS имеют прежние хеши. UI и автономная поставка сохраняют результат № 9.
