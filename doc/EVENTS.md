# Событийная основа и согласованный шаг

Задача № 14 завершена 2026-10-20. Реализация в `src/engine/events.ts`, проверки в `events.test.ts`. EventScheduler является предметной основой очереди; полный цикл поста ещё не подключён. DOM, реальные часы, таймеры и случайность не используются.

Дополнение № 16: полный цикл линии подключён в [SIMULATION.md](SIMULATION.md). Текущие версии: движок 0.6.0, конфигурация 1, снимок 4. Проверки ниже описывают исходную задачу.

## Порядок событий

ModelEvent содержит id, целое timeMs и один из фиксированных видов: completion, calendar, source, transfer, dispatch. Время находится между текущим моментом и горизонтом. Очередь сортируется по времени, фазе и обычному лексикографическому сравнению ID без зависимости от локали. Одинаковые ожидающие ключи «время, фаза, ID» отклоняются, поэтому порядок добавления не становится скрытым правилом разрешения ничьей.

| Фаза | Действие |
|---|---|
| До событий отметки | Integrate начисляет интервал по предыдущему состоянию |
| Completion | Завершение операции и принятие результата обработчиком |
| Calendar | Граница календаря; в этой фазе находится автоматический горизонт |
| Source | Разрешение источника, без реализации самого выпуска |
| Transfer | Мгновенная передача и возможное выбытие |
| Dispatch | Назначение допустимой работы |
| После устойчивости | Один согласованный снимок |

Порядок завершения, календаря и разрешений соответствует разделу 3.13 концепта. Обслуживание, переналадки, drum и финансовые интегралы не реализованы заранее: подключаемые в следующих задачах предметные функции будут использовать предусмотренные фазы.

События, созданные в ходе отметки, добавляются в ту же сортируемую очередь. Transfer и dispatch могут создавать новые мгновенные передачи и назначения, пока отметка не станет устойчивой. Возврат к ранней уже пройденной фазе запрещён. Сортировка применяется к текущему набору ожидающих событий; событие не может быть обработано до того, как оно создано.

Для учебных сетей выбрана обычная сортировка массива. Куча, универсальная шина, подписки, плагины и универсальные payload не добавлялись. Оптимизация требует измерений реального событийного прогона.

## API и граница состояния

EventScheduler получает неизменяемый RunConfig, начальный EngineState и фиксированные EventHandlers для предметных фаз. Он копирует начальное состояние. Обработчики пока задают проверочные переходы; реальный цикл подключится в № 16.

| API | Назначение |
|---|---|
| schedule(event) | Ставит независимую копию события в очередь до будущего шага |
| invalidateOperation(stationId) | Повышает версию операции, делая прежнее завершение устаревшим |
| step() | Обрабатывает ближайшую полную отметку и возвращает StepResult либо null после завершения |
| advanceTo(targetMs) | Обрабатывает все отметки до цели включительно, затем при необходимости начисляет интервал без событий |
| getSnapshot() | Возвращает последний глубоко замороженный согласованный снимок |
| getFailure() | Возвращает причину остановки после ошибки |

StepResult содержит timeMs, processedEvents, staleCompletions и finished. ProcessedEvents является техническим числом извлечённых событий, включая пропущенные устаревшие и автоматический горизонт, а не числом производственных операций.

Контекст обработчика предоставляет отдельную копию state, время отметки, schedule и invalidateOperation. Во время шага нужно пользоваться контекстом: повторный вызов методов продвижения или внешнего добавления через сам scheduler запрещён. После завершения отметки контекст закрывается. Ссылки на сохранённый draft не меняют зафиксированное состояние, поскольку оно повторно копируется перед фиксацией.

Обработчики являются доверенными синхронными функциями движка и должны менять только переданное состояние и очередь через контекст. Внешние побочные действия обработчиков, например запись в файл или глобальный массив, не входят в транзакцию. Модули будущего движка не должны через обработчики обращаться к DOM, часам или сети. Это не система выполнения пользовательского кода.

## Отмена и защита от повторного выпуска

В StationState добавлено внутреннее operationVersion. CompletionEvent содержит stationId и версию, действовавшую при планировании. При несовпадении событие пропускается, обработчик выпуска не вызывается. При принятии завершения версия повышается до вызова обработчика, поэтому второй ожидающий event с тем же токеном также не выпустит материал.

При календарной паузе вызывающий код сохраняет остаток и повышает версию. После открытия планируется новое завершение с текущей версией и расчётом календарного времени по остатку. Сам scheduler не вычисляет остаток и не запускает посты; для этого есть календарные функции и будущий цикл поста. Версия не сбрасывается и проверяется на переполнение.

OperationVersion не включена в UI-снимок: снимок по-прежнему не является форматом продолжения работы. Его схема остаётся 2. Схема конфигурации остаётся 1, engineVersion повышена до 0.4.0, rngVersion остаётся none-1. Нового сохраняемого формата нет.

## Согласованность, ошибки и горизонт

Шаг выполняется на копиях состояния и очереди, включая версии операций. До окончания отметки getSnapshot возвращает предыдущий снимок. После завершения всех связанных событий создаётся и фиксируется новый. При ошибке обработчика, неверной фазе или превышении лимита состояние и очередь отметки не фиксируются; остаётся предыдущий согласованный снимок. Scheduler останавливается с сохранённой ошибкой, повторные попытки продвижения её возвращают. Для нового прогона создаётся новый экземпляр.

Защитный предел MAX_TRANSITIONS_PER_TIMESTAMP равен 10 000 извлечениям в одной отметке. Он нужен для диагностики ошибочной бесконечной мгновенной цепочки и не меняет длительности или материальный учёт. Это технический предел начальной реализации, не обещание производительности; конечные бюджеты проекта определяются по измерениям позже. Частичный снимок при достижении предела не публикуется.

Автоматическое событие горизонта гарантирует точное завершение даже при пустой производственной очереди. На горизонте completion и transfer ещё выполняются, source и dispatch пропускаются. Поэтому завершённый ровно на границе результат принимается и может быть передан, но новая работа не начинается. Доработки после горизонта нет.

В уже опубликованную отметку нельзя добавить внешнее событие задним числом. После горизонта новые события запрещены. Продвижение назад и за горизонт запрещено. При продвижении до точки без событий integrate начисляет интервал и публикуется согласованное состояние на этой точке.

EventError содержит code, objectId и причины RU/EN. Ошибки предметного обработчика сохраняются как исходные ошибки. Диагностика потока, финансы и отдельный UI результата ошибки пока не реализованы.

## Проверка

Прошли 183 теста в пяти файлах, включая 15 новых событийных, строгий TypeScript и production-сборка. Проверены перестановка исходного набора событий, порядок фаз и ID, согласованный снимок после dispatch→transfer, совпадение step и advanceTo с промежуточными точками и до горизонта, независимость двух экземпляров и копирование данных.

Проверены два завершения одной версии с реальным учётным выпуском, устаревшее завершение после обеда и новый момент по сохранённому остатку, завершение до закрытия на одной отметке, подавление новых стартов у горизонта и начисление пустого хвоста. Проверены откат выпуска при последующей ошибке той же отметки, предел мгновенной цепочки, запрет ранних фаз и повторного входа, дубликаты, неверные времена, версии и отсутствующий обработчик.

UI эти модули ещё не использует, хеши встроенных JS/CSS автономного HTML не изменились, браузерная приёмка не повторялась. В № 15 предстоит подключить фактические источники push и общий сырьевой склад. Это требует нового явного поручения пользователя.
