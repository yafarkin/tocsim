## Принятый линейный редактор

В разделе «Мои процессы» создаётся цепочка из 1–30 постов. Пользователь меняет названия, времена в минутах и CV, общие и собственные входные/выходные буферы с наследованием, seed и число смен; добавляет, удаляет и перемещает посты. Используются прежние EditorConfig, compileConfig/compileLinearProcess и неизменяемый RunConfig, отдельной модели расчёта нет. Неподдерживаемые настройки отклоняются без обрезания данных. Порядок берётся из маршрутов, внутренние ID оставшихся объектов сохраняются.

Начальные условия отдельно подтверждены пользователем: три поста 3/8/3 минуты, CV 0, seed 42, смена 08:00–17:00 с обедом 12:00–13:00, подача одной единицы каждые 3 минуты, глобальный вход 1 и выход 0, нулевые физические начальные запасы. Цены/затраты нулевые по плану MVP. Рецепты 1:1, последовательная обработка и передача по единице, без переналадок/обслуживания/брака/подмены, policy=push. Исходник даёт 59 изделий. Новый пост получает явные имя и время 3 минуты от формы, CV 0 и наследуемые буферы.

Есть несколько именованных процессов, открытие, явное сохранение, независимая копия и подтверждённое удаление. Одинаковые имена допустимы. Неоконченные поля живут в памяти отдельно от последней корректной конфигурации. Переход с правками предлагает сохранить/отбросить/отменить, закрытие вкладки с правками или памятными записями вызывает beforeunload. Восстановление незавершённой формы после закрытия не обещается.

Запуск работает и без сохранения, после проверки формы. Пользовательский Runner находится в ProcessPlayback отдельно от Runner урока. В момент запуска захватывается неизменяемый RunConfig. Есть пауза, шаг, продолжение, скорость, остановка и новый прогон. Новый прогон возвращает те же условия к началу с прежней скоростью, затем запускается обычной кнопкой. Язык/тема/режим и редактирование независимой копии не пересоздают текущий Runner.

При работе/паузе поля записи текущего прогона, её сохранение/удаление заблокированы. Копия или другая запись редактируются независимо. Новый запуск из формы и уход к урокам требуют остановки/завершения текущего прогона. Старый пользовательский результат остаётся связан со своим RunConfig до следующего явного запуска и сохраняется в памяти при редактировании и посещении уроков. Архива результатов нет. Пользовательский прогон не попадает в таблицы уроков. Скрытый раздел не выводит отчёты с повторяющимися ID в DOM.

FlowDiagram, RunSummary и BottleneckSearch прежние. processLabels передаёт пользовательские имена через необязательный entityNames, поэтому ID вроде prep/raw не подменяют их подписями примеров. Режим custom исключает частные подсказки чужих примеров. Поиск использует захваченный RunConfig, а не свежие правки формы; уход из раздела отменяет поиск и очищает его подсветку.

## Хранение, JSON и API

Каждая запись хранится в своём ключе `toc.process.<id>`: schemaVersion=1, id, revision, updatedAt, config:EditorConfig. Отдельного индекса нет. ID записи отделён от config.id. revision является последней сохранённой версией; у новой памятной записи это 0. Перед обновлением/удалением revision читается повторно. Это обнаружение конфликта, не атомарная синхронизация вкладок. Повреждённые и будущие версии не затираются, остальные записи доступны.

openProcessStorage даёт list(), issues(), save(id,config,expectedRevision), remove(id,expectedRevision), read(id). Входы и выдаваемые данные независимы. Отказ доступа/чтения/записи оставляет данные в памяти с persisted=false и сообщением RU/EN, а не обещанием сохранения в браузере. Неудачная запись не повышает revision; повтор после восстановления возможен. read перечитывает одну запись, сохраняя остальные памятные данные. При отказе удаления запись убирается только из списка в памяти, браузерная запись может остаться; UI это объясняет.

Переносимый JSON: format=toc-process, schemaVersion=1, config:EditorConfig. Локальных revision/updatedAt, снимков, временных рядов и результатов там нет. exportProcessJson и parseProcessJson проверяют UTF-8 размер до 2 МиБ (2097152 байта), JSON, оболочку, обе версии и линейное подмножество. Неизвестные поля оболочки отклоняются. readProcessJsonFile проверяет размер до чтения, повторно проверяет фактический текст и сообщает ошибки чтения через ConfigError RU/EN. Предпросмотр не меняет библиотеку. Только принятие импорта создаёт запись; copyImportedProcess требует новый config.id, вызывающий код передаёт новый ID записи. Внутренние ID сохраняются. Копирование произвольных технических примеров в редактор не поддерживается.

## Текущий поиск узкого места

Кнопка «Поиск узкого места» использует применённые условия RunConfig, а не черновики полей. Она доступна до запуска, на паузе и после остановки/завершения, недоступна во время воспроизведения. Поиск отдельно прогоняет весь заданный горизонт с начала, включая разогрев, и не меняет текущие время/скорость/статус/выход Runner или таблицы уроков.

Для каждого поста все времена обработки его строк уменьшаются на 10%, с округлением до миллисекунды и минимумом 1 мс. Сохраняются партии, планы, распределения/CV (с поправкой округления границ), качество, переналадки, обслуживание, источники, начальные запасы и календарь. Поддержаны constant/lognormal/uniform/triangular. В копиях фактические ёмкости из resolved фиксируются явными значениями по материалам до ускорения, чтобы наследуемые буферы на долю смены не пересчитались вместе со временем.

При случайности (CV>0 или 0<p<1 для дефекта) выполняются три парных seeds: текущий, +1, +2 по модулю 2^32. Без случайности достаточно текущего seed. Это маленькая серия, не статистическое доказательство. Годный принятый выпуск сравнивается точно по каждому конечному продукту; разные продукты не суммируются, процентного деления на исходный выпуск нет.

Пост входит в список лидеров, если в каждой паре не уменьшает ни один продукт и увеличивает хотя бы один относительно исходника. Его результат также должен не уступать ускорению любого другого поста по каждому продукту в каждой паре. Один лидер: outcome=candidate. Несколько лидеров имеют одинаковые векторы в каждой паре: outcome=tied. Разные лучшие посты между seeds или обмен продуктов: ambiguous. Если положительного прироста вообще нет: noGain. Пустой список не означает, что у процесса нет ограничений; метод проверяет одиночное ускорение, а не все сочетания совместных изменений.

Актуальный BottleneckResult: productIds, samples, stationIds:string[], outcome=candidate|tied|ambiguous|noGain. Одиночного stationId в результате больше нет. В samples: seed, baseline:string[] и outputs с отдельными stationId/quantities. Только память, новой сохраняемой схемы нет. Таблица показывает выпуск и парное изменение; при нескольких seeds диапазоны. Старые частичные/отменённые результаты не публикуются.

Поиск последовательный, порциями до 64 отметок и примерно 8 мс с возвратом управления через таймер; компиляция и одна отметка сами не прерываются. Вызов не обращается к DOM. Отдельного Worker/сервера/очереди заданий нет. Результат привязан к calculationHash. Смена расчётных условий отменяет поиск, сбрасывает таблицу и рамки. Язык/режим/тема сохраняют результат; новый Runner с теми же условиями не делает его устаревшим. Начало воспроизведения отменяет выполняемый поиск через React effect; проверка должна дождаться обновления интерфейса.

## Подсветка и её смысл

Каждый найденный пост получает оранжевую пунктирную рамку 5 px, dash 10/4, и подпись «Кандидат в ограничение». Цвет светлой темы #c75b0a, тёмной #fb923c. Цвета реальных состояний постов сохранены. FlowDiagram принимает bottleneckStationIds; сам поиск не назначает drum DBR.

flowThroughStation в diagram.ts выделяет структурные маршруты от источников через пост к готовому продукту четырьмя обходами достижимости. Для нескольких кандидатов используется объединение routeIds без повторов. Все проходящие ветви включаются, обходные и соседняя ветвь перед сборкой не выдаются за проходящие через найденный пост. Ветвление не сводится произвольно к одному маршруту. Стрелки потока более толстые, пунктирные, цвета accent; есть пояснение RU/EN и пометки текстового списка. Координаты, анимация передач и расчёты модели прежние.

Это связи конфигурации, а не доказанный фактический критический путь изделия. История операций для такого пути не хранится. № 36 закрыта в реально принятом пользователем объёме; точный критический путь не оставлять как автоматически разрешённую следующую часть.
