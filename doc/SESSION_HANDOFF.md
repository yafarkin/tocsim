## Что реально работает

Есть автономная живая SVG-схема с RU/EN, независимые от DOM точная арифметика, компилятор линейной конфигурации, материальный учёт, чистый производственный календарь и событийная основа со стабильным порядком и согласованным шагом, источники push с общим сырьевым складом. Эти части соединены в работающую Simulation с шагом, продвижением до времени, полным горизонтом и остановкой; не отдельный демонстрационный симулятор.

Полный детерминированный цикл работает через Simulation, runner управляет просмотром в основном потоке. Пауза, шаг и скорость уже реализованы. RNG, графики, полный редактор, storage, импорт, уроки и A/B ещё не реализованы. EventScheduler сохраняет механизм фаз, а Simulation подключает в них цикл постов, не создавая отдельный движок. Интерфейс теперь использует engine и runner: SVG отображает фактический поток.

## Арифметика

Масштаб равен 1 000 000. Количество хранится как безопасное неотрицательное целое number в микроединицах, деньги как bigint микроденежных единиц. Абсолютный предел обоих равен Number.MAX_SAFE_INTEGER: 9 007 199 254 740 991 микроединице. Промежуточные произведения через bigint могут быть больше; проверяется конечный диапазон.

ParseQuantity и parseMoney принимают десятичные строки с точкой и максимум шестью знаками после неё. Не использовать parseFloat перед разбором. Пробелы, экспоненты, запятая, лишняя точность и завершающий перевод строки отклоняются. Форматирование возвращает точную десятичную запись.

AddQuantity, subtractQuantity и multiplyQuantity проверяют диапазон; множитель является целым числом повторений. AddMoney и subtractMoney поддерживают отрицательные результаты. Закупочная цена и фактическая стоимость запаса неотрицательны.

PurchaseCost округляет проводку один раз до ближайшей микроединицы, половину вверх. SplitCost выделяет долю из текущего остатка вниз, сохраняет разницу у остатка, последнее изъятие получает всё оставшееся. Не пересчитывать существующий запас по исходной цене. MoneyToJSON/moneyFromJSON обслуживают известные денежные поля как строки целых микроединиц, а не отображаемые суммы. Глобальный reviver для произвольных строк не нужен.

## Конфигурация и идентичность

CompileConfig принимает unknown, проверяет поля и создаёт независимый глубоко замороженный RunConfig. Source сохраняет исходную форму для будущего «изменить копию», resolved содержит микроединицы и разрешённые значения. Исходник не меняется. Тип DeepReadonly дополняет runtime Object.freeze.

Теперь принимаются несколько источников с маршрутами к первым постам и производственные цепочки без сборок или разветвлений выходов. Вход поста может иметь несколько маршрутов только от сырьевых источников; выходной маршрут поста один. Источники одного raw material должны иметь одинаковую availability. Все сущности используются, циклы и повторные маршруты отклоняются. На посту одна строка плана, один рецепт, одна последовательная обработка, cv: 0, без переналадки и обслуживания. Рецепт production имеет один дробный положительный вход и один целый положительный выход; выпуск 10 не означает 10 повторений операции.

ID уникальны среди объектов, строк планов и начальных запасов. Разрешены ASCII-буквы, цифры, _ и -. Зарезервированы market и warehouse. Компилятор не создаёт и не перенумеровывает ID. Источник имеет availability virtual либо warehouse; конечный сырьевой склад общий по материалу.

Буферы только явно заданные количества либо отдельный вид infinite. Вход должен вмещать комплект, выход может быть нулевым или меньше выпуска. GlobalBuffers, наследование и норматив по доле смены пока отклоняются; они будут на этапе 5. Начальный запас имеет ID, владельца, место, материал, количество и явную стоимость. Проверяются суммы вместимости и диапазон.

Неизвестные поля и schemaVersion отклоняются. ConfigError содержит code, path, objectId при доступном ID и причины ru/en. Возвращается первая ошибка. Полноценного импорта, хранения и миграций пока нет; пользовательские строки не исполняются.

Нормализация сортирует сущности по стабильным ASCII-ID, переводит десятичные строки в микроединицы и фиксирует порядок полей. Расчётный хеш FNV-1a 64 включает расчётные поля и версии, исключает названия, цвета, язык, displayOrder и ID редакторской копии. Стабильные ID расчётных сущностей включены. Это воспроизводимый отпечаток, не защита и не гарантия отсутствия коллизий. Для точного повторения нужны параметры и совместимые версии.

## Материальный учёт

InventoryState содержит единственный массив stocks и nextStockOrdinal; EngineState расширяет его timeMs и stations. StockState содержит ID, владельца, место, материал, количество, стоимость и provenance. Места: warehouse, input, output, reserved, held. Записи не сливаются, FIFO определяется порядком поступления в массиве, а не временем происхождения.

Provenance содержит origin, defective, defectSourceIds и processingMs. Origin бывает unreleased (ещё на сырьевом складе), known со startedAtMs либо unknown для начального WIP неизвестного возраста. При выпуске берётся минимум известных времён; наличие unknown делает возраст потомка неизвестным. Подставлять 0 вместо неизвестного возраста нельзя.

ProcessingMs является вектором bigint миллисекунд обработки по stationId. Доли времени и стоимости разделяются с сохранением остатка; точность времени 1 мс. Сборка суммирует фактические стоимости и векторы. Один дефектный компонент делает дефектным результат одного повторения; независимый следующий комплект не загрязняется. Генерации брака и контроля нет, сохраняются переданные атрибуты. Полного дерева предков нет.

CreateInventory создаёт независимые начальные записи из RunConfig. ReceiveStock принимает уже оценённый запас, не закупает его. TransferStock меняет владельца/место и добавляет доли в конец очереди получателя. ConsumeStock удаляет доли ровно один раз и возвращает их вызывающему коду для будущего учёта выбытия. ReserveInputs изымает полный комплект из input в reserved. CompleteProduction потребляет один резерв и создаёт целый held-выпуск, добавляя фактическое время обработки.

При reserved или held новый резерв запрещён; прямой приём, перенос и consumeStock для reserved запрещены. После завершения входы не дублируют выход в WIP. При нулевом выходном буфере результат остаётся held на посту; отдельного 0/0 буфера нет. Перенос с ёмкостью выполняется отдельно.

Полная запись сохраняет ID, частичная доля и выпуск получают lot:N. Счётчик локален состоянию. Операции работают на копии и заменяют запас со счётчиком только после проверки всего результата. Ошибка нехватки второго компонента, ёмкости или переполнения не оставляет частичных изменений. Возвращаемые объекты независимы. Копирование массива выбрано как простое решение; оптимизация только по измерениям.

Низкоуровневые операции принимают параметры и ёмкости от вызывающего кода, не выбирают маршруты и не планируют работу поста. Поддержка комплекта из нескольких материалов проверяет агрегаты, но compileConfig по-прежнему не допускает производственные сборки. CompleteProduction завершает одно повторение, не многократную партию. Это важно для будущего сохранения отдельных комплектов при браке.

## Календарь и точный горизонт

Модельное время 0 равно открытию первой смены. Расписание задаётся миллисекундами от полуночи условных суток. Сутки равны 86 400 000 мс, дни повторяются без выходных, реальных дат и часовых поясов. Одна смена, один обед строго внутри; ночная смена через полночь не поддерживается, конец ровно в 24:00 допустим.

CreateCalendar(schedule, days, workDuringLunch) создаёт независимый замороженный календарь. EndTimeMs равен `(days − 1) × DAY_MS + shiftEndMs − shiftStartMs`. Поле EditorConfig.durationMs теперь означает именно этот интервал; calendarForDuration восстанавливает число дней, compileConfig проверяет соответствие. Прежний технический пример 86 400 000 для одного дня заменён на 32 400 000 при смене 08:00–17:00. Новый UI должен выбирать дни и записывать вычисленный горизонт. Схема данных не менялась.

CanStart использует полуоткрытые рабочие интервалы и исключает горизонт. NextOpening возвращает текущее/следующее открытие или null. WorkedMsUntil и activeWorkMs считают активные миллисекунды; минуты только для отображения. AdvanceWork возвращает момент и remainingMs, не дорабатывает после горизонта. Завершение ровно на закрытии засчитывается, новый старт проверяется отдельно. Нулевой остаток возвращается в исходной точке.

Операция на 20 минут с 11:50 заканчивается в 13:10, с 16:50 в 08:10 следующего дня. Подмена в обед даёт 12:10 в первом примере. Источник всегда использует общий календарь без подмены. Чистые функции поддерживают подмену поста, но compileConfig пока отклоняет lunchReplacement: true до соответствующего этапа полной механики.

SourceAttemptTime вычисляет координату `ordinal × intervalMs` в общем накопленном рабочем времени без ежедневного сброса. Попытка 0 в начале; точное закрытие переносит попытку на открытие, конечный горизонт исключён. V34: 11:58 → 13:05 и 16:56 → 08:03. В № 15 эти моменты подключены к фактическому допуску, закупкам и общему складу через events.ts и inventory.ts.

Арифметическое пропускание дней не обходит каждый день; большие произведения через bigint и безопасный конечный диапазон. CalendarError содержит code value/range и причины RU/EN. ClockAt возвращает индекс дня с нуля и время суток для отображения.

## Событийная основа после № 14

EventScheduler из events.ts принимает RunConfig, EngineState и фиксированные EventHandlers: integrate, completion, calendar, source, transfer, dispatch. Это не универсальная шина; произвольных payload, подписок и плагинов нет. Состояние и события копируются. Обычный массив сортируется по времени, фазе и лексикографическому ID. Дубли ожидающих ключей запрещены.

Step обрабатывает ближайшую полную отметку. AdvanceTo обрабатывает события до цели включительно, затем при необходимости начисляет интервал без событий. До конца отметки getSnapshot возвращает прежний снимок. На успехе новая копия состояния и снимок фиксируются, на ошибке вся отметка откатывается и scheduler останавливается с getFailure. Возвращаемый StepResult содержит timeMs, processedEvents, staleCompletions и finished. Число событий не является числом производственных операций.

Контекст обработчика содержит draft state, timeMs, schedule и invalidateOperation. Обработчики должны быть синхронными, доверенными функциями движка и менять только draft/очередь. Внешние побочные эффекты не откатываются. Внутри обработчика нельзя повторно вызывать методы продвижения/добавления самого scheduler. После отметки контекст закрыт; сохранённые ссылки на draft не меняют зафиксированное состояние.

StationState теперь имеет operationVersion. CompletionEvent хранит токен версии. Неактуальный токен пропускается, актуальный потребляется повышением версии до вызова completion. Это предотвращает повторный выпуск. При паузе нужно сохранить остаток и вызвать invalidateOperation; после открытия запланировать завершение с новой текущей версией и календарным расчётом. Полный цикл поста подключён в Simulation в № 16. В UI-снимок внутренний operationVersion не включён, схема снимка теперь 4 из-за данных источников и линии; operationVersion всё так же не сериализуется.

Порядок: integrate прошлого интервала, completion, calendar/horizon, source, transfer, dispatch, повтор мгновенных передач/назначений до устойчивости, затем снимок. Возврат к уже пройденным ранним фазам запрещён; dispatch→transfer допустим для стабилизации. Предел MAX_TRANSITIONS_PER_TIMESTAMP = 10 000 технический, при превышении частичный снимок не публикуется. Финальные бюджеты определяются будущими измерениями.

Автоматический horizon гарантирует точный конец даже пустого производства. На нём completion и transfer выполняются, source и dispatch пропускаются. После горизонта и в опубликованную отметку нельзя добавлять события. Прогон не читает реальные часы. EventError содержит code, objectId, ru/en. Полные API и проверки основы в EVENTS.md, цикл постов в SIMULATION.md.

Проверены сортировка независимо от порядка добавления, один снимок после dispatch→transfer, совпадение step/advanceTo, независимость экземпляров, две completion одной версии с одним фактическим выпуском, пауза в обед и новый конец по остатку, закрытие/горизонт, откат выпуска при следующей ошибке, бесконечная мгновенная цепь и диагностика. Это проверочные обработчики, не готовая симуляция линии.

## Источники после № 15

Sources.ts экспортирует createPushState, createPushHandlers, scheduleInitialSources и createPushScheduler. Последняя создаёт только прогон источников: посты не обрабатывают материал. Simulation переиспользует эти части в одном EventScheduler. Обработчик transfer с producerId @sources распределяет пакет допусков сырья; другие transfer-события он отклоняет. Будущий общий transfer должен различать этот случай и готовый результат поста. Integrate обработчика push очищает только записи передач последней отметки; при добавлении интегралов его надо сохранить в композиции.

Source-фаза отмечает текущие попытки всех источников, одно transfer-событие затем планирует допуски. Порядок конкуренции: приоритет получателя по убыванию, sourceId, stationId. Для одного источника это приоритет и ID получателя; между источниками равного приоритета sourceId предшествует stationId. Свободный вход, бюджет попытки и общий warehouse-остаток ограничивают объём. Блокировка одной пары не останавливает другие. Невыпущенная часть забывается, долг не накапливается. Следующая попытка ставится через sourceAttemptTime, на горизонте её нет.

Конечный запас передаётся через transferStock, с его фактической стоимостью, без повторной закупки. Для виртуального сырья сначала планируется весь реально допущенный объём одной попытки, затем одна закупка purchaseCost и разделение её стоимости через splitCost между получателями. Не округлять отдельную закупку для каждого маршрута: это создаёт лишние микроединицы стоимости на дробных частях.

EngineState теперь имеет sources и sourceTransfers. SourceState: sourceId, nextOrdinal, pendingQuantity, attempts, releasedQuantity, purchasedCost, lastAttempt. LastAttempt содержит время, requestedQuantity, releasedQuantity и blockedBy (capacity/stock, может быть обе причины). PendingQuantity обнуляется после отметки. SourceTransfers хранит только текущую отметку: время, источник, пост, материал, количество и фактическую стоимость. Следующий integrate очищает список. После обнаружения исчерпания конечного warehouse новые попытки больше не планируются; уже поставленная ближайшая попытка ещё может отметить отсутствие сырья. Это ограниченные данные для UI, не бесконечный журнал.

Snapshot схемы 4 показывает источники без внутренних nextOrdinal/pendingQuantity, цены и стоимость строками целых; вложенные причины копируются и замораживаются. Старые снимки приложение не сохраняло/импортировало. Продолжения по снимку нет; при будущем хранении нужна явная совместимость и миграции. Полный финансовый отчёт, продажи и списания не добавлены.

CompileConfig теперь разрешает несколько источников и первые посты, включая общий рецепт у альтернативных первых постов. Производственные входы остаются однотипными; несколько входных маршрутов разрешены только от сырьевых источников. Выход поста один. Сборки и производственные разветвления по-прежнему отклоняются. Начальный warehouse проверяется по наличию конечного источника того же материала; диапазон количества считается отдельно по материалам. Смешанная virtual/warehouse доступность одного raw material отклоняется, чтобы не создавать два вида общего остатка.

Проверены V23 с двумя источниками и общим запасом 5, сохранение фактической стоимости/признаков без повторной покупки, приоритеты, независимость от порядка массивов, заполненный вход, дробное свободное место, один закупочный остаток, отсутствие долга, V34, бесконечный вход, равенство step/advanceTo и неизвестное расписание. Все источники используют общий календарь, подмена поста на сырьё не влияет. Подробности в SOURCES.md.

## Работающая линия после № 16

Simulation из simulation.ts принимает RunConfig и создаёт единый EventScheduler с учётом, источниками и календарём. API: step, advanceTo, runToEnd, getSnapshot, stop, getFailure. Первый step/advanceTo(0) обрабатывает стартовую отметку. После пользовательского stop модель не продолжается, повтор создаёт новый экземпляр. Пауза просмотра реализована в Runner и не вызывает stop.

Transfer @line разгружает более старый output перед новым held. Нулевой выход передаёт held напрямую; положительный сначала принимает готовое в собственный буфер, затем передаёт дальше. Частичная выгрузка разрешена. Новая обработка возможна после освобождения held, даже если отдельный output ещё полон. Dispatch резервирует один комплект и запускает положительную детерминированную операцию. Освободившиеся входы снова будят передачи до устойчивости. Внутренние transferPending/dispatchPending предотвращают дубли служебных событий и не попадают в снимок.

Integrate уменьшает remainingProcessingMs по activeWorkMs. Закрытие сохраняет остаток и инвалидирует completion. Открытие планирует новый токен, старое событие пропускается. Completion точно на границе принимается до календаря. Для совпадения 24:00 и следующего 00:00 активная операция явно переводится в paused до назначения новой версии. Пропущенное завершение с отрицательным остатком является ошибкой, не исправляется молча.

На завершении reserved изымается, held создаётся ровно один раз; тогда же увеличиваются consumed/produced по материалам. При рынке годный выход увеличивает sold/soldCost; переданный скрытый дефект даёт scrapped/scrapCost. Случайного брака, контроля, T/OE/NP и расчёта lead time пока нет. Не выдавать эти счётчики за полный финансовый отчёт. Происхождение сохраняется в физических записях; будущие метрики выбытия должны агрегировать нужные атрибуты из возвращённых consumeStock долей.

EngineState имеет line: LineState|null, у source-only прогонов null. LineState хранит внутренние pending-признаки, counters и transfers текущей отметки. Snapshot схемы 4 добавляет line и расширенный пост: progress, input с missingQuantity, output с heldQuantity и blockedBy. Processing/Starved/Blocked/Paused различаются; календарные причины lunch/offShift/horizon имеют приоритет. Сохраняется остаток обработки и фактические запасы, даже если на экране первична календарная причина.

LineSnapshot.termination: running/horizon/stopped/error; flow: normal/exhausted/missingInput/blocked. Полный горизонт не сокращается при исчерпании сырья. Дробного остатка меньше комплекта недостаточно для старта, он остаётся с явной нехваткой. Остановка хранит фактическое время и не меняет уже достигнутый horizon. Первая ошибка бросается вызывающему коду, снимок отмечен error на последней согласованной отметке, getFailure сохраняет исходную причину. После терминального stop/error step возвращает null.

Проверены линии 3–6 постов. V01: первое изделие в 15 минут и 10 к 60; V02: 3/8/3 даёт первое в 14 и 29 к 240. V03/V04: при занятом потребителе нулевой выход блокируется после 4 выпусков, выход на 3 после 7. V05: 6 передано, 4 held, остаток затем освобождается. V06/V07/V08/V28: обед, ночь, границы, устаревший токен и отсутствие двойного выпуска. ## Runner после № 17

Runner из src/runner/runner.ts создаёт Simulation с неизменяемым RunConfig и отделяет состояние просмотра от расчёта. Методы start, pause, resume, step, setSpeed, stop, repeat, getView, getFailure и dispose. RunConfig доступен readonly, повтор использует тот же объект, seed, версии и исходную конфигурацию. Repeat сразу запускает новый прогон, сохраняя только скорость. Старт/повтор не выполняют физические события синхронно, они ставят отложенную порцию.

RunnerView схемы 2 содержит status, speed, model Snapshot схемы 4, transfers и error с code/причинами RU/EN. Данные глубоко заморожены и JSON-совместимы. Статусы ready/running/paused/finished/stopped/error/disposed. Paused относится к просмотру; модельный пост может сохранять processing с неподвижным прогрессом. Stop терминальный, pause допускает resume. Шаг из ready/running/paused выполняет одну полную отметку и оставляет paused либо finished у горизонта.

Числовая скорость положительна и конечна, означает модельные мс на реальную мс; дробная цель сохраняется. Max вычисляет до горизонта порциями. Смена числовой скорости учитывает уже прошедший реальный интервал по старой скорости. После max числовой режим начинается от достигнутой отметки. Pause сбрасывает невыполненную цель к достигнутому времени, resume задаёт новую реальную опору: пауза и вычислительный долг не дают скачка после продолжения.

Default host использует performance.now и setTimeout(0). Настоящие часы только в runner, не в engine. RunnerHost задаёт now/request/cancel; request должен быть отложенным, не синхронным. В очереди один таймер. Pause/stop/repeat/dispose отменяют его; старый callback защищён токеном и не может продвинуть повтор. Dispose не уведомляет уже удалённый UI. OnUpdate можно использовать для React-состояния; пауза прямо из него отменяет следующую порцию.

Порция ограничена 64 полными отметками и проверкой бюджета 8 мс между ними. Одна тяжёлая отметка не прерывается и может превышать бюджет. Это не измеренная гарантия 16 мс и не замер браузерной реакции 250 мс. Worker и сложного планировщика нет. EventScheduler/Simulation получили наблюдательный nextEventTime, который позволяет не выходить за цель и безопасно начислять хвост без событий. Расчёт и engineVersion 0.6.0 не изменились.

Обновление UI публикуется после команды или порции, не внутри отметки. Модельный снимок является последним в порции; transfers дополнительно агрегирует реальные передачи каждой её отметки. Это пакет по связям, не журнал. Resume очищает старый пакет без проигрывания старого движения. Не восстанавливать движение из выдуманных скоростей или числа видимых фишек.

Проверены скорость 1/120/max и шаг против прямой Simulation, пауза на час, смена скорости/дробная цель, отмена старого callback, повтор, dispose, шаг целой отметкой, ошибки часов и движка, данные без ссылок и неизменность RunConfig. Отдельно исполнен настоящий отложенный default host в Node. Все 238 тестов, TypeScript и build прошли. UI использует runner с frame-host через requestAnimationFrame. Визуальная приёмка № 18 выполнена, но численные браузерные замеры 16/250 мс не заявляются. Полные API и границы в RUNNER.md.
