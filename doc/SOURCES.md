# Источники push и общий склад

Задача № 15 завершена 2026-10-20. Код в `src/engine/sources.ts`, проверки в `sources.test.ts`. Источники используют существующие календарь, EventScheduler и учётные операции; полного цикла станка пока нет.

## Подключение

| API | Назначение |
|---|---|
| createPushState(run) | Начальное состояние учёта, постов, источников и передач |
| createPushHandlers(run) | Фиксированные обработчики source, transfer и очистки записей передач в integrate |
| scheduleInitialSources(scheduler, run) | Первые события источников в модельное время 0 |
| createPushScheduler(run) | Готовая связка только источников, без обработки постов |

Для полного цикла № 16 нужно переиспользовать эти функции, добавив обработчики постов, а не создавать второй движок. Transfer с producerId @sources является внутренней пакетной обработкой допусков сырья. Другие передачи этот обработчик отклоняет; будущий общий обработчик должен направлять их в логику постов.

## Расписание и распределение

Первая попытка источника происходит в начале первого дня. Следующая ставится через sourceAttemptTime по накопленному общему рабочему времени. На отметке хранится не более одной следующей попытки каждого источника. Обед и ночь не сбрасывают остаток интервала, подмена отдельного поста не разрешает сырьевой выпуск в обед. Попыток на конечном горизонте нет.

В фазе source отмечаются все источники, которым разрешена попытка. Затем одно событие transfer распределяет их конечные количества по явным маршрутам. Общая конкуренция сортируется по убыванию приоритета получателя, затем sourceId и stationId. Поэтому при равном приоритете разных источников действует sourceId; для одного источника получатели равного приоритета сортируются по stationId. Порядок массивов конфигурации не влияет на результат.

Допуск не превышает количество текущей попытки, свободный вход и остаток конечного сырья. Несколько источников используют одни warehouse-записи по materialId. Блокировка одного получателя не мешает другим допустимым парам. Частичные микроединицы допустимы. Невыполненная часть попытки после распределения забывается: долг не накапливается, новая попытка имеет обычное настроенное количество.

Бесконечный вход не вызывает мгновенного заполнения: каждая попытка ограничена количеством, а следующий момент строго позже в рабочем времени. Положительность интервала проверяется конфигурацией. Конечная закупочная цена и технический безопасный диапазон действуют и при бесконечной ёмкости.

## Стоимость и происхождение

Конечный исходный склад передаётся через transferStock с фактической стоимостью и FIFO. Повторной закупки нет; закупочная цена материала для переоценки этого запаса не используется. При первом допуске unreleased получает известное время запуска. Дефекты и вектор приписанного времени не теряются.

Для виртуального сырья сначала планируется фактически размещённое количество попытки. Затем purchaseCost округляет одну общую закупку на это количество. При нескольких получателях эта стоимость делится через splitCost с сохранением остатка. Поэтому две половины при цене в одну микроединицу дают в сумме одну микроединицу, а не две отдельные округлённые закупки.

Всё распределение одной отметки находится в транзакции EventScheduler. Ошибка нехватки диапазона или учёта откатывает запасы, счётчики источников, закупки и записи передач вместе. Финансовый отчёт периода, продажи и списания не добавлялись.

## Состояние и данные для UI

SourceState хранит sourceId, nextOrdinal, pendingQuantity, attempts, releasedQuantity, purchasedCost и lastAttempt. LastAttempt содержит время, запрошенное и выпущенное количество и blockedBy с кодами capacity и stock. При полном выполнении blockedBy пуст. При частичном или нулевом допуске могут присутствовать обе причины. Внутренний pendingQuantity обнуляется после отметки и не превращается в долг.

SourceTransfers содержит только передачи последней обработанной отметки: время, источник, получатель, материал, количество и фактическую стоимость. При следующем начислении интервала список очищается. Неограниченный журнал не накапливается. Последняя попытка каждого источника и накопительные счётчики сохраняются в состоянии.

В снимке не показываются внутренние nextOrdinal/pendingQuantity, денежные суммы кодируются строками целых микроединиц. Вложенные причины копируются и замораживаются. Это данные для будущего UI; визуализация движения и вывод причин на странице в № 15 не реализовывались.

## Расширение допустимой конфигурации

Для проверки общего сырья теперь разрешены несколько источников и их маршруты к нескольким первым постам. На посту остаются один входной материал, один рецепт и один выходной маршрут. Вход может иметь несколько маршрутов только от источников того же сырья. Разветвление выходов поста, сборки и слияние нескольких производственных ветвей остаются запрещены.

Разные первые посты могут использовать общий рецепт, а отдельные цепочки заканчиваются в market. Все посты, рецепты и материалы должны участвовать в сети; циклы, повторные маршруты и отсутствующие ссылки отклоняются. Все источники одного raw material обязаны иметь одинаковую availability, поскольку обращаются к одному виду склада. Для разных сырьевых материалов вид доступности может различаться.

Начальные warehouse-записи проверяются по существованию конечного источника соответствующего материала. Диапазон складского количества проверяется отдельно по материалам, без сложения несопоставимых физических единиц. Общая стоимость запасов по-прежнему имеет единый диапазон.
