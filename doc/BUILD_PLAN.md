## 1. Назначение и границы плана

План определяет порядок реализации, зависимости, промежуточные результаты и проверки. Он не является списком задач: здесь нет исполнителей, статусов разработки, сроков или отдельных карточек. По отдельному поручению пользователя этапы 1–4 разложены на первоочередные задачи № 8–19 в [tasks.md](../tasks.md). После первой очереди согласованы задачи этапа 5 № 28–32 и отдельно запрошены № 36–39. Остальные поздние работы остаются в плане; весь план заранее в трекер не переносится.

Предметные правила берутся из концепта. План не заменяет их и не вводит дополнительных механик. Если реализация выявит противоречие, сначала уточняется соответствующее правило концепта и проверочный пример, затем меняется код. Нельзя молча исправлять модель ради удобства интерфейса или прохождения урока.

Целевой результат остаётся прежним: автономный HTML, RU/EN, песочница, десять уроков, несколько материалов и рецептов, сборка и разделение, два режима партий, буферы постов и глобальные значения, вариативность, обслуживание, контроль, push, ограниченный учебный DBR, метрики, A/B, локальное сохранение и перенос конфигураций.

Промежуточная линейная линия нужна для проверки основы. Она не заменяет согласованный MVP. Этапы последовательно расширяют одну реализацию; отдельный демонстрационный движок, который затем придётся переписывать, не создаётся.

## 2. Принципы порядка реализации

Сначала проверяется способность поставить приложение одним локально открываемым файлом. Затем создаются точные данные и событийная основа. На этой основе рано появляется настоящая наглядная схема с движением и паузой. После этого добавляются сложные потоки, потери и управление. Полный редактор, сохранение и учебные тексты подключаются к уже проверяемой модели.

Двигаться дальше следует после выполнения условия перехода текущего этапа. Допустимо исправлять ранний этап, когда появился новый воспроизводимый случай. Нельзя обходить провал основы дополнительной логикой в React или анимации.

Наглядность проверяется дважды: на минимальном потоке и на полной модели со сборкой и развилкой. Автономная сборка проверяется с начала и затем после добавления значимых браузерных возможностей. Это предотвращает позднее обнаружение проблем `file://`.

Принцип «НЕ ПЕРЕУСЛОЖНЯТЬ!» действует на каждом этапе. Используются один клиентский проект, один движок и обычные модули. Не нужны монорепозиторий, плагины производственных механик, универсальный оптимизатор, сервер, отдельная система событий UI или заранее созданный Worker. Зависимость добавляется только при понятной пользе для текущего результата.

## 4. Этап 1. Основа проекта и автономная сборка

### Результат

Минимальный TypeScript/React-проект с одной страницей, встроенным оформлением и SVG-элементом собирается в один HTML. Это проверка технологического пути, пока без симуляционной логики.

### Порядок реализации

Сначала выбрать совместимые версии Node.js, TypeScript, React, Vite и средств проверки. Зафиксировать версии зависимостей и lock-файл. Не ориентироваться на предполагаемые номера из текста концепта. Настроить строгую проверку TypeScript, тестовый запуск и production-сборку.

Затем проверить однофайловую сборку на минимальном примере. JavaScript, CSS, словари и встроенные данные должны попадать внутрь HTML. Не использовать CDN, сетевой шрифт, загрузку соседнего JSON, динамические chunks или обязательную регистрацию service worker.

Предусмотреть простое обращение к словарю RU/EN с первого экрана, чтобы дальнейшие подписи не приходилось извлекать из всех компонентов. Полные тексты уроков на этом этапе не писать. Данные UI пока находятся только в памяти.

Разделение кода вводить по мере появления ответственности: определения предметной модели, движок, runner и UI. Не создавать пустую инфраструктуру под каждую будущую возможность. Разделы архитектуры из концепта задают границы зависимостей, а не обязательное количество пакетов.

### Проверка и условие перехода

Открыть production-HTML напрямую через `file://` с отключённой сетью. Проверить выполнение скрипта, отображение SVG, смену языка и отсутствие обязательных внешних запросов. Проверить тот же файл через простой статический сервер в подкаталоге. Локальный сервер нужен только для этой проверки, а не пользователю приложения.

Если самостоятельный файл не работает, устранить причину до разработки большого интерфейса. Не откладывать проблему до финальной сборки и не заменять требование обязательным localhost.

## 5. Этап 2. Контракты и точная учётная основа

### Результат

Определены входные конфигурации, состояние прогона и снимок для UI. Есть точные операции количества, стоимости, резервирования и передачи. Пока эти операции можно проверять без реального времени и браузера.

### Порядок реализации

Сначала описать материалы, рецепты, посты, строки циклического плана, профили партий, маршруты, источники, календарь и настройки буферов. Использовать сущности концепта: сборка является постом с несколькими входами, а контроль отличается типом операции. Сборка и буфер не требуют отдельного универсального движка компонентов.

Разделить данные на следующие представления:

| Представление | Содержимое | Допустимые изменения |
|---|---|---|
| Редакторская конфигурация | Исходные значения, наследование буферов, стабильные ID, schemaVersion | До старта или в новой копии |
| RunConfig | Исходная конфигурация, разрешённые значения, seed, версии и расчётный хеш | Неизменяемый после создания |
| Состояние движка | Остатки, операции, события, счётчики и текущий момент | Только через переходы движка |
| Снимок для UI | Согласованные количества, состояния, причины, метрики и сведения о передачах | Копия для чтения, без изменения движка |

Затем реализовать разбор десятичных количеств в микроединицы, проверку диапазона и целого положительного выхода. Денежные суммы и распределение остатка выполнить по правилам 3.16 концепта. Строковое представление больших целых на границе JSON определить сразу, чтобы позднее не менять схему из-за BigInt.

Реализовать элементарные учётные переходы: выделить количество из FIFO-остатка, перенести, зарезервировать на посту, преобразовать входы в выходы, разделить стоимость и признаки происхождения. При разделении сохранять время запуска, неизвестный возраст, скрытый дефект и долю приписанных минут. Не хранить полное дерево предков, если достаточно агрегатов концепта.

Ввести стабильные ID и единую функцию нормализации расчётной конфигурации. Названия и язык не должны менять случайность или расчётный хеш. Сохранять различие между «наследовать» и «собственное значение».

Проверки структуры и числовых значений отделить от проверок применимости политики. Последние будут дополняться вместе с реализацией DBR. На промежуточных этапах неподдерживаемая механика отклоняется явно; недопустимо принимать её параметры и затем игнорировать.

### Проверка и условие перехода

Проверить дробные расходы, выпуск 1→10 и 10→1, передачу частей и сохранение остатка стоимости. Подготовить набор небольших конфигураций как входные данные будущих тестов. Это технические проверочные примеры, а не окончательные уроки.

Переходить к времени после того, как последовательность учётных операций не создаёт отрицательных остатков, лишнего материала и денег. Ошибки арифметики не компенсируются округлением отображаемых значений.

## 6. Этап 3. Детерминированный событийный движок

### Результат

Из конфигурации можно получить повторяемый прогон простой линии с настоящими сменами, обедом, источниками, конечными буферами и push. Движок запускается в тестах без DOM, React и storage.

### Порядок реализации

Сначала реализовать рабочий календарь и преобразования между абсолютным модельным временем и накопленным рабочим временем. Проверить паузу операции, сохранение остатка, переход к следующему открытому моменту и точный конец горизонта.

Затем реализовать очередь событий, упорядоченную по времени, фазе и стабильному ID. Время хранить целыми миллисекундами. Начальная реализация может целиком обрабатывать одну временную отметку синхронно, но публичная граница уже должна различать атомарный переход и законченный снимок отметки.

Подключить источник и общий сырьевой остаток. Попытки источника отсчитывать в накопленном рабочем времени, включая перенос через обед и ночь. Для нескольких источников одного материала остаток общий. Неисполненная push-попытка не создаёт долг.

После этого реализовать цикл поста для одного рецепта и партии 1. На каждой отметке выполнять фазы из 3.13 концепта: интегрирование прошедшего интервала, завершения, календарь, разрешения, передачи, новые старты, согласованный снимок. Резервирование и выпуск использовать из этапа 2.

Добавить конечный входной и выходной буфер, нулевую выходную ёмкость, удерживаемый результат и частичную выгрузку. Пост не должен начинать новую обработку, если предыдущий результат его удерживает. Обеденная и ночная пауза отменяет старое завершение операции либо делает его недействительным по версии.

Разделить состояние завершения прогона и диагностику потока. Нехватка сырья не является ошибкой вычислений. Зафиксировать события переходов состояний и передачи как данные, которые позже сможет показать схема. Пока достаточно количеств, длительностей состояний и физических выходов; непостроенные денежные показатели не изображать фиктивными числами.

### Проверка и условие перехода

Проверить аналитический пример трёх постов по 5 минут, границу мощности детерминированного ограничения, ночную и обеденную паузу, завершение ровно на границе, блокировку и общий склад. Сравнить обработку отметка за отметкой с продвижением сразу до заданного времени.

Движок не должен читать реальные часы, использовать таймеры браузера или сам рисовать. Переход к схеме разрешён, когда одинаковый RunConfig даёт одинаковую последовательность событий и итог простой линии.

## 7. Этап 4. Первая наглядная симуляция

### Результат

На экране видна работа настоящей простой линии: материал поступает, перемещается, накапливается и блокирует соседние операции. Пауза, шаг и скорость работают через runner, а не через изменение времён постов.

### Порядок реализации

Сначала реализовать runner в основном потоке: он вызывает движок порциями, хранит состояние запуска и отдаёт UI только законченные снимки. Реальные часы используются только для выбора следующего целевого модельного времени. Применённая скорость не попадает в формулу обработки или RNG.

Затем построить минимальную SVG-схему: посты, входные и выходные стопки, стрелки, названия материалов, число деталей, прогресс и подпись состояния. Использовать стабильные ID постов для связей и выбора. Не создавать пока все формы конструктора и окончательную систему графиков.

Подключить иллюстрацию фактических передач по данным движка. Уже на этом этапе различать анимацию и учёт: фишка движения не создаёт дополнительную деталь. Показывать голодание с причиной и блокировку с удерживаемым результатом.

Добавить постоянно доступные старт, паузу, продолжение, шаг, скорость, остановку и повтор. На старте конфигурация фиксируется. На паузе завершить визуальные иллюстрации в конечных положениях и остановить их; шаг обрабатывает следующую полную отметку и вновь оставляет прогон на паузе.

### Проверка и условие перехода

Проверить, что человек по схеме может показать направление потока, место очереди и пост без работы. Проверить паузу и шаг на передаче и на завершении обработки. Сравнить итог с прямым запуском движка без UI и при разных скоростях.

Если схема показывает только меняющиеся числа и по ней нельзя понять поток, исправить отображение сейчас. Наглядность не откладывается до полировки. Повторить проверку production-HTML через `file://`.

## 8. Этап 5. Несколько материалов и полный производственный поток

### Результат

Движок поддерживает сборку, разветвление, несколько рецептов одного поста, оба режима партий, транспортный порог, переналадку и все согласованные настройки буферов.

### Порядок реализации

Сначала расширить маршрутизацию на произвольный допустимый DAG постов. Материал передаётся только по явным маршрутам. Обработать нескольких получателей по приоритету и ID, нескольких производителей по FIFO и готовности. Убрать любые предположения «у поста один сосед» из вычислений и снимка.

Затем добавить атомарный набор нескольких входов для сборки. Полный комплект всей партии резервируется до старта. Отсутствие одного компонента не компенсируется наличием другого. Дробный остаток и последующее пополнение используют уже проверенные операции количества.

На этой основе реализовать последовательную обработочную партию, накопление до транспортного порога и выпуск последнего остатка. Отдельно реализовать одновременный цикл, в котором выход появляется только в конце. Не смешивать время одного повторения и всего цикла. При недостатке места выгружать доступную часть, а остатком удерживать пост.

После этого добавить циклический план рецептов и переналадку при смене recipeId. Сохранять правило ожидания очередного рецепта без пропуска строки. При одинаковом рецепте переналадка не добавляется. Переналадка приостанавливается календарём.

Завершить разрешение глобальных буферов и переопределений постов. Ёмкости «на долю смены» вычисляются из плана до запуска. Расчётный минимум повышается до комплекта партии, а недостаточное явно введённое количество выдаёт ошибку. В RunConfig фиксируются вычисленные количества и исходные правила наследования.

### Проверка и условие перехода

Проверить четыре независимых случая: простая цепочка, сборка двух ветвей, общий материал двух потребителей, один пост с двумя рецептами и переналадкой. Для каждой конфигурации проверить WIP на посту, FIFO, отсутствие дублирования входов и частичную выгрузку.

Временный просмотр схемы из этапа 4 должен уже отображать эти конфигурации хотя бы без окончательной компоновки. До добавления потерь должны проходить количественные проверки без случайности. В частности, `0.3 A → 1 B` не должен порождать вечный голод из-за остатка в буфере.

## 9. Этап 6. Вариативность, обслуживание и качество

### Результат

Работают все случайные механизмы и потери MVP. Прогоны повторяются по конфигурации, seed и версиям. Календарная пауза не генерирует новую длительность.

### Порядок реализации

Сначала ввести версионированный генератор и ключи случайности: seed, пост, рецепт, номер операции, назначение и sampleIndex. Написать эталоны базовых значений. Затем подключить распределения: детерминированное, логнормальное через среднее и CV, равномерное и треугольное. Вырожденные распределения дают константу.

Проверить численные преобразования в целевых браузерах на небольшом эталонном наборе сразу, до подготовки уроков. При различиях устранить их в одном модуле преобразований. Не писать заранее собственную математическую библиотеку, если выбранное простое решение проходит требование воспроизводимости.

Далее добавить обслуживание по активным часам или числу завершённых повторений, по первому достигнутому порогу. Требование отмечается сразу, но партия завершается и выгружается до обслуживания. После его завершения сбрасываются оба счётчика. Активная обработка при подмене в обед тоже учитывается.

Затем добавить скрытый дефект каждой выходной штуки и наследование дефекта в производственном преобразовании. Разные изделия одного выпуска используют разные sampleIndex. Дефект не меняет распределение материала по приоритетам и не раскрывается на схеме до контроля.

Последним подключить контроль как фильтрацию проверенного объёма: годные доли передаются, дефектные списываются со стоимостью и долей ранее потраченного времени. Различать распространение дефекта в производстве и фильтрацию на контроле. Бесплатная проверка пригодности на конечном выходе не создаёт продажу брака.

### Проверка и условие перехода

Проверить p = 0, p = 1, несколько исходов в одной партии, смешанный дробный контроль, обслуживание в середине партии, перенос обслуживания через обед и ночь. Сравнить одинаковые seed при разных скоростях и способах продвижения времени.

Моменты распределений проверять на серии, а не требовать точного среднего от нескольких операций. Не усекать длинную длительность скрытым пределом. Новые состояния добавить в существующую схему и подписи причин, не раскрывая скрытые дефекты.

Результат прогона содержит все показатели концепта с понятными единицами, границами и интервалами. Материальный и стоимостный балансы проверяются независимо от отображения.

### Порядок реализации

Использовать уже собранные проводки материала и интегралы состояний. Достроить средний WIP, физический выход по продуктам, lead time и количество незавершённых изделий. При начальном WIP сохранять неизвестный полный возраст у потомков.

Добавить простой табличный просмотр отчёта. Графики пока могут быть минимальными: важнее подтвердить значения, которые затем будут визуализироваться. DBR нельзя оценивать до корректного WIP, выхода и измерения голодания.

## 11. Этап 8. DBR без отдельного диспетчера постов

### Результат

DBR поддерживает согласованный продуктовый цикл одного drum, рассчитывает запуск сырья, соблюдает лимит открытых слотов и показывает покрытие. Работа подтверждена на четырёх топологиях до создания полного интерфейса настройки политики.

### Порядок реализации

Сначала реализовать проверку применимости: один выбранный drum, явные маршруты, согласованный продуктовый состав, p = 0 во всём управляемом потоке, отсутствие независимых продуктов и дефектного начального запаса. Альтернативный производитель выбирается явно. Недопустимый DBR возвращает причину, а не превращается в push.

Затем построить номинальные слоты по циклу drum, средним временам, календарю, переналадкам и плановому обслуживанию. Расписание не использует будущие случайные длительности и не переписывает задним числом плановые времена ради скрытия опоздания.

После этого разложить потребность конечного продуктового цикла по выбранным маршрутам. Сначала суммировать потребность общего компонента, затем округлять до выпуска и обработочной партии. Учитывать начальные запасы по местам и остатки планового выпуска один раз. Включить боковую ветвь сборки после drum. Хранить реестр работ как расчётные данные потребности, без отдельной очереди команд каждому посту.

Рассчитать опережения L и B отдельно. L отвечает за номинальное изготовление, B за целевую готовую защиту. Полученные разрешения сырья ограничиваются началом прогона, периодическими попытками источников и физической ёмкостью. Проверка минимального связанного комплекта и группы слотов должна выявлять невозможный лимит, а не создавать взаимную блокировку из самой политики.

Далее подключить состояние rope к существующему источнику и ограничение старта выбранного drum. Слот допускается по сроку и лимиту, даже если начальный запас исключил новую закупку. Обработка требует допущенного слота, наступления его времени, полного комплекта и готового ресурса. Переналадка и обслуживание могут занимать предусмотренные промежутки до времени обработки.

Вне drum посты продолжают свои циклические планы. Не добавлять им разрешения на каждую операцию, скрытую перепланировку и резервирование материала под будущую заявку. После исчерпания заявок возможна доработка остатков; источник не создаёт новый материал сверх плана. Это поведение проверяется отдельно.

Последним реализовать фактическое покрытие последовательности будущих слотов готовыми входами drum, зоны и опоздание. Текущая обработка, переналадка и незавершённые компоненты не засчитываются как готовая защита. При B = 0 цветовые зоны не рассчитываются.

### Проверка и условие перехода

Последовательно проверить линейную линию, сборку до drum, сборку после drum с боковым компонентом и общий материал двух ветвей конечного изделия. Дополнительно проверить перенос drum на пост с двумя рецептами, начальный готовый комплект, общую upstream-партию для нескольких слотов, невозможный лимит, задержанную сырьевую заявку и доработку излишков.

Сравнить push и DBR с теми же мощностями, source-интервалами, физическими буферами, seed и горизонтом. Малый B должен показывать риск голодания, а не молча увеличивать запас. DBR не обязан выигрывать при любой настройке.

Переходить к полному интерфейсу политики после подтверждения материального баланса, единственности заявок и работы всех четырёх топологий. Если заданный план несовместим, показывать конкретную ошибку. Не добавлять оптимизатор ради автоматического исправления конфигурации.

## 12. Этап 9. Полная визуализация, графики и A/B

### Результат

Все состояния полной модели наглядны, а студент может сравнить две конфигурации без скрытой смены условий. Схема остаётся основной учебной поверхностью.

### Порядок реализации

Сначала достроить компоновку SVG по слоям DAG. Раздельно показать входы разных материалов, запас на посту, выходной буфер, сборку и разветвление. Выбор поста подсвечивает его связи, но обычный поток понятен и без последовательного выбора каждого блока.

Затем завершить визуальный язык по разделам 5.6 и 5.7 концепта. Материал имеет постоянные цвет и обозначение, состояние относится к посту. Растущая очередь имеет количество и изменение за подписанный интервал. Заполненный буфер, удерживаемый результат и голодание различаются. Большой защитный запас не помечается автоматически как ошибка.

На обычной скорости показать фактические передачи фишками. На высокой скорости объединять их по маршруту и интервалу, сохраняя количество и направление. Не проигрывать устаревшие события. На паузе схема неподвижна и показывает законченный снимок, а шаг объясняет последний переход. Нулевой выходной буфер изображается как прямая передача, без шкалы 0/0.

После этого достроить графики и таблицы: выход по сменам и накопленный, WIP по материалам, lead time, состояния постов, денежные показатели и DBR. Использовать показатели этапа 7, не вычислять альтернативные формулы внутри компонентов. В легендах явно указать временную шкалу, единицы и интервал.

Добавить режим поиска ограничения с проверкой и объяснением. Он скрывает готовую рекомендацию и обводку, но оставляет наблюдаемые очереди и реальные причины состояний.

Затем реализовать A/B на двух независимых экземплярах движка. Копия сохраняет stationId и recipeId для сопоставимых случайных ключей; runId различает экземпляры UI, но не добавляется в ключ RNG. Оба движка при синхронном просмотре продвигаются к одинаковому модельному времени, не к номеру события.

Сравнение показывает все влияющие на расчёт отличия. При изменении скорости обработки наследуемый буфер на долю смены может пересчитаться. Предусмотреть фиксацию ёмкостей в количествах для эксперимента одного фактора. Разные горизонты сравниваются на общем интервале или помечаются как несопоставимые итоги.

### Проверка и условие перехода

На конфигурациях уроков 2, 8 и 9 по основной схеме должны читаться маршрут, очередь, занятый ресурс и ресурс без работы. Повторить на обычной скорости, ускоренно, на паузе и шагом. Проверить, что скрытый брак не раскрывается визуализацией.

Для A/B подтвердить отсутствие общего изменяемого состояния, одинаковый результат совпадающих конфигураций и наличие в списке различий производных изменений буферов. Убедиться, что графики не скрывают незавершёнку средним только завершённых изделий. Повторить автономную сборку с полной схемой и графиками.

## 13. Этап 10. Конструктор и жизненный цикл конфигурации

### Результат

Пользователь собирает допустимую сеть и настраивает эксперимент без изменения исходников. После старта настройки расчёта заблокированы, новый эксперимент создаётся отдельной копией.

### Порядок реализации

Сначала добавить библиотеку материалов и рецептов, затем формы поста и циклического плана, затем маршруты и источники. «Добавить сборку» использует существующий пост с несколькими входами. «Добавить контроль» настраивает существующий тип операции и явный маршрут. Свободное рисование цеха не требуется.

Подключить проверку из этапа 2, дополненную правилами этапов 5–8. Ошибка указывает объект и поле. Приоритеты и несбалансированные мощности допустимы для эксперимента; отсутствующий активный маршрут и недостаточная ёмкость для комплекта запрещают запуск. Неиспользуемая запись справочника сама по себе не ломает проект.

Затем завершить глобальные настройки буферов, наследование и два режима применения. Предпросмотр показывает новые количества и затрагиваемые посты. Изменение глобального значения не стирает переопределения без явного выбора пользователя.

Добавить настройки календаря, горизонта, seed, затрат и политики. После запуска показывать использованный RunConfig, но не редактировать его. Повтор использует прежние вычисленные значения; изменённая копия восстанавливает редакторские правила. Изменения в копии не затрагивают готовый результат A.

Предусмотреть проверяемое удаление зависимостей, отмену и возврат правок только в редакторе. При удалении используемого рецепта показать затронутые планы и связи. Не создавать глобальную историю событий приложения ради обычной отмены формы.

### Проверка и условие перехода

Полностью через UI создать цепочку, сборку и развилку. Настроить два рецепта одного поста, входные и выходные ёмкости, обслуживание и seed. Проверить ошибки на изменении партии и рецепта, затем успешно запустить исправленную конфигурацию.

Проверить блокировку параметров и на работающем, и на приостановленном прогоне. Скорость просмотра, язык и выбор поста остаются доступны. Новая копия редактируется независимо от прежнего прогона. Данные пока могут жить в памяти; поведение редактора не зависит от успешного сохранения.

## 14. Этап 11. Хранение, перенос и шаринг

### Результат

Конфигурации можно сохранять, переносить между локальным HTML и хостингом, импортировать из JSON и открывать по URL-коду. Приложение остаётся работоспособным при недоступном storage.

### Порядок реализации

Сначала реализовать экспорт и импорт JSON поверх тех же нормализатора и валидатора. Экспортировать редакторскую конфигурацию и данные повторения из концепта, не временные ряды. Импорт создаёт новую запись библиотеки, а не заменяет чужую по совпадению ID. До принятия показать название, версию и ошибки.

Затем добавить адаптер сохранения с памятью вкладки и необязательным localStorage. Проверять получение storage и пробную запись. Если сохранение недоступно или квота исчерпана, оставить конфигурацию в памяти и доступным JSON-экспорт. Очищать можно только выбранные данные собственного пространства имён.

Сразу использовать schemaVersion для всех сохраняемых структур. Предусмотреть последовательные чистые миграции и отказ от неизвестной будущей версии. Конкретную миграцию добавлять при реальном изменении схемы, а не выпускать искусственные пользовательские версии ради демонстрации механизма. Исходник не уничтожается при неудачном преобразовании.

Добавить revision и обнаружение доступных конфликтов между вкладками с сохранением копии. Не строить синхронизацию устройств и распределённые блокировки. История прогонов и возобновление с середины не входят в MVP.

Последним добавить сжатый hash, ограничения размера и проверку после распаковки. Использовать встроенную в HTML библиотеку, если она действительно упрощает этот формат. Hash занят конфигурацией и не конкурирует с роутером интерфейса. Для `file://` предложить копирование кода и его вставку, для хостинга полный адрес. Если Clipboard API недоступен, остаётся обычное выделение текста.

### Проверка и условие перехода

Проверить цикл JSON → импорт → нормализация → тот же результат прогона; затем тот же цикл для сжатого кода. Стабильные ID вычислительных объектов должны сохраниться. Испорченный, чрезмерный и несовместимый ввод не повреждает открытую конфигурацию.

Проверить запрет storage, нулевую квоту, переполнение, ошибку миграции и неизвестную версию. Проверить открытие перенесённого HTML по другому локальному пути: отсутствие старой области storage не ломает работу. Проверить отсутствие сетевых запросов при импорте и загрузке встроенных данных.

## 15. Этап 12. Уроки и самостоятельное обучение

### Результат

Все десять уроков доступны на RU/EN, используют реальные возможности движка и объясняют результаты. Прогресс сохраняется по версии урока, а собственный эксперимент не подменяет исходное упражнение.

### Порядок реализации

Сначала превратить исходники раздела 6 концепта в полные конфигурации, без скрытых умолчаний. Использовать уже имеющиеся технические примеры как основу, но проверить все параметры каждого конкретного урока. Встроенный оригинал должен восстанавливаться независимо от пользовательской копии.

Для вариативных сравнений выполнить фиксированную серию seeds 0…29. Сохранить медианный знак, диапазон результатов, горизонт и демонстрационный seed. Если эффект не соответствует объяснению, корректировать урок и его версию, а не подменять результат расчёта. Если существенен пустой старт, показать это в разборе.

После калибровки написать окончательные объяснения, вопросы-прогнозы и разборы. Не придумывать процент выигрыша до измерения. Для каждого действия указать, что нужно увидеть на схеме и что проверить в метриках.

Порядок подключения уроков соответствует их учебной зависимости: сначала вариативность, ограничение и защита; затем локальная загрузка, обед и партии; затем качество, сборка, разделение; последним DBR и миграция. Все они входят в целевую поставку, а не скрываются как будущие уровни.

Подключить каталог, переходы, восстановление оригинала и отметку изменённого эксперимента. Прогресс хранит выполненные действия и просмотренный разбор. Не оценивать прохождение по случайному знаку результата и не блокировать доступ к урокам игровой валютой.

Завершить перевод всех экранов, сообщений валидации, определений и уроков. Пользовательские имена не переводятся автоматически. Переключение языка не пересоздаёт движок, не сбрасывает seed и не меняет числовые данные.

### Проверка и условие перехода

Пройти каждый урок от открытия до разбора на двух языках. Обязательно пройти сборку разных материалов и использование одного материала несколькими постами. Проверить, что урок можно изменить до старта, выбрать другую длительность и перепрогнать, сохранив исходный пример.

Проверить восстановление прогресса без истории временных рядов. Конфигурация каждого урока должна проходить импорт/экспорт и URL-код, а результаты повторяться. Учебный текст должен объяснять фактическое поведение, включая неподходящие настройки и несовпавший стохастический исход.

## 16. Этап 13. Сквозная проверка и производительность

### Результат

Полный продукт проходит проверки концепта. Решения о дополнительной оптимизации принимаются по измерениям, а не по предположению, что «потом понадобится».

### Порядок проверки

Сначала выполнить все числовые проверки V01…V38, балансы, события одной отметки, воспроизводимость и четыре конфигурации DBR. Повторить одинаковые прогоны через разные способы продвижения времени, runner и A/B.

Затем проверить пользовательские пути: загрузить урок, изменить копию, запустить, ускорить, поставить на паузу, сделать шаг, продолжить, сравнить, экспортировать, импортировать. Проверить также остановку пользователем, вычислительный лимит и отсутствие производственного прогресса. Причина завершения и фактический интервал должны быть понятны.

После этого измерить целевую нагрузку: учебные сети 3–12 постов, пользовательская сеть до 30, два прогона и длительные горизонты. Записать устройство, браузер, число событий, объём сохранённого состояния и задержку управления. Учитывать, что короткие операции тяжелее длинных при одинаковом количестве дней.

Сначала ограничить видимые фишки, частоту обновлений, объём журнала и ряды графиков без изменения итогов. Настроить размер вычислительной порции. Если одна отметка слишком длинная, обеспечить внутреннее продолжение между атомарными переходами без публикации промежуточного снимка. Если этого недостаточно, рассматривать Worker с тем же протоколом и запасным режимом без него.

Не ускорять модель удалением WIP, пропуском случайных исходов или незаметным изменением партии. Не объединять записи с разными дефектами, стоимостью или происхождением, если это меняет результат.

Отдельно выполнить проверку наглядности, клавиатуры, уменьшенного движения, текстового представления схемы, табличных графиков, узкого экрана и A/B. На высокой скорости не допускается долг анимаций, а на паузе движение прекращается.

### Условие перехода

Проходят обязательные проверки концепта, а оставшиеся ограничения совпадают с явно описанными границами MVP. Измеренные задержки соответствуют целям 7.4 концепта на зафиксированном устройстве либо причина устраняется до поставки. Ошибка базового баланса не переводится в список «известных особенностей» ради выпуска.

## 17. Этап 14. Автономная поставка

### Результат

Получен один готовый `dist/index.html` с воспроизводимой сборкой. Этот файл открывается локально и размещается на статическом хостинге без отдельной серверной логики.

### Порядок завершения

Зафиксировать версии движка, RNG, схем данных, уроков и сборки. Проверить, что экспортируемые данные содержат необходимые версии, а пользователь видит версию приложения. Runtime не должен требовать Node.js, npm или инструментов разработки.

Выполнить проверку типов, тесты, production-сборку и проверку итогового артефакта. Просмотреть структуру HTML и фактические запросы браузера: отсутствие внешнего script, CSS, словаря и шрифта должно подтверждаться, а не предполагаться из настройки сборщика.

Открыть файл без сети в Chrome/Edge, Firefox и Safari, затем проверить тот же файл по HTTP в подкаталоге. Повторить ключевые пути: урок, редактор, запуск, схема, пауза, A/B, JSON, URL-код и работа без storage. Зафиксировать версии браузеров и результаты в документе проверки поставки в `doc/`.

Обновить README: открытие HTML, необязательность сохранения, перенос JSON, локальный код и размещение на статическом хостинге. Не требовать команды dev-сервера как способ использования готового продукта. Файлы исходников и документация остаются в репозитории; для работы достаточно HTML.

### Условие завершения

Артефакт и исходники соответствуют друг другу, проходят проверки, а все десять уроков включены. Нет скрытого обязательного сетевого ресурса. В документации честно перечислены ограничения DBR, хранения и финансовой модели.

По постоянному поручению пользователя от 2026-10-21 завершённая и проверенная задача после коммита сразу отправляется в origin/master; CI публикует проверенный HTML. Незавершённая работа не публикуется.

## 21. Изменения плана и границы упрощения

При обнаружении проблемы сначала воспроизвести её на наименьшей конфигурации, затем определить, находится ли причина в коде, неясном требовании или неподходящем уроке. Исправление кода сохраняет смысл концепта. Изменение предметного правила сначала отражается в концепте. Изменение учебного примера не маскируется как исправление закона модели.

Допустимо упростить оформление, количество отображаемых фишек, устройство компонентов и внутреннюю структуру кода. Нельзя под видом упрощения убрать сборку, развилку, обслуживание, один из режимов партий, RU/EN или автономный HTML. Также нельзя незаметно расширить DBR до неподдерживаемых сочетаний и затем получить зависающий прогон.

На поздних этапах не добавляются CONWIP, MTBF/MTTR, рыночный спрос, люди как конкурирующий ресурс, многосменность и история IndexedDB. Они остаются последующими итерациями по концепту. Worker и численные преобразования дорабатываются только при подтверждённой необходимости выполнить уже согласованное требование.

Первоначальная очередь ограничена этапами 1–4. После их реализации порядок и объём следующих задач пересматриваются по фактическим результатам; очередной список не создаётся механически из всех оставшихся разделов. План не содержит обещания сроков до проверки технических рисков.

## 22. Что считается завершением реализации

Пользователь получает один HTML и может открыть его без сети, выбрать язык, пройти любой из десяти уроков, изменить конфигурацию до запуска и наблюдать настоящий поток материалов. На схеме понятны очереди, работа, голодание и блокировка. Ускорение, пауза и шаг помогают исследовать причины.

Он может самостоятельно построить сборку и развилку, настроить партии, планы, буферы и потери, повторить прогон с тем же seed и сравнить две конфигурации. Метрики имеют проверенные формулы, а DBR явно ограничен областью, которую поддерживает первая версия.

Сохранение не является условием работы. Конфигурация переносится через JSON и код/URL, а отсутствие или переполнение storage не уничтожает текущий эксперимент. Исходники, версии и документ проверки позволяют воспроизвести сборку и подтвердить её ограничения.

План был подготовлен на документальном этапе. Наличие плана не разрешает автоматически начинать все этапы реализации. Работа выполняется по одной согласованной задаче с проверкой, коммитом и вопросом пользователю перед следующей.
