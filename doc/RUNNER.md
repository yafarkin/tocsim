# Runner и управление прогоном

Задача № 17 завершена 2026-10-20. Код в `src/runner/runner.ts`, проверки в `runner.test.ts`. Runner работает в основном потоке и управляет уже существующей Simulation. Параметры производства и случайность от реального времени не зависят.

## API и состояние просмотра

| Вызов | Действие |
|---|---|
| new Runner(runConfig, onUpdate?, host?) | Создаёт исходный прогон в состоянии ready |
| start() | Запускает ready-прогон; физические события выполняются в отложенной порции |
| pause() | Отменяет следующую порцию и замораживает достигнутое модельное состояние |
| resume() | Продолжает paused-прогон без учёта времени паузы |
| step() | Отменяет автоматическое продвижение, выполняет одну целую отметку и оставляет paused, либо finished у горизонта |
| setSpeed(number или 'max') | Меняет только скорость просмотра |
| stop() | Терминально останавливает Simulation на фактически достигнутом времени |
| repeat() | Создаёт новую Simulation с тем же RunConfig и сразу запускает, сохраняя выбранную скорость |
| getView() | Возвращает неизменяемые данные просмотра и последний согласованный снимок модели |
| getFailure() | Возвращает исходную ошибку |
| dispose() | Отменяет таймер и освобождает runner без уведомления удалённого UI |

Повторный start у уже запущенного или терминального прогона ничего не делает. Resume действует только после pause. Шаг доступен из ready, running и paused; в терминальных состояниях ничего не меняет. Готовый полный горизонт не подменяется пользовательской остановкой. После dispose команды отклоняются. Для нового прогона после остановки или ошибки используется repeat.

RunnerView после № 18 имеет схему 2 и содержит status, speed, model, error и агрегированные transfers. Подробности в FLOW_SCHEME_CHECK.md. Статусы: ready, running, paused, finished, stopped, error, disposed. Это отдельное состояние просмотра, не состояние поста и не RunConfig. В model остаются фактические производственные причины и прогресс. Поэтому на паузе просмотра работающий в модели пост может оставаться processing, но его время и прогресс не меняются.

RunConfig передаётся как уже проверенный неизменяемый объект и доступен через readonly runConfig. Ни скорость, ни пауза, ни повтор не меняют параметры рецептов, seed или расчётный хеш. GetView содержит только JSON-совместимые данные; функции, таймеры, часы и изменяемые ссылки движка в него не входят. OnUpdate вызывается после команд и завершённых порций, а не внутри атомарного шага.

## Реальное и модельное время

Числовая скорость является положительным конечным множителем модельных миллисекунд на реальную миллисекунду. Дробная часть цели сохраняется между порциями, в движок передаётся целая отметка. Скорость max задаёт целью горизонт и вычисляет его последовательными ограниченными порциями.

При смене числовой скорости уже прошедший реальный интервал учитывается по прежнему множителю. Переход из max в числовой режим начинает отсчёт от реально достигнутого времени, без долга максимального режима. Pause сбрасывает невыполненную цель к достигнутому времени. Resume ставит новую реальную опорную точку, поэтому время паузы и прежняя вычислительная задолженность не вызывают скачка.

Шаг не использует реальный интервал, а вызывает Simulation.step. Первый шаг обрабатывает всю стартовую отметку 0, включая источники, передачи и назначения. Скорость не меняет длительность обработки и не подменяет время движка.

## Порции и уступка управления

Default host использует performance.now и setTimeout(callback, 0). Таймер только запускает следующую порцию и уступает управление основному циклу приложения. Сам расчёт выполняется синхронными атомарными шагами Simulation. Worker, rAF-зависимость, библиотека диспетчеризации и новые зависимости не добавлялись.

Технические ограничения порции: до 64 полных отметок и проверка прошедшего бюджета 8 мс между ними. Хотя бы одна отметка выполняется за порцию. Движок получил только наблюдательный метод nextEventTime: он позволяет обрабатывать события не дальше целевой точки. Если до цели нет событий, вызывается advanceTo для начисления хвоста без событий. Фазы, результаты и engineVersion от этого не изменились.

Отдельная тяжёлая отметка не прерывается посередине и может превысить бюджет. Поэтому 8 мс являются порогом планирования между отметками, а не измеренной гарантией длительности порции или всей реакции UI. Цели 16/250 мс из концепта требуют последующих замеров в браузере на зафиксированном устройстве. При необходимости внутреннего продолжения отметки сохраняется правило непубликации промежуточного состояния.

В очереди runner находится не больше одного собственного таймера. Pause, stop, repeat и dispose отменяют его. Дополнительная проверка токена игнорирует уже попавший в очередь старый callback, в том числе после repeat. Перед уведомлением UI следующая порция уже зарегистрирована, поэтому pause прямо из onUpdate может отменить её. Изменение представления не требует вмешательства в очередь событий модели.

Для тестов RunnerHost задаёт now, request и cancel. Request обязан откладывать вызов, а не выполнять callback синхронно. Часы должны быть конечными, неотрицательными и монотонными. Такая подмена позволяет проверять часы и порции без ожидания реальных учебных дней.

## Завершение и ошибки

Finished соответствует точному горизонту Simulation. Stopped является пользовательским терминальным завершением с фактическим интервалом; paused оставляет возможность продолжения. Error останавливает автоматические порции и предоставляет причины RU/EN как данные. Исходная ошибка доступна отдельно. Ошибка внешних часов относится к runner и не переписывает последнее согласованное состояние модели; ошибка самого движка также отражается в model.line.termination.

Ошибки точной арифметики получают понятное описание диапазона/данных, остальные предметные ошибки сохраняют свои code и причины. Потребитель onUpdate является доверенным кодом UI и не входит в транзакцию модели. Dispose не уведомляет удалённого потребителя и не оставляет таймеров.

## Проверка и границы

Прошли 238 тестов в восьми файлах, из них 20 новых для runner, строгий TypeScript и production-сборка. Сравнены прямой движок, скорость 1, ускорение 120, max и полные пошаговые прогоны. Проверены дробное накопление реального времени, смена скорости, пауза на длительный интервал, шаг из ready/running, stop, repeat, сохранение RunConfig, отмена старых callback, dispose, предел порции и бюджет между отметками.

Отдельно проверены пауза из обработчика обновления, неизменяемость/JSON, невалидная скорость, немонотонные часы и ошибка диапазона движка без частичного выпуска. Default host также выполнен с настоящим отложенным таймером Node и дал тот же итог. Это проверка интеграции планировщика, а не браузерная визуальная приёмка.

EngineVersion остаётся 0.6.0, схема конфигурации 1, схема модели Snapshot 4, rngVersion none-1. Схема RunnerView 2 описывает временные данные просмотра; хранения/импорта не добавлено.

В № 18 страница подключена к runner и настоящей схеме. Полный набор управления и несколько примеров остаются в № 19. В № 18 обновлённая автономная сборка проверена по протоколу FLOW_SCHEME_CHECK.md. Runner публикует последний снимок порции и агрегат фактических передач всех её отметок. Это ограниченный пакет, не журнал. Пауза сохраняет пакет, resume очищает его без повторного проигрывания.
