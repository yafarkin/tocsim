# Концепт учебного симулятора TOC

Версия документа: 1.2. Дата: 2026-10-20. Статус: концепт после повторной проверки реализуемости и согласованности требований. Реализация приложения в рамках текущего этапа не создаётся. Результаты обеих проверок и оставшиеся риски приведены в [REVIEW.md](REVIEW.md).

Документ фиксирует согласованные требования и предлагаемые правила там, где пользователь оставил выбор разработчику. Такие правила являются проектными решениями MVP, а не утверждением о точном поведении реального завода. Раздел 10 перечисляет ограничения и вопросы, которые потребуется проверить при реализации.

## 1. Цель, аудитория и принципы дизайна

### 1.1. Назначение

Приложение помогает студенту самостоятельно изучить Теорию ограничений, наблюдая работу производственной системы и сравнивая результаты управленческих решений. Основой служат идеи книги Элияху Голдратта и Джеффа Кокса «Цель». Симулятор представляет собой учебную модель, а не средство расчёта реального предприятия.

Доступны песочница и объясняющие уроки. Интерфейс, инструкции уроков, сообщения проверки и глоссарий доступны на русском и английском языках. Перевод пользовательских названий материалов и постов не выполняется автоматически.

Готовый продукт представляет собой один самостоятельный HTML-файл. Его можно открыть непосредственно в браузере без установки Node.js, сервера и подключения к сети. Тот же файл можно разместить на GitHub Pages или другом статическом хостинге.

### 1.2. Учебные результаты

| Эффект | Что должен установить студент | Основное наблюдение |
|---|---|---|
| Зависимость и вариативность | Равные средние мощности не обеспечивают ровный поток | Появляются очереди, голодание и потеря выхода относительно детерминированной базы |
| Ограничение | Выход системы зависит от ограничивающего ресурса | Ускорение другого поста увеличивает запас, но не устойчивый выход |
| Потерянное время | Простой ограничения имеет системную цену | Потерянный выход и денежный throughput видны в сравнении |
| Защитный буфер | Запас перед ограничением уменьшает голодание | Ограничение реже ждёт материал, выход повышается до доступной мощности |
| Локальная эффективность | Занятость каждого поста не является целью системы | Push создаёт WIP без соответствующего роста продаж |
| Партии | Обработочная партия отличается от транспортной | Меньшая передача ускоряет поступление деталей дальше по цепочке |
| Качество | Позднее обнаружение брака расходует время ограничения | При раннем контроле меньше ограничивающего времени уходит на негодные изделия |
| DBR | Запуск можно подчинить расписанию ограничения | Сопоставимый выход достигается с меньшим WIP |
| Миграция | После расширения ресурса ограничение может переместиться | Рост выхода останавливается на следующем ограничивающем ресурсе |
| Рыночное ограничение | Мощность сама по себе не создаёт продажи | Предусмотрено для следующей итерации |

Не обещаем рост WIP при любых настройках сбалансированной линии. Он зависит от запуска, свободных мест и конечного горизонта. При конечных буферах запас ограничен, а избыток запуска превращается в блокировку. Потеря выхода от вариативности демонстрируется на подобранных конфигурациях и нескольких seeds, а не объявляется обязательной для любого прогона.

### 1.3. Принципы

1. У каждого состояния есть видимая причина. Надпись «нет 2 креплений» полезнее одной жёлтой рамки.
2. Сравниваются конфигурации при одинаковых исходных условиях. Изменения настроек после запуска запрещены, включая изменения на паузе.
3. Модель и её отображение разделены. Частота кадров, скорость анимации и открытая вкладка интерфейса не изменяют расчёт.
4. Простые настройки доступны сразу. Формулы, распределения и подробная диагностика открываются по запросу.
5. Учебные подсказки объясняют причины, а не предлагают повысить загрузку всех постов.
6. Деньги, физический выход и загрузка показываются раздельно. Выпуск детали ещё не означает продажу конечного изделия.

Не переусложнять модель и реализацию. Новая сущность или механизм нужны только для конкретного согласованного учебного эффекта либо для устранения воспроизводимой ошибки. Не вводить дополнительное планирование, ресурсы или настройки ради гипотетических будущих сценариев. Подробность документа должна устранять неоднозначность, а не расширять объём продукта.

### 1.4. Согласованные границы

В MVP сразу входят несколько материалов, рецепты, сборка и разветвление использования одного материала. План рецептов задаётся до запуска. Посты имеют входные и выходные буферы в собственных настройках, а конфигурация содержит глобальные настройки буферов.

Смены и обед моделируются без выходных. Вне рабочего времени обработка, переналадка и обслуживание приостанавливаются с сохранением остатка. Длительность зависит от урока и изменяется перед новым прогоном. Общего обязательного горизонта в 10 дней нет.

Не создаются 3D, реалистичная планировка, транспортные мощности, промышленные оптимизаторы, бэкенд, аккаунты и мультиплеер. Люди не являются ограниченным ресурсом. Стоимость их участия учитывается агрегированными затратами поста.

## 2. Глоссарий

| Термин | Сущность или правило модели |
|---|---|
| Материал / Material | Описание типа сырья, полуфабриката или конечного изделия |
| Пост / Station | Один ресурс, выполняющий один рецепт за раз |
| Рецепт / Recipe | Входные количества нескольких материалов и один выходной материал |
| Сборка / Assembly | Обычный пост с рецептом из нескольких входов; отдельный вычислительный класс не нужен |
| Источник / Source | Запускает сырьё с общего склада согласно политике |
| Входной буфер / Input buffer | Материал, выделенный конкретному посту, с отдельными лимитами по материалам |
| Выходной буфер / Output buffer | Готовый результат поста до распределения потребителям |
| Маршрут / Route | Разрешённая мгновенная передача конкретного материала между выходом и входом |
| Общий склад сырья | Доступный запас вне производственного WIP; при бесконечной доступности закупка происходит при запуске |
| Общий склад готовой продукции | Выход системы перед продажей; в MVP продажа годного изделия происходит немедленно |
| Ограничение / Constraint | Ресурс или правило, ограничивающее достижение цели; в уроках прежде всего выбранный пост |
| Узкое место / Bottleneck | Пост с наименьшей эффективной мощностью для заданного продуктового состава |
| Drum | План работы выбранного ограничения |
| Buffer в DBR | Защита расписания ограничения запасом готовых комплектов или временем опережения |
| Rope | Правило выпуска сырья, связанное с разрешёнными слотами drum |
| Push | Запуск по доступному месту и локальному плану без подчинения ограничению |
| Обработочная партия | Несколько повторений рецепта, организованных в одну производственную партию |
| Транспортная партия | Сколько готовых изделий передаётся из последовательной обработки за один выпуск |
| WIP | Материал внутри производственной границы, включая обработку и готовый заблокированный результат |
| Throughput, T | Денежный результат продаж за вычетом полностью переменных затрат; не количество деталей |
| Inventory/Investment, I | Деньги, связанные в запасах; для ROI также учитывается капитал постов |
| Operating expense, OE | Расходы периода на работу системы, не капитализируемые в WIP |
| Lead time | Время от запуска материала до выхода или продажи, с явно указанным способом измерения |
| Seed | Исходное значение детерминированного генератора случайных чисел |
| CV | Стандартное отклонение времени обработки, делённое на его среднее |

Пять шагов фокусирования в уроках означают найти ограничение, использовать его доступную мощность, подчинить остальные решения, расширить ограничение и повторить поиск. Высокая занятость сама по себе не доказывает, что пост является ограничением.

## 3. Спецификация симуляционной модели

### 3.1. Время и вычислительный подход

Используется дискретно-событийная симуляция. Движок переходит к следующему завершению операции, границе календаря, слоту запуска или иному событию. Он не пересчитывает всю модель на каждом кадре и не округляет каждую операцию до крупного такта. Такой подход подходит для длинных прогонов с обедами, партиями и переналадками.

Внутреннее время хранится целым числом миллисекунд от начала прогона. Пользователь вводит минуты, часы и рабочие дни. Случайные длительности округляются до миллисекунды с нижней границей 1 мс. Нулевая длительность разрешена только мгновенной передаче и нулевой переналадке; время обработки строго положительно.

«Шаг» обрабатывает все события одной ближайшей временной отметки и связанные с ними мгновенные передачи. Движок возвращает устойчивое состояние, в котором ни один доступный запуск не пропущен. Графики получают данные с заданным интервалом модельного времени, независимо от числа кадров.

### 3.2. Конфигурация и идентичность

Конфигурация содержит schemaVersion, собственный ID и название, материалы, рецепты, посты, маршруты, источники, конечные материалы, календарь, политику запуска, глобальные буферы, начальные запасы, затраты, seed и горизонт. Урок дополнительно содержит lessonId и lessonVersion.

Каждый объект имеет стабильный ID, который сохраняется при копировании конфигурации для A/B. Порядок отображения и перевод названий не меняют ID. Новый объект получает новый ID; удалённые ID автоматически не перенумеровываются.

При старте создаётся неизменяемый RunConfig с engineVersion, rngVersion, seed, хешем нормализованной конфигурации и разрешёнными глобальными настройками. Текущее состояние прогона хранится отдельно. Для точного повторения требуются не только seed, но и совместимые версии движка и генератора.

RunConfig сохраняет и исходные правила наследования, и вычисленные значения отдельными полями. «Повторить» использует вычисленные значения прежнего прогона, а «Изменить копию» восстанавливает редакторскую конфигурацию с её наследованием. Хеш расчётной конфигурации не зависит от названия, перевода и порядка отображения, но включает всё, что влияет на вычисление и стабильные ID. Анимация и выбранная вкладка в него не входят.

Минимальные группы данных и их обязательность:

| Группа | Обязательные данные | Значения по умолчанию или ограничения |
|---|---|---|
| Материал | ID, название, роль, цвет | Закупочная цена нужна для сырья, цена продажи для конечного изделия |
| Рецепт | ID, входы, выходной материал, количество выхода, тип | Не менее одного входа, один тип выхода |
| Пост | ID, название, план, приоритет, настройки буферов | Приоритет 0, буферы наследуются |
| Профиль обработки | Рецепт, режим партии, число повторений, распределение времени | Одна последовательная операция, детерминированное время при CV = 0 |
| План | Упорядоченные строки, число партий каждой строки | Циклический, без автоматического пропуска строки |
| Обслуживание | Признак включения, длительность, один или два порога | Выключено; при включении длительность и хотя бы один порог положительны |
| Источник | Материал, ссылка на общий складской остаток или виртуальную доступность, размер и интервал запуска | Размер 1, интервал 1 рабочая минута для базового шаблона |
| Маршрут | ID производителя/источника, получатель/рынок, материал | Нет маршрута, нет разрешённой передачи |
| Календарь | Начало и конец смены, начало и конец обеда | Одна смена, обед строго внутри неё |
| Прогон | Seed, длительность, политика | Урок задаёт длительность; новая песочница предлагает 1 день, не фиксируя его |

Начальные запасы можно задать на складе сырья и в буферах. Они должны помещаться в ёмкость, иметь явно заданную сырьевую стоимость и не быть скрытым бесплатным предзаполнением урока. Начальный WIP имеет отметку «существовал до прогона»; его полный lead time неизвестен, поэтому он исключается из среднего полного lead time завершённых изделий, но включается в временные интегралы с начала наблюдения. Инициализация незавершённой операции в середине обработки в MVP не требуется.

Неизвестное время первоначального запуска наследуется всеми потомками такого запаса. Для них можно показать время с начала наблюдения, но нельзя подставлять 0 как якобы известную дату запуска. В среднем полного lead time они учитываются отдельной группой «неизвестен возраст исходного WIP».

### 3.3. Материалы и количества

Материал задаёт ID, название, цвет, роль и, для сырья, закупочную стоимость одной условной единицы. Для конечного изделия задаётся цена продажи. Названия могут уточнять «краска» или «лист», но система единиц измерения не вводится. Пользователь отвечает за согласованность масштаба количества и цены.

Входы рецепта положительны и допускают дроби, выход является целым числом больше нуля. Допустимы `0.3 A → 1 B`, `10 A → 1 B`, `1 A → 10 B`, `10 A → 10 B`. Рецепт имеет один тип выхода. Получение дверей или боковин из листа задаётся разными рецептами одного поста.

Предлагаемая точность MVP составляет до шести десятичных знаков количества. Значения разбираются из десятичной записи в целые микроединицы, без двоичного накопления ошибки. Импорт с большей точностью отклоняется с понятным сообщением. Промежуточные умножения проверяются на безопасный целочисленный диапазон. Рецепт с выходом 0, дробным выходом или отсутствующим материалом не запускается.

Каждый производственный выпуск содержит целое число новых изделий. Дробный расход разрешён для любого входа, в том числе `0.3 A → 1 B`, даже если A выпущен другим постом. Потребление 0.3 из одной A оставляет 0.7 A во входном запасе. Это учебное допущение о делимости входа без моделирования резки. Остаток сохраняет стоимость, возраст и скрытый дефект исходной A. Если дефектная A расходуется по частям, каждый использовавший её результат наследует дефект.

Передача количества между буферами также допускает дроби с точностью 10⁻⁶, хотя новый производственный выпуск всегда целый. Делимость является общим учебным допущением количественной модели, отдельная операция резки не нужна. Иначе после расхода 0.6 из буфера ёмкостью 1 осталось бы 0.4, а запрет передать часть следующей единицы создал бы искусственный вечный голод. Система единиц измерения и отдельный справочник единиц не нужны. Фишки соответствуют целым изделиям, дробные остатки отображаются шкалой и числом. При целых рецептах и целых ёмкостях потоки остаются целочисленными.

### 3.4. Рецепты и производственный план

Рецепт содержит входы `a[m]`, выход `q` одного материала, тип операции «производство» или «контроль». Время и размер партии задаются в профиле выполнения рецепта конкретным постом. Это позволяет двум постам выполнять один рецепт с разной скоростью.

Пост содержит упорядоченный циклический план. Строка плана задаёт рецепт, число обработочных партий подряд и профиль выполнения. Например, две партии дверей, затем одна партия боковин. При окончании последней строки цикл повторяется. Недоступный очередной рецепт не пропускается автоматически: пост ждёт его комплект. Подсказка объясняет, что простой вызван планом.

Одна обработочная партия содержит целое `k ≥ 1` повторений рецепта. Ей нужны `k × a[m]` каждого входа, а её выход составляет `k × q`. Плановая строка считается выполненной после завершения обработки партии, включая удерживаемый на посту результат. Новая партия всё равно не стартует до освобождения поста.

Для первого рецепта начальная наладка бесплатна, если в конфигурации не указан другой начальный рецепт. При переходе на другой recipeId применяется общая длительность переналадки поста. Переход к тому же рецепту новой переналадки не вызывает. Матрица переналадок между парами рецептов отложена.

### 3.5. Два режима обработки партий

| Правило | Последовательная партия | Одновременная партия |
|---|---|---|
| Пример | Механическая обработка деталей | Печь, сушильная камера |
| Накопление входов | Полный комплект на всю партию | Полный комплект на всю партию |
| Резервирование | Все входы изымаются из буфера при старте партии | Все входы изымаются из буфера при старте партии |
| Время | Отдельная случайная длительность каждого повторения | Одна случайная длительность всего цикла |
| Появление результата | После отдельных повторений | Весь результат в конце цикла |
| Транспортная партия | От 1 до полного выхода партии | Выход доступен после цикла, затем передаётся по свободным местам |

В последовательном режиме профиль задаёт время одного повторения рецепта, а не одной выходной штуки. При `1 лист → 3 двери` одно завершение даёт три двери. Транспортный порог считается в выходных штуках. При достижении порога весь доступный выпуск разрешается передавать с учётом свободных мест и правил делимости раздела 3.3. Последний остаток партии выпускается независимо от порога. Порог определяет момент разрешения передачи, а не требование иметь всё указанное количество свободных мест одновременно.

Готовые изделия до достижения транспортного порога остаются на посту и входят в WIP. При невозможности выгрузки достигшего порога результата пост прекращает следующие повторения до освобождения результата. Необработанные, но уже зарезервированные входы остаются на посту. Размер транспортной партии не создаёт дополнительной транспортной задержки.

### 3.6. Настройки входных и выходных буферов

Буферы являются частью настроек поста, а не свободно размещаемыми узлами конструктора. На схеме они всё равно видны рядом с постом. Глобальные настройки служат значениями по умолчанию, которые пост может наследовать или переопределять.

| Настройка | Глобальное значение по умолчанию | Переопределение поста |
|---|---|---|
| Входная ёмкость | Запас на 0.5 рабочей смены | Наследовать, свой коэффициент смены, количество по материалам, бесконечно |
| Выходная ёмкость | 0 | Наследовать, своё количество по материалам, бесконечно |
| Распределение | Приоритет поста, затем стабильный ID | Числовой приоритет поста |

В MVP не вводится общий лимит «всех материалов одной суммой»: условная единица краски несопоставима с дверью. Каждому разрешённому входному и выходному материалу соответствует своя ёмкость. Значение «бесконечно» является отдельным типом настройки, а не числом Infinity в JSON.

Кнопка «Применить ко всем постам» перед запуском имеет два явных варианта: «Обновить наследуемые» и «Сбросить переопределения и применить всем». Пользователь видит перечень изменяемых постов и итоговые количества до применения. Обычная правка глобального значения сохраняет индивидуальные переопределения. Во время прогона обе операции недоступны.

Расчёт входа на долю смены выполняется до запуска. Пусть плановый цикл поста потребляет `A[m]` материала и занимает `C` минут, включая среднюю обработку и циклические переналадки. Если в рабочей смене `S` минут без обеда, предварительная ёмкость `h × S × A[m] / C`, где `h = 0.5` по умолчанию. Обслуживание и брак в этот простой норматив не включаются, что подписывается рядом с расчётом.

Для сырья ёмкость округляется вверх до микроединицы, для получаемых от других постов материалов до целой штуки. Ёмкость повышается как минимум до максимального полного входного комплекта одной партии, использующей этот материал, с тем же округлением. При редком рецепте такой минимум может превышать расчёт на половину смены; интерфейс сообщает причину. Это повышение выполняется для расчётной настройки «доля смены». Явно введённая недостаточная ёмкость не исправляется молча, а блокирует запуск с объяснением. Ёмкости пересчитываются при изменении плана до запуска и фиксируются в RunConfig. Для начального частично настроенного поста без валидного плана расчёт недоступен.

Пример: план расходует 80 дверей за 480 рабочих минут. Настройка 0.5 смены даёт 40 дверей. Если одна обработочная партия требует 50, ёмкость повышается до 50. Для сборки «1 корпус + 4 крепления» при 40 сборках за смену получаем 20 корпусов и 80 креплений.

Выходная ёмкость хранит результат уже законченной обработки. При нулевой ёмкости передача идёт сразу во входные буферы получателей, а непереданный остаток удерживает пост. При положительной ёмкости результат сначала помещается в неё; пост освобождается после выгрузки всего выпуска. Затем выходной запас распределяется дальше.

Разрешается частичная выгрузка количества. Например, выпуск 10 дверей, свободно 6 мест, 6 выгружаются, 4 остаются на посту и блокируют его. Это позволяет использовать буфер меньше одновременной партии без искусственного запрета работы. Для дробных количеств действуют правила делимости раздела 3.3; новый производственный выпуск партии всё равно целый. При нулевой выходной ёмкости самого буфера нет, а готовый удерживаемый результат относится к посту. Процент заполнения 0/0 не вычисляется: показываются «прямая передача» и количество удерживаемого результата.

Для линейных уроков выходная ёмкость по умолчанию нулевая. Выходной буфер A и входной буфер B на одном маршруте дают суммарный промежуточный запас. Интерфейс показывает обе ёмкости и их сумму по материалу, чтобы увеличение одного буфера не выглядело бесплатным улучшением.

### 3.7. Маршруты, склады и распределение

Маршрут задаёт производителя, получателя и materialId. Доставка мгновенна, пропускная способность транспорта не ограничена. Анимация движения не меняет модельное время.

Сырьё доступно на общем складе, конечная продукция поступает на общий выход. Полуфабрикаты находятся в буферах и на постах. Отдельный общий промежуточный склад не вводится: его роль при необходимости играет выходной буфер производителя.

После события освобождения материала или места движок последовательно распределяет доступный запас. Получатели сортируются по убыванию приоритета, затем по ID. Внутри материала используется FIFO по времени доступности и ID партии. Получатель получает не больше свободной входной ёмкости. Выделенный материал не отбирается обратно другим постом.

При конкуренции нескольких производителей их выпуски обрабатываются по времени готовности и ID. Готовый результат на посту рассматривается после уже находящегося в его выходном буфере более старого запаса. Скрытые признаки брака при распределении не учитываются.

Склад сырья имеет единственный остаток по materialId. Два источника одного материала обращаются к этому общему остатку, не создают две копии запаса и разрешают одновременную конкуренцию по приоритету получателя, затем sourceId. Источник использует общий календарь смены и обеда; подмена на отдельном посту сама по себе не запускает дополнительное сырьё в обед. Внутренние мгновенные передачи готовы выполняться и на календарной границе; запрет касается новых обработок и запусков сырья.

Продажа выполняется только по явному маршруту в рынок. Для одной пары «пост, выходной материал» в MVP разрешены либо маршруты к потребляющим постам, либо маршрут в рынок. Одновременная конкуренция рынка и внутренних потребителей за тот же выпуск не вводится. Несколько разных конечных продуктов разрешены. Само совпадение materialId с продаваемым материалом не продаёт деталь посреди цепочки контроля.

Пост может накапливать компоненты будущих рецептов своего цикла в пределах входных лимитов, даже если следующий рецепт ждёт другой материал. Автоматического резервирования полного комплекта перед пополнением входного буфера нет. Поэтому чрезмерные приоритеты и запасы могут вредить другим ветвям. Такой эффект является предметом урока о разделении потока.

Если материал должен иметь двух альтернативных производителей, это разрешено для push. Для простого расчёта норматива выбирается среднее потребление поста, а не способность производителей. Для DBR требуется явно выбрать плановый маршрут каждого заказа, как описано в разделе 4.

### 3.8. Жизненный цикл поста и состояния

Пост одновременно выполняет одну операцию. Перед запуском очередной партии проверяются календарь, отсутствие удерживаемого результата, необходимость обслуживания, рецепт плана, наличие полного комплекта и переналадка.

Порядок принятия работы: завершить выгрузку предыдущего результата; выполнить назначенное обслуживание; убедиться в наличии комплекта для следующей партии; выполнить нужную переналадку; атомарно изъять комплект и начать обработку. Пока выполняется переналадка, входной запас остаётся на месте и принадлежит этому посту. После переналадки комплект проверяется повторно. Другой пост не может его забрать.

| Состояние | Причина и отображение |
|---|---|
| Работает / Processing | Зелёный цвет, прогресс повторения или общего цикла |
| Голодает / Starved | Жёлтый цвет, точный список недостающих входов очередной партии |
| Заблокирован / Blocked | Оранжевый цвет, удерживаемый результат и заполненный получатель |
| Переналадка / Setup | Фиолетовый цвет, старый и новый рецепт, остаток времени |
| Обслуживание / Maintenance | Синий цвет, причина порога и остаток |
| Обед / Lunch | Серый цвет, время возобновления и приостановленная операция |
| Вне смены / Off shift | Серый штрихованный фон |
| Ожидает drum / Waiting for drum | Голубой цвет, ближайший разрешённый слот |
| Нет плана / Invalid configuration | Ошибка настройки, запуск всей конфигурации запрещён |

«Сломан» не используется в MVP, поскольку случайные поломки отложены. Цвет всегда дополняется подписью и значком. Приоритет отображаемого состояния: календарная остановка, обслуживание, переналадка, блокировка, работа, ожидание drum, голодание. В данных сохраняется и приостановленная операция, и причина календарной остановки.

### 3.9. Календарь, обед и горизонт

По умолчанию рабочий день длится с 08:00 до 17:00, обед с 12:00 до 13:00. Чистое доступное время равно 480 минутам. Дни повторяются без выходных, реальных дат и часовых поясов. До запуска можно изменить расписание. Поддерживается одна смена и один общий обед в сутки.

Вне смены и в обед обработка, переналадка и обслуживание останавливаются с сохранением оставшейся длительности. Вариативная длительность выбирается один раз при начале операции и после паузы не генерируется заново. Перенос операции через несколько суток разрешён.

Пример: операция на 20 минут началась в 11:50, остановилась в 12:00 и завершилась в 13:10. Операция на 20 минут, начатая в 16:50, завершается в 08:10 следующего дня.

Для урока защиты времени ограничения есть настройка поста «Работать в общий обед». Она означает наличие подмены и добавляет указанную стоимость за фактическое обеденное время занятости. Ночное производство и завершение партии за пределами смены в MVP не предусмотрены. Основное согласованное правило остаётся приостановкой.

Горизонт задаётся числом рабочих дней конкретного урока или пользователя. Прогон начинается в начале первого рабочего дня и заканчивается в конце смены последнего. События завершения ровно на границе включаются, новые операции на границе не запускаются. Автоматической доработки незавершёнки после горизонта нет. Сводка явно показывает оставшийся WIP.

### 3.10. Плановое обслуживание

В конфигурации поста обслуживание можно отключить или включить. Параметры: длительность, порог активных часов обработки, порог количества повторений рецептов. При включении хотя бы один порог положителен. Первое достижение любого порога помечает обслуживание как требуемое.

В часы не входят голодание, блокировка, переналадка, обслуживание и календарная приостановка. Активная обработка во время обеда при включённой подмене учитывается наравне с обычной обработкой. В количество входят фактически завершённые повторения рецепта, включая выпущенный скрытый брак. Одновременный цикл из k повторений увеличивает количественный счётчик на k в конце цикла.

Текущая обработочная партия завершается полностью. После выгрузки её результата пост обслуживается до запуска следующей партии, даже если порог был превышен внутри партии. Такая отсрочка показывается в журнале. Обслуживание не создаёт брак и не меняет рецепт наладки. Оба счётчика обнуляются после полного окончания обслуживания.

### 3.11. Вариативность и случайные числа

Профиль обработки содержит среднее время μ > 0 и CV ≥ 0. Простой режим при CV = 0 детерминирован. При CV > 0 предлагается логнормальное распределение положительных длительностей с `σ²_ln = ln(1 + CV²)` и `μ_ln = ln(μ) − σ²_ln / 2`. Интерфейс показывает, что μ является средним, а не медианой.

Расширенный режим предлагает равномерное распределение с min > 0 и max ≥ min либо треугольное с min > 0, min ≤ mode ≤ max. Среднее и CV в нём вычисляются из параметров и доступны для чтения. Независимо задавать несовместимые μ, CV и границы нельзя. Установлены допустимые пределы CV и длительности; предварительный предел MVP CV ≤ 2 проверяется на учебных сценариях.

Глобальный seed обязателен и редактируется до запуска; формат MVP является беззнаковым целым 32-битным числом, включая 0. `Math.random()` в движке запрещён. Алгоритм генератора, преобразование в нормальное распределение и округление версионируются. Предлагается счётчиковое получение случайных значений по ключу `(seed, stationId, recipeId, operationOrdinal, purpose, sampleIndex)`. purpose разделяет обработку, брак и другие случайные механизмы. sampleIndex различает выходные изделия одной операции и несколько базовых случайных значений одного преобразования. Иначе партия ошибочно получила бы один общий исход брака. Счётчики назначаются при начале соответствующей операции, а не при создании событий UI. Потоки не зависят от обхода UI и взаимного порядка событий разных постов.

Межбраузерная воспроизводимость является требованием движка. Для случайных преобразований нужен версионированный численный алгоритм с одинаковыми эталонными результатами, а не неявное обещание идентичности встроенных трансцендентных функций всех JavaScript-движков. На раннем этапе проверяются наборы округлённых длительностей и порядок событий в целевых браузерах; при различиях используется единая реализация численных преобразований. Версия этого алгоритма включается в rngVersion.

Усечение случайного распределения по скрытому верхнему пределу запрещено: оно меняет заявленное среднее. Округление до миллисекунд и минимум 1 мс раскрываются в описании модели. Чрезмерный результат, превышающий безопасный диапазон времени, останавливает прогон с диагностикой, а не незаметно заменяется средним. Вырожденные равномерное min = max и треугольное min = mode = max обрабатываются как константа.

Изменение среднего или CV в A/B преобразует те же базовые случайные значения для совпадающих ключей. Добавление поста не сдвигает случайность существующих постов. Если меняются партии и число операций, соответствие ограничено: одинаковый seed не означает одинаковую судьбу каждой физической детали. Интерфейс поясняет такую границу сравнения.

Никаких отдельных случайных задержек движения фишек в движке нет. Неопределённость урока создаётся обработкой и браком. Зависимость времени от брака не моделируется.

### 3.12. Брак и контроль

Производственный профиль задаёт вероятность скрытого дефекта p от 0 до 1 для каждой выходной штуки. При p = 0 генерация дефектов не нужна. Дефект хранится в состоянии изделия и не показывается до контроля. Цвет фишки до контроля не выдаёт его наличие.

Дефект входного дискретного изделия делает все выходы соответствующего повторения дефектными. В одновременном режиме сохраняются комплекты повторений, поэтому один дефектный комплект не портит остальные автоматически. Для дробных расходных материалов собственный дефект в MVP не задаётся. Модель не пытается описывать смешивание загрязнённой краски.

Контроль задаётся отдельным постом с типом операции «контроль». Его номинальный профиль `1 A → 1 A` задаёт проверку одной единицы объёма; он не производит новый материал, не создаёт новый дефект и гарантированно выявляет существующий. При целом неделённом входе годная штука проходит, дефектная списывается. Если вход состоит из дробных долей разных исходных изделий, контроль сохраняет их индивидуальные признаки: годные доли проходят, дефектные списываются. Он не объявляет весь проверяемый объём дефектным из-за одной плохой доли. Например, 0.6 годной A и 0.4 дефектной A дают 0.6 пропущенной A и 0.4 списания. Это фильтрация существующего количества, а не рецепт с дробным производственным выходом. У обычных производственных рецептов выход по-прежнему целый и положительный.

Пост контроля имеет время, вариативность, партии, буферы, календарь и затраты как обычный пост. Одно повторение проверки завершено после проверки полного заданного объёма независимо от доли брака; временной порог обслуживания учитывает всю проверку. Стоимость и приписанные минуты проверяемого объёма распределяются между прошедшими и списанными долями. Поддержка разных имён проверенного и непроверенного материала отложена. Один materialId до и после контроля не требует исключения из проверки маршрутов: ацикличность определяется по постам, а не по совпадению названия материала.

Маршруты контроля задаются явно, а не выводятся только из совпадения материалов. Соединение «производитель → контроль → ограничение» нельзя обойти прямой передачей, если такого маршрута нет. На конечном выходе выполняется бесплатная проверка пригодности к продаже: скрытый дефект списывается без дохода. Это учебная модель отсутствия продажи негодного изделия, а не возвратов покупателей.

Для урока раннего контроля дефект возникает на посту до ограничения, а контроль переносится перед ним или после него. Если дефект создаёт само ограничение, ранний контроль его не предотвращает. Отчёт различает источник дефекта, место обнаружения и время ограничения, потраченное на позднее списанные изделия.

### 3.13. Порядок одновременных событий

Очередь сортируется по времени, фазе и стабильному ID. Для одной временной отметки применяется следующий порядок:

1. Начислить интегральные метрики за прошедший интервал по предыдущему состоянию.
2. Завершить операции с нулевым остатком, принять выпуски и достижения порогов обслуживания.
3. Применить границу календаря и горизонта. Завершение ровно в 12:00 засчитывается до обеда.
4. Принять разрешения источников и drum, если горизонт не закончился. Закрытый календарь переносит запуск к следующему открытому моменту.
5. Передать готовый материал, освободить посты и выполнить немедленные продажи или списания.
6. Назначить обслуживание, переналадку и допустимые обработки, затем повторить мгновенные передачи до устойчивого состояния.
7. Снять согласованный снимок состояния и метрик.

Одновременные старты конкурирующих получателей разрешаются общим правилом приоритетов. Нулевая транспортная задержка не должна создавать бесконечную цепь: любой производственный цикл имеет положительное время, а граф маршрутов является ациклическим по постам. Движок имеет защитный лимит мгновенных переходов и возвращает диагностическую ошибку при нарушении.

При паузе операции календарём плановое событие её завершения отменяется или помечается недействительным по версии операции. После возобновления назначается новое событие по остатку. Устаревшее событие не должно завершить операцию второй раз. Ацикличность проверяется по узлам постов, поэтому рецепт контроля `A → A` сам по себе не является циклом маршрутов; обратная связь из контроля к прежнему посту в MVP запрещена.

Если нет незавершённых операций и будущих поступлений или разрешений, способных изменить состояние, фиксируется отсутствие производственного прогресса. Показываются недостающие компоненты, заполненные буферы и заблокированные планы. Исчерпание конечного сырья или всех заданий отличается от взаимной блокировки. Если до горизонта остаются только календарные события без возможности выпуска, движок может сразу начислить оставшиеся фиксированные расходы и интегралы до заданного конца. Такая оптимизация не сокращает оплачиваемый период и не завышает прибыль. Будущее открытие календаря, слот drum или возможная поставка источника не должны ошибочно считаться тупиком.

Результат содержит отдельно статус завершения: полный горизонт, остановлен пользователем, вычислительный лимит или ошибка; и диагностику потока: нормальная работа, исчерпано сырьё/задания, отсутствует комплект, взаимная блокировка. При пользовательской остановке и техническом лимите метрики считаются только до фактически достигнутого времени, а результат помечается неполным. Достижение полного горизонта не означает выполнение всех запланированных изделий.

### 3.14. Метрики потока

Все показатели содержат интервал измерения и границу системы. Время рабочих смен и полное календарное время показываются отдельно.

| Показатель | Правило расчёта |
|---|---|
| Физический выход | Число годных конечных изделий по каждому типу; сумма разных типов только с подписью «штук, смешанный состав» |
| Выход за смену | Продажи годных изделий между началом и концом соответствующего рабочего дня |
| WIP | Количества по материалам во входах, выходах, обработке, ожидании передачи и на заблокированных постах |
| Средний WIP | Интеграл выбранного WIP по времени, делённый на длину того же интервала |
| Время в состоянии | Интеграл индикатора состояния поста |
| Загрузка обработкой | Активное время обработки / разрешённое рабочее время поста |
| Доля голодания/блокировки | Соответствующее время / то же разрешённое рабочее время |
| Занятость | Обработка + переналадка + обслуживание, делённые на доступное время; отдельно от полезной обработки |
| Lead time готового изделия | Время продажи минус самое раннее время запуска сырья в его происхождении |
| Производственный lead time | Дополнительно время продажи минус первый старт обработки предка |
| Заполнение буфера | Количество / конечная ёмкость; для бесконечного буфера процент не вычисляется |

Отдельная сводка показывает сырьё до запуска и готовую продукцию до продажи. Не суммируем физический WIP краски, дверей и креплений в одно число без оговорки. По умолчанию показываем состав по материалам и денежную оценку. В линейных уроках 1:1 разрешён единый счётчик деталей.

При сборке выход наследует самое раннее время запуска участвовавших компонентов; при разделении наследование копируется вместе с долей стоимости. Так определяется учебный lead time изделия. Показатель не объявляется универсальным временем пребывания одного неизменяемого объекта для закона Литтла.

Для исключения двойного счёта используется отдельный учёт входов и результатов. При старте партии входы переходят из буфера в запас на посту. В последовательной обработке входы очередного повторения считаются преобразованными только при его завершении; до этого они остаются WIP исходных материалов. В одновременном режиме все входы преобразуются при завершении общего цикла. На одном завершении входы списываются и выходы появляются атомарно. Частично готовый результат, удержанный транспортным порогом, учитывается как выходной материал на посту, а не одновременно как прежние входы.

Внутри полного комплекта партии FIFO определяет, какие входные доли принадлежат каждому повторению. Уже выпущенные изделия, зарезервированные входы будущих повторений и выходной буфер являются непересекающимися запасами. Схема показывает их раздельно при раскрытии поста. На незавершённом одновременном цикле числовой WIP может оставаться, например, «10 листов в обработке», а не «30 ещё не существующих дверей».

По умолчанию средний WIP и полный lead time используют календарное время между началом и фактической остановкой прогона, включая ночи. Дополнительный рабочий lead time интегрирует общий календарь смен без обеда. Если показан средний WIP только рабочего времени, λ и W для проверки закона Литтла вычисляются по той же шкале. У окна [0, T] нет лишней ночи после последней смены. При прерванном прогоне знаменатель ограничивается фактически пройденным интервалом; при T = 0 средние не вычисляются.

Для метрики потраченного ограничивающего времени вместе с долями стоимости передаётся вектор фактических минут обработки по stationId. При сборке векторы суммируются, при разделении распределяются между выходами, текущая операция добавляет свои минуты. При списании сохраняется соответствующая доля минут выбранного ограничения. Так 1→10 не приписывает всем десяти изделиям полное время одной операции десять раз. Подробное дерево всех предков не обязательно хранить: достаточно временных отметок, стоимости, дефекта и агрегированного вектора, если выбранный режим проверки не требует идентичности отдельных деталей.

### 3.15. Проверка закона Литтла

Для линии с сохранением единицы потока, без сборки, разветвления количества и брака, используем `L ≈ λ × W`. L является средним числом деталей внутри фиксированной границы, λ является выходом за единицу времени, W является средним временем пребывания тех же деталей.

Для стационарной оценки исключается заданный период разогрева. Короткий прогон с пустого старта и незавершёнными деталями на финише помечается как имеющий краевой эффект. Несовпадение в таком прогоне не считается автоматически ошибкой модели.

Точная конечная проверка использует тождество `∫N(t)dt = Σ длительностей пересечения жизни каждой детали с окном наблюдения`. В сумму входят начальные и незавершённые детали с обрезанными интервалами. Отдельно показывается поправка относительно `число завершённых × средний lead time завершённых`.

На сборочных сетях и рецептах 1:10 общая проверка «сумма всех штук = выход × возраст готового изделия» отключена. В интерфейсе доступна проверка для отдельного сохраняющего единицу участка либо стоимостный баланс. Концепт не подменяет несовместимые единицы.

### 3.16. Денежные метрики

Приложение использует условные денежные единицы. Материалу сырья задаётся закупочная цена, изделию цена продажи. Труд не добавляет стоимость запасу. Пост имеет фиксированные затраты за полную смену, ставку дополнительных обеденных затрат и стоимость капитала.

Фактическая сырьевая стоимость сохраняется в происхождении материала. При сборке стоимости входов суммируются, при выпуске q изделий стоимость распределяется между ними. Разделение выполняется с сохранением остатка, чтобы округление не создавало деньги. Производственный труд и простои относятся в OE.

Денежные поля допускают до шести десятичных знаков, внутренние суммы хранятся в целых микроденежных единицах с проверкой диапазона. Умножения цены на количество выполняются без потери разрядов, например через BigInt; наружу большие целые сериализуются десятичными строками по схеме. Закупочная проводка округляется один раз до микроденежной единицы. При последующем дроблении стоимость не вычисляется заново по цене: выделяемая доля округляется вниз, остаток сохраняется у оставшегося запаса, последняя доля получает весь остаток. Представление двумя знаками в UI не изменяет учёт.

| Показатель | Формула и соглашение MVP |
|---|---|
| Revenue | Сумма цен проданных годных конечных изделий |
| TVC sold | Сырьевая стоимость фактически вошедших в проданные изделия материалов |
| T | Revenue − TVC sold |
| Scrap expense | Стоимость материалов, списанных в брак, без повторного включения в TVC sold |
| OE | Фиксированные расходы периода + дополнительные обеденные расходы + Scrap expense |
| Чистый результат NP | T − OE; в интерфейсе подписано, что налоги, проценты и амортизация не моделируются |
| I stock | Сырьевая стоимость физически имеющихся запасов, включая WIP; бесконечный виртуальный резерв до закупки не оценивается |
| I total | I stock + заданный капитал постов |
| ROI периода | NP / среднее I total за тот же период; при нулевом знаменателе значение отсутствует |

Отнесение стоимости брака в OE является явным учебным соглашением для сохранения баланса, а не полноценной бухгалтерской системой. При изменении будущей финансовой модели необходимо менять её версию и подписи. Основные отношения `NP = T − OE` и роль вложений опираются на [материал Goldratt Research Labs по throughput accounting](https://goldrattresearchlabs.com/pdf/Theory_of_Constraints_Throughput_Accounting.PDF); конкретные правила списания и усреднения в этом симуляторе определены выше.

Фиксированные расходы начисляются пропорционально прошедшим рабочим минутам общей смены без обеда, даже когда пост голодает, заблокирован или обслуживается. Обеденная доплата начисляется за активную обработку, переналадку или обслуживание в обед при включённой подмене. Капитальная стоимость увеличивает I, а не списывается целиком в OE при запуске.

Закупка виртуально доступного сырья происходит при его запуске. Для конечного исходного склада задаются начальное количество и стоимость. Стоимостный контроль: начальные запасы + закупки = конечные запасы + TVC sold + Scrap expense. Отдельный виджет движения денег может показать Revenue − закупки − расходы без повторного списания Scrap expense. Он не называется чистой прибылью.

Проверочный денежный пример: сырьё для трёх изделий куплено по 10, два годных проданы по 30, третье списано; расходы работы 5. Получаем Revenue = 60, TVC sold = 20, T = 40, Scrap expense = 10, OE = 15, NP = 25. Конечный запас равен 0, баланс материала в деньгах даёт 30 = 20 + 10. Если третье изделие не списано, а осталось в WIP, I stock = 10, OE = 5 и NP = 35; закупка всё равно составила 30. Это объясняет разницу результата периода и движения денег.

### 3.17. Обнаружение ограничения

Для фиксированного продуктового состава оценивается нагрузка каждого поста на один плановый комплект выхода. Учитываются средняя обработка, частота переналадок, обслуживание и доступный календарь. Ветви сборки пересчитываются по коэффициентам рецептов. Наибольшее отношение требуемой нагрузки к доступному времени даёт кандидата на ограничение.

В прогоне дополнительно используются голодание, блокировка, очереди, фактический полезный выход и расписание. Из-за вариативности и конкуренции за материал наблюдаемая задержка может отличаться от планового кандидата. Интерфейс различает «выбранный drum», «плановое ограничение» и «наблюдаемые признаки». При неоднозначности показываются несколько кандидатов, а не выдуманная точность.

Режим «Найди узкое место» скрывает вычисленную рекомендацию, обводку ограничения и заранее раскрывающие ответ формулировки. Сами очереди, времена и состояния остаются доступны для исследования. Проверка объясняет ответ через нагрузку и причины простоя. Улучшение проверяется новым прогоном, а не только ростом локальной загрузки.

## 4. Политики запуска и алгоритмы

### 4.1. Общие положения

Политика управляет допуском сырья в производственную границу. DBR дополнительно управляет допустимыми стартами выбранного drum. Она не меняет физическую скорость постов и не отменяет их буферы, календарь, план или обслуживание. Для корректного сравнения push и DBR прочие параметры сохраняются.

Источник описывает материал, доступность сырья, разрешённые первые посты и конечные партии запуска. Никакого бесконечного мгновенного заполнения бесконечного буфера не допускается. Каждый источник имеет положительный интервал запуска и количество на попытку. Неисполненные push-попытки из-за заполнения не накапливают бесконечный долг.

Интервал источника отсчитывается в накопленном рабочем времени общего календаря. Первая попытка происходит в начале первого дня, следующие в моменты n × интервал. Обед и ночь приостанавливают этот отсчёт, он не сбрасывается в начале новой смены. Пример первого дня: источник с интервалом 7 минут после попытки в 11:58 снова пробует в 13:05; после попытки в 16:56 снова пробует в 08:03 следующего дня. Попытка ровно на закрытии рабочего интервала переносится на его ближайшее открытие и не дублируется. На конце всего прогона новая попытка не выполняется.

### 4.2. Push

1. В заданный момент источник пытается выпустить настроенное количество сырья в свободные входные места первых постов.
2. Получатели выбираются по приоритету, затем ID. Неразмещённое сырьё остаётся вне производства, затраты закупки на него не начисляются.
3. Через заданный интервал выполняется следующая попытка. При конечном складе выпуск ограничен остатком.
4. Посты выполняют собственные планы при наличии входов и рабочего времени, не проверяя потребность ограничения.

Шаблон «Загрузить всех» задаёт достаточно частый запуск, большие конечные буферы и локальные планы. Бесконечные буферы разрешены для специального урока роста запасов, но ограничиваются безопасным числом событий и памятью приложения. Push не означает случайное производство материалов без рецепта.

### 4.3. DBR: выбранное учебное приближение

В MVP используется один явно выбранный drum. Это расписание одного поста, а не оптимизационный солвер для произвольной сети. Конструктор поддерживает сборку и разделение потоков, но DBR требует однозначно заданных производственных маршрутов и согласованного плана продукции. Если эти условия не выполнены, конфигурация работает в push, а DBR показывает конкретную причину недоступности.

До старта пользователь выбирает drum, его циклический план, защитное время B и максимальное число открытых заданий. B измеряется в рабочих минутах календаря drum и является целевым покрытием готовыми комплектами. Отдельно задаётся номинальное опережение изготовления L для сырьевой ветви. Начальная оценка L является суммой средних операций и необходимых переналадок по самой длинной ветви до drum; пользователь может изменить её до запуска. Она не включает целевой запас B и не обещает учесть очереди. В форме показываются оба значения и суммарное опережение запуска.

Значение B в комплектах можно задать как удобный вариант; оно переводится во время по среднему темпу выбранного плана и показывается вместе с округлением до полной партии. Обслуживание и переналадки не считаются полезной обработкой в оценке готового покрытия.

Политика не использует скрытое знание будущих случайных длительностей. Плановые слоты строятся по средним временам и календарю. План не пересчитывается каждый раз так, чтобы скрывать опоздание.

### 4.4. Подготовка drum и rope

1. Развернуть циклический план drum на горизонт. Каждый слот содержит рецепт, полную обработочную партию, плановое время старта и уникальный slotId. Между слотами включить среднюю обработку, переналадки и прогнозируемое обслуживание по принятым порогам.
2. Задать конечный продуктовый цикл, соответствующий целому числу циклов drum, и разложить его потребность назад по выбранным маршрутам до источников. Это включает компоненты сборок после drum, даже если их собственная ветвь не проходит через drum. Количество повторений производящего рецепта округлять вверх до целого, затем до полной обработочной партии. Излишек учитывать как плановый остаток следующих циклов, не заказывая повторно.
3. Сформировать единый реестр плановых работ с ключом «пост, рецепт, номер партии». Один плановый выпуск учитывается один раз, его результат распределяется между зависимыми потребностями. Для общей детали, используемой двумя ветвями, потребности суммируются до округления. Работы связываются со слотами drum, обеспечивающими соответствующий конечный продуктовый цикл. Общая upstream-партия получает срок самого раннего зависимого слота. Компоненты сборки после drum прикрепляются к этому же продуктовому циклу, а не игнорируются.
4. Рассчитать момент разрешения сырьевой заявки как `плановый старт связанного слота − L ветви − B`. Вычитание сначала B выполняется по рабочему календарю drum, затем L по общему календарю источников и upstream-постов. В MVP их календарь одинаков, кроме платной работы отдельных постов в обед; такая работа учитывается в предварительном плановом проходе. Если цикл включает несколько слотов drum, общая заявка привязывается к самому раннему из них. Это консервативный учебный алгоритм, а не оптимизация сроков всех заказов.
5. Отрицательный момент разрешения превратить в разрешение в начале прогона. Подписать, что первые слоты могут опоздать из-за пустого старта. Автоматического бесплатного предзаполнения нет.

Проверка до старта требует однозначно связать весь целевой поток с конечным продуктовым циклом выбранного drum. Независимые продукты, не связанные с ним и не являющиеся компонентами его конечных изделий, в DBR MVP запрещены с объяснением; в push они допустимы. Для альтернативных производителей в плане выбирается один, остальные в этом DBR-прогоне не производят данный материал. Произвольные независимые канаты и смешанный push/DBR относятся к следующей итерации.

Плановые остатки инициализируются фактическим начальным запасом по месту хранения, а не общей суммой одинакового materialId по всей схеме. Начальный материал, уже выделенный другому посту, нельзя второй раз обещать drum. Каждый остаток учитывается один раз. Предварительный проход проверяет и лимит открытых заданий, и ёмкости. Если они не позволяют разместить даже минимальный связанный комплект, DBR не запускается. Если разместить комплект можно, но ёмкости недостаточны для цели B, это предупреждение о недостижимом уровне защиты, а не скрытое увеличение буферов.

Планирование является конечным проходом по DAG маршрутов и заданным планам. Оно не ищет автоматически наилучший состав продукции или порядок рецептов. До реализации DBR должен пройти отдельный этап проверки на линейной линии, сборке upstream от drum, сборке downstream от drum и общем материале двух ветвей одного продукта.

### 4.5. Работа DBR во время прогона

Разрешённая заявка входит в ограниченную очередь rope. Открытым считается допущенный политикой слот, партия которого ещё не завершена на drum. Допуск происходит при наступлении самого раннего срока его сырьевых заявок, с учётом лимита. Если благодаря начальному запасу сырьевые заявки не нужны, срок допуска равен плановому старту слота минус B, но не раньше начала прогона. Такой слот тоже занимает место в лимите: отсутствие новой закупки не означает отсутствие работы. Новые слоты сверх лимита открытых заданий не разрешаются. Общая upstream-партия может обеспечивать несколько слотов; тогда они допускаются группой, и лимит должен вмещать минимальную такую группу. Несовместимый лимит выявляется до старта, иначе возник бы тупик из-за самой политики.

Сырьё запускается только на тех же периодических попытках источника, что в push, при наличии разрешённой потребности, свободного входного места и остатка склада. Размер и интервал источника остаются верхним пределом запуска в обеих политиках. В DBR неисполненная потребность ждёт следующей попытки, а в push неисполненная попытка отбрасывается. Приоритет заявок DBR: просроченное плановое время слота, затем slotId и sourceId. При закрытии слота разрешаются ранее отложенные заявки, но фактический запуск всё равно ждёт ближайшей попытки источника. Лимит заданий является дополнительной защитой, а не заменой расписания drum.

Проверка согласованности планов использует потребности полного повторяемого продуктового цикла. Для каждого upstream-поста строится вектор требуемых повторений рецептов и сравнивается с вектором его собственного плана. Допускается целое кратное циклов с явным учётом округлённого остатка; отсутствующий рецепт или устойчивый избыточный выпуск одного материала при нехватке другого блокирует DBR. Чередование рецептов и зависимость компонентов проверяются предварительным детерминированным плановым проходом с теми же маршрутами и конечными буферами. Это не оптимизация: неудачный заданный порядок нужно исправить пользователю, а не скрыто заменить.

Для рекурсивного расчёта заявки используется правило `нужно повторений = ceil(max(0, потребность − плановый остаток) / выход рецепта)`, затем округление до полного числа обработочных партий поста. После планового выпуска остаток увеличивается на выход и уменьшается на выделенное количество. Для дробного входа расчёт выполняется в точных микроединицах. Плановые остатки и физические остатки являются разными структурами: план не создаёт реальный материал.

На каждом посту остаётся фиксированный план рецептов. DBR не перепрыгивает к другому рецепту при нехватке материала. Подготовленный план должен соответствовать потребностям слотов; проверка до старта выявляет недостающие рецепты и невозможные соотношения. При резервировании входов на обработку учитываются обычные приоритеты. Заявки rope являются плановым учётом потребности, а не тайными неперемещаемыми физическими резервами, обходящими учебный эффект конкуренции.

Реестр плановых работ используется для расчёта сырьевых заявок и проверки совместимости. Он не является отдельным диспетчером всех постов: вне drum посты продолжают свои циклические планы при наличии материала. После последней заявки они могут доработать имеющийся запас до конца горизонта; новый материал сверх заявок источник не добавляет. Излишки начального запаса и округления партий могут остаться в WIP или быть переработаны дальше. Отсутствие лишнего выпуска не обещается. Дополнительные разрешения на каждую операцию и отдельный алгоритм выбора рецептов в MVP не вводятся.

Drum не начинает обработку слота раньше его планового времени. Нужная переналадка и обслуживание выполняются в предусмотренных межслотовых интервалах по общим правилам поста; они не должны ошибочно начинаться только после наступления времени обработки. Если слот наступил, а полного комплекта нет, drum голодает. После появления комплекта и окончания необходимой подготовки он стартует сразу; последующие слоты сохраняют собственные плановые времена, но ждут освобождения ресурса. Раннее завершение создаёт видимое ожидание расписания, позднее увеличивает опоздание. После последнего слота за горизонт новые слоты не создаются.

Слот закрывается после завершения обработки его партии drum; блокировка выгрузки не отменяет выполненную обработку. Связанные обязательства до конечного выпуска остаются в плановом учёте downstream. Невыполненные сырьевые заявки остаются видимым долгом, пока их потребность действительно существует; выполненное количество не заказывается повторно.

В DBR MVP требуется p = 0 на всех постах управляемого потока и отсутствие начального дефектного запаса. Иначе жёсткий план без компенсации брака может навсегда лишить slot комплекта и исчерпать лимит открытых заданий. Контроль с нулевой вероятностью дефекта допустим как операция. Эксперименты с браком доступны в push; автоматическая компенсация потерь и совместный урок DBR с браком являются следующей итерацией. При выборе неподдерживаемого режима приложение показывает ошибку и не переключается в push молча.

### 4.6. Зоны буфера DBR

Для простого однотипного drum защищённость в комплектах определяется как минимум по всем входам `floor(доступно[m] / требуетсяНаПартию[m])`. «Доступно» включает только физический входной запас drum после завершения всех мгновенных передач. Материал в выходе другого поста с конкурирующими получателями не обещается drum заранее. Незавершённые детали не засчитываются как готовая защита.

При нескольких рецептах проверяется последовательность ближайших ещё не начатых слотов: виртуально из текущих остатков вычитаются комплекты до первого, который нельзя обеспечить. Сумма средних времён полезной обработки обеспеченных слотов даёт покрытие C. Текущая уже обрабатываемая партия и её изъятые входы не входят в C. Один избыток дверей не маскирует нехватку боковин следующего слота. Переналадка, обслуживание и календарное ожидание не считаются запасом обработки.

Покрытие относительно цели B отображается так: красная зона при C < B/3, жёлтая при B/3 ≤ C < 2B/3, зелёная при C ≥ 2B/3. Значение C > B подписывается как избыток. Альтернативный график «проникновение в буфер» равен `max(0, 1 − C/B)` и имеет обратное направление. При B = 0 цветовые зоны отключены. Эти учебные пороги не выдаются за обязательный промышленный стандарт.

На графике отдельно показываются покрытие, опоздание слотов, материальный запас и WIP upstream. DBR во времени не заменяется одной раскраской процента заполнения физического буфера.

### 4.7. CONWIP

CONWIP оставляется на следующую итерацию. Для линии 1:1 его можно реализовать как возврат разрешения после выхода детали. Для сборки и коэффициентов 1:10 потребуется определить единицу карточки и границу контура. До такого определения универсальная кнопка CONWIP не добавляется.

## 5. Интерфейсы и поведение

### 5.1. Навигация и рабочие режимы

Основные разделы: «Уроки», «Песочница», «Мои конфигурации», «Глоссарий». Рабочий экран имеет вкладки «Схема», «Метрики», «События» и панель выбранного объекта. Конструктор является режимом того же экрана до запуска, поэтому студент не переносит настройки между разными инструментами.

Числа и проценты прохождения в текстовых макетах иллюстративны. Они не являются измеренными результатами будущего движка или обещанием конкретного выигрыша.

Переключение RU/EN сохраняет настройки, результаты и текущее модельное время. Числа отображаются с учётом языка, но JSON всегда использует стандартную числовую запись. Поля принимают десятичную запятую и точку с однозначной нормализацией; неоднозначные разделители тысяч не принимаются.

```text
|                                                                  |
| Пост          Вход              Выход           Переопределения   |
| Штамповка     наследует         наследует       нет               |
| Покраска      наследует         10 дверей       выход             |
| Сборка        20 / 80           наследует       вход              |
|                                                                  |
| [Обновить наследуемые] [Сбросить переопределения и применить всем]  |
| Предпросмотр: изменятся 2 поста, 4 лимита. [Показать значения]      |
+------------------------------------------------------------------+
```

В глобальном эксперименте пользователь может, например, установить входные буферы на 0.1, 0.5 или 2 смены, запускать независимые прогоны и сравнивать WIP и голодание. Ни одна глобальная настройка не меняется внутри уже начатого прогона.

### 5.6. Схема и визуальные правила

Посты располагаются по слоям слева направо в соответствии с маршрутами. Сборка получает несколько входящих линий, разветвление несколько исходящих. Пользователь выбирает разрешённые соединения в форме, свободного рисования цеха нет. Перестановка отображения в одном слое не меняет приоритет распределения.

Каждый пост показывает название, текущий рецепт, состояние, прогресс, численность входов и выходов. Входные стопки находятся слева от блока, выходные справа. При нескольких материалах используются отдельные подписанные стопки. Клик по числу открывает точный состав, ёмкость, возраст старейшей партии и причину ожидания.

Для малых количеств одна фишка соответствует одной детали. Для больших стопка агрегируется, например «фишка × 10», с обязательным числом. Отрисовка ограничена числом видимых фишек, учётные количества не уменьшаются. Форма и подпись дополняют цвет материала. Скрытый брак визуально не отличается до контроля.

При мгновенной передаче модель уже учитывает материал у получателя. Короткая анимация между блоками лишь объясняет событие. При высоких скоростях она агрегируется или отключается, чтобы не создавать очередь анимаций. Режим уменьшенного движения заменяет перемещение краткой подсветкой.

Выделение ограничения является отдельным оформлением, не цветом рабочего состояния. При выборе поста не теряются его состояние и отметка выбранного drum. Легенда доступна постоянно.

### 5.7. Экран во время прогона

```text
+--------------------------------------------------------------------------------+
| День 2, 11:43 / 5 дней       [Пауза] [Шаг] Скорость: 20x [Остановить]             |
| Конфигурация зафиксирована. [Создать изменённую копию для нового прогона]         |
+--------------------------------------------------------------------------------+
| [Схема] [Метрики] [События]                 [Найди узкое место] [Показать причины]|
|                                                                                |
| [Пост A: работает] -> [12/40] -> [Пост B: голодает] -> [Сборка] -> [Продано 35]  |
|                                  Нет 2 деталей C                               |
|                                                                                |
+--------------------------------------------------------------------------------+
| Выход: 35 изделий | WIP: по материалам | T: 350 | OE: 180 | NP: 170              |
| [Выход по сменам] [WIP и lead time] [Состояния постов] [Денежные показатели]      |
| Объяснение: очередь перед A не означает наличие полного комплекта у B.          |
+--------------------------------------------------------------------------------+
```

«Пауза» прекращает продвижение модельного времени и сохраняет конфигурацию заблокированной. «Продолжить» возобновляет тот же прогон. Скорость управляет количеством модельного времени за реальную секунду, не длительностями операций. «Максимум» выполняет расчёт порциями с обновлением UI и возможностью остановки.

«Остановить» завершает прогон как прерванный, сохраняя доступный в памяти результат и фактический горизонт. «Повторить» запускает тот же RunConfig с начала. «Изменить и перепрогнать» создаёт редактируемую копию и предлагает оставить текущий результат для A/B. «Сбросить» очищает состояние прогона, но не стирает сохранённую конфигурацию и прогресс уроков. Переход между разделами сам по себе не удаляет результат.

### 5.8. Метрики и события

Экран метрик содержит графики накопленного физического выхода по продуктам, WIP по материалам, среднего и распределения lead time завершённых изделий, времён состояний постов, T/OE/NP и покрытия DBR. Масштаб времени выбирается в рабочих днях или полном календарном времени; обозначение видно на оси.

Ночь может сворачиваться только визуально. Интегралы полного lead time и среднего календарного WIP остаются рассчитанными по полному времени. Для сравнения разных конфигураций время измерения и способ сворачивания должны совпадать.

При наведении показываются значение, время, единица и определение. Табличный вид доступен для каждого графика. Средний lead time сопровождается количеством завершённых изделий и числом ещё незавершённых, чтобы малое значение при огромном WIP не выглядело улучшением.

Журнал событий фильтруется по посту и типу. Строка содержит модельное время, причину, материал, количество и ссылку на пост. Например: «День 2, 10:14. Штамповка заблокирована: во входе покраски нет места для 4 дверей». Полный неограниченный журнал в память не накапливается; хранится кольцевой диагностический буфер, а агрегаты считаются независимо.

### 5.9. A/B-сравнение

```text
+----------------------------------------------------------------------------+
| Сравнение A/B        Общий seed: 2048     Горизонт: 5 дней                   |
| Отличия: B, входной буфер ограничения 4 -> 20                               |
+-------------------------------------+--------------------------------------+
| A: исходный                        | B: защитный буфер                    |
| [Схема и время]                    | [Схема и время]                      |
+-------------------------------------+--------------------------------------+
| Показатель             A                B               Разница             |
| Продано                ...              ...             ...                 |
| Средний WIP            ...              ...             ...                 |
| Голодание ограничения  ...              ...             ...                 |
| Средний lead time      ...              ...             ...                 |
| Чистый результат       ...              ...             ...                 |
|                                                                            |
| [Общий график выхода] [Общий график WIP] [Различия конфигураций]              |
+----------------------------------------------------------------------------+
```

A/B содержит два независимых состояния движка и два неизменяемых RunConfig. Можно сначала закончить A, затем создать B из его конфигурации. При синхронном просмотре оба движка продвигаются к одинаковому модельному времени, а не к одинаковому номеру события.

Общий seed задаётся до запуска. При разных горизонтах итоговые числа не подписываются как прямое улучшение: предлагается общий интервал сравнения. Изменение структуры и несовпадающие операции отмечаются в списке различий. Для выводов о вариативности рекомендуется несколько seeds; в MVP их можно перебрать вручную, автоматические серии относятся к следующей итерации.

### 5.10. Конструктор

Создание новой линии начинается с шаблона либо пустого проекта. Последовательность работы: описать материалы; задать рецепты; добавить посты и их планы; разрешить маршруты; выбрать источники и конечные изделия; настроить календарь, буферы и политику; проверить; запустить.

Кнопка «Добавить сборку» создаёт обычный пост и форму рецепта с несколькими входами. Кнопка «Добавить контроль» создаёт контрольный пост и предлагает вставить его в выбранный маршрут. Удаление используемого материала или рецепта требует сначала устранить зависимости либо явно показывает все удаляемые связи. Отмена и возврат изменений доступны только в редакторе и не меняют историю прогонов.

Проверка выявляет отсутствующих производителей, неиспользуемые выходы, отсутствующие цены конечных изделий, циклы маршрутов, недостижимый конечный выход, входную ёмкость меньше комплекта партии, невозможный план, некорректный календарь и выход за пределы числовой точности. Несколько материалов на входе считаются нормальной сборкой, а несколько потребителей нормальным разветвлением.

Неиспользуемый материал без активного маршрута является предупреждением, если он лишь хранится в справочнике. Выпускаемый активным планом материал без потребителя и без рынка является ошибкой. Невыполнимость входного комплекта из-за геометрии буфера является ошибкой, а риск временного голодания из-за вариативности или приоритета предупреждением. Проверка push не требует, чтобы все посты были сбалансированы: дисбаланс нужен для уроков.

Ошибки блокируют запуск. Предупреждения, например бесконечный буфер, возможное голодание низкоприоритетной ветви или дорогая переналадка, объясняются и не блокируют допустимый эксперимент.

### 5.11. Урок как самостоятельное занятие

Урок содержит короткое объяснение, вопрос-прогноз, исходную конфигурацию, действие студента, измеримый результат и разбор. Перед раскрытием ограничения студент может выбрать пост и объяснить причину. Ответ не требует свободного текста для прохождения, но личная заметка допускается.

Запись прогресса содержит lessonId, lessonVersion, просмотренные объяснения, завершённый исходный прогон, проверенный ответ и просмотренное сравнение. Для прохождения требуется выполнить перечисленные в уроке действия и открыть разбор. Неподтверждённый ожидаемый знак стохастического эффекта не ставит студенту автоматический «провал»: система предлагает повтор и объясняет неопределённость. Изменённый эксперимент сохраняется отдельно и не подменяет прохождение исходной версии. Обновление версии урока не стирает старую отметку, но показывает наличие нового материала.

После исходного прогона студент получает предложение изменить один параметр. Новый прогон сохраняет связь с базовым. Разбор показывает, какой показатель изменился и почему. Если конкретный seed не дал ожидаемого знака эффекта, вывод не подделывается: показываются фактические числа и предложение проверить более длинный горизонт или другой seed.

Вариант B создаётся из конфигурации A и сначала показывает те же значения всех настроек. Если последующая правка времени или плана меняет расчётные ёмкости «на долю смены», до запуска показываются обе перемены. Для эксперимента «изменить только скорость» предусмотрена команда «Зафиксировать текущие ёмкости как количества». Если студент оставил наследуемый расчёт, B использует пересчитанные ёмкости и сравнение явно перечисляет этот дополнительный фактор. Автоматически пересчитанные буферы нельзя скрывать в сравнении одного фактора.

При изменении параметров урок помечается «изменённый эксперимент». Выполнение исходного упражнения и исследование своей конфигурации различаются в прогрессе. Кнопка восстановления возвращает исходную конфигурацию выбранной версии урока. Прогресс не зависит от наличия истории временных рядов.

### 5.12. Доступность и размеры экранов

Основной целевой интерфейс рассчитан на настольный браузер и планшет в горизонтальном положении. На узком экране схема прокручивается, панель поста открывается отдельной вкладкой; A/B переключается между A и B вместо двух тесных колонок. Сохраняются таблицы результатов и основные кнопки.

Все формы и действия доступны клавиатурой. Для схемы существует текстовый список постов, маршрутов и текущих причин ожидания. Цвет не является единственным каналом, движение можно сократить, формат графика можно заменить таблицей.

### 5.13. Хранение, импорт и шаринг

В localStorage хранятся библиотека конфигураций, пользовательские сценарии, прогресс уроков и настройки UI. Каждая сохранённая структура содержит schemaVersion и собственные ID. Временные ряды, полные снимки текущего прогона и неограниченный журнал там не хранятся. После перезагрузки можно восстановить конфигурацию и повторить прогон, но не обещается продолжение с той же секунды.

Доступность localStorage проверяется пробной записью и удалением собственного ключа в try/catch. Получение самого объекта storage также может завершиться ошибкой. При отказе используется память вкладки, показывается ненавязчивый статус «Сохранение недоступно, экспортируйте JSON». Расчёт, уроки и импорт продолжают работать.

Поведение localStorage для `file://` не стандартизировано и зависит от браузера; перенос HTML может изменить доступную область хранения. Поэтому JSON является обязательным переносимым способом сохранения. Основание: [MDN, localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage). Не обещается автоматический перенос локальных сохранений на GitHub Pages.

При переполнении квоты приложение сохраняет рабочую конфигурацию в памяти, сообщает об ошибке записи, предлагает JSON-экспорт и удаление выбранных старых конфигураций. Другие ключи origin не очищаются. Пользовательские данные не удаляются молча ради освобождения места.

Сохраняемые записи разделены по объектам и пространству имён TOC. Обновление одной конфигурации выполняется одной записью, миграция сначала читает и проверяет старые данные, затем формирует новую версию в памяти. Исходник не затирается до успешной валидации. При сбое доступен экспорт исходных данных. Будущая неизвестная schemaVersion открывается с сообщением о несовместимости, а не с догадками о структуре. Резервная копия не должна удваивать все данные при уже исчерпанной квоте.

Экспорт JSON содержит версию схемы, конфигурацию, seed, настройки запуска и, для пользовательского урока, инструкции и цели. Временные ряды по умолчанию исключены. Импорт выполняется через выбор файла и чтение его содержимого, без fetch локального пути. Сначала показываются название, версия и результат проверки, затем создаётся новая конфигурация; существующая библиотека не перезаписывается по совпадению ID без явного действия.

URL-шаринг использует сжатый JSON в hash и версионированный префикс формата. Языковые словари и встроенные уроки в ссылку не включаются. Сжатие выполняется встроенной в сборку библиотекой, например fflate, после проверки её документации при реализации. Распаковка ограничена по размеру и числу объектов; предварительные пределы: файл 2 МБ, распакованный URL 1 МБ, до 30 постов в пользовательской конфигурации. Эти ограничения относятся к интерфейсу, а не к учебной формуле.

Hash целиком зарезервирован для конфигурации; экран и выбранная вкладка хранятся в UI, библиотека маршрутизации с конкурирующим hash-роутингом не нужна. Ссылка не содержит историю прогонов и персональные записи. Данные из ссылки не выполняются как код и не подставляются как HTML.

Для локального файла полный путь `file://` не является переносимой ссылкой. Доступны «Копировать код конфигурации» и «Импортировать код/URL». На хостинге копируется полный HTTPS-адрес с hash. Если ссылка слишком длинная для практического обмена, предлагается JSON вместо обещания универсального предела длины URL. Clipboard API необязателен: код всегда можно выделить и скопировать вручную.

История результатов между сессиями может быть добавлена через IndexedDB позже, со своим лимитом, очисткой и миграциями. Для MVP достаточно двух результатов A/B в памяти. Закрытие вкладки теряет несохранённые результаты, что сообщается рядом с экспортом конфигурации.

## 6. Каталог сценариев-уроков

### 6.1. Общие правила конфигураций

Числа ниже являются точными проектными исходниками уроков, но ожидаемые стохастические различия ещё предстоит подтвердить движком. Детерминированные результаты проверяются аналитически. Для вариативных уроков при реализации выбираются и фиксируются seeds после серии прогонов, с сохранением честных сравнений и описанием условий.

Для первичной калибровки используется заранее фиксированная серия seeds 0…29 с одинаковыми A/B-парами. Медианный знак целевого эффекта должен соответствовать объяснению, диапазон различий сохраняется в отчёте. Демонстрационный seed выбирается из этой серии и помечается как иллюстративный; он не подменяет проверку всей серии. Если эффект зависит от горизонта, урок явно называет выбранную длительность и краевой эффект. При необходимости меняется конфигурация урока с новой версией, а не скрывается неудачный исход.

Если не указано иное: смена 08:00–17:00 с обедом 12:00–13:00, партия 1, выходной буфер 0, входной буфер наследует 0.5 смены, обслуживание и брак выключены, переналадка 0, исходные буферы пусты, сырьё доступно, конечный выход продаётся сразу. Цены и затраты заданы в условных единицах и не имитируют цены реального производства. Стандартный комплект денежного урока: сырьё 10, конечное изделие 30, каждый пост 40 за смену, капитал 1000. В уроках разных продуктов цены задаются отдельно.

Неуказанный источник выпускает по 1 единице сырья каждую рабочую минуту начиная с 08:00 первого дня, пока есть место. Разные источники имеют независимые расписания попыток, но используют общий остаток одинакового сырья. Если рецепту требуется больше одной единицы, запас накапливается до полного комплекта; источник не обходит ёмкости. Контроль не преобразует материал, прочие неуказанные линейные рецепты имеют коэффициенты 1:1. Для каждого урока при реализации эти умолчания разворачиваются в полный экспортируемый конфиг.

У всех уроков до запуска доступны seed и длительность. Основной маршрут прохождения предлагает менять один фактор. Пользователь может изменить остальные параметры, получив пометку собственного эксперимента.

### 6.2. Урок 1. Зависимые операции и вариативность

Связь с книгой: поход с Херби используется как тема для обсуждения зависимости движения и разброса, без воспроизведения текста книги.

**Цель.** Различить среднюю мощность отдельного ресурса и фактический выход зависимой цепочки.

**Старт.** Три поста 1:1 со средним временем 5 минут, CV = 0, входные буферы по 4 детали, источник 1 деталь каждые 5 рабочих минут. Горизонт 2 дня. Исходный прогон детерминирован.

**Действие.** Установить CV = 0.5 всем трём постам, сохранив средние времена, seed, запуск и ёмкости. Затем увеличить буферы до 40 и горизонт до 5 дней. Дополнительная ветвь упражнения использует бесконечные входы и запуск каждые 4 минуты.

**Ожидаемый вывод.** На выбранном сравнении вариативность вызывает голодание и блокировку. Больший запас смягчает часть потерь, но увеличивает WIP. При ограниченных буферах рост запаса прекращается на ёмкости; при запуске выше среднего спроса обработки и неограниченном запасе WIP может продолжать расти.

**На экране и в метриках.** Видны непустые очереди перед одним постом одновременно с голоданием другого, график выхода, времена голодания/блокировки и WIP. Разбор не утверждает, что один seed доказывает математическое ожидание. Проверка предлагает объяснить, почему «в среднем по 5 минут» не означает идеальный поток.

### 6.3. Урок 2. Ограничение определяет выход

Связь с книгой: обсуждение NCX-10 и термообработки как ограничивающих ресурсов.

**Цель.** Найти ограничение и отличить локальное улучшение от системного.

**Старт.** Четыре поста со временами 3, 4, 8 и 3 минуты, CV = 0. Источник каждые 3 минуты, буферы по 20, горизонт 3 дня. Рекомендация ограничения скрыта.

**Действие.** Выбрать предполагаемое ограничение, проверить, затем ускорить второй пост с 4 до 2 минут. В следующем сравнении вернуть базу и ускорить третий с 8 до 6.

**Ожидаемый вывод.** Второй пост не увеличивает устойчивый темп системы. Ускорение третьего повышает доступный темп, пока не проявится другое ограничение. Конечный горизонт и заполнение линии отделяются от устойчивой оценки.

**На экране и в метриках.** Очередь перед третьим постом, голодание после него, выход по сменам и плановая мощность. Проверка требует указать причину, а не выбрать самый загруженный блок по цвету.

### 6.4. Урок 3. Буфер защищает ограничение

Связь с книгой: защита Херби и обеспечение работы ограничивающих ресурсов.

**Цель.** Найти полезную величину защиты и увидеть цену избыточного запаса.

**Старт.** Посты 3, 4 и 6 минут; CV первых двух 0.9, последнего 0. Источник каждые 3 минуты. Перед ограничением 1 место, другие входы по 20, горизонт 5 дней.

**Действие.** Сравнить ёмкость перед третьим постом 1, 8 и 40. Затем применить глобально 0.1, 0.5 и 2 смены, наблюдая различие с локальной настройкой. Сохранять одинаковую выходную ёмкость.

**Ожидаемый вывод.** Запас уменьшает голодание ограничения, но после достаточной защиты дальнейшее увеличение преимущественно связывает материал. Буфер не создаёт мощность.

**На экране и в метриках.** Красные эпизоды нехватки материала, фактический запас перед третьим постом, выход, денежный I и lead time. Подсказка показывает, унаследовал ли пост глобальное изменение или сохранил своё переопределение.

### 6.5. Урок 4. Локальная загрузка и WIP

Связь с книгой: критика показателей локальной эффективности и выпуска ради занятости.

**Цель.** Установить, что больше занятости upstream не обязательно означает больше продаж.

**Старт.** Линия 2, 3, 6 и 2 минуты, CV = 0.2, источник каждые 2 минуты, входные буферы по 300, горизонт 4 дня. Большие буферы заданы явно как учебное отклонение от глобальных 0.5 смены.

**Действие.** Сравнить частый push с push каждые 6 минут, затем с DBR на третьем посту с защитой 60 рабочих минут и ограниченным числом заданий. Отдельно включить выходные буферы первых постов по 100.

**Ожидаемый вывод.** Частый запуск и дополнительные выходные буферы увеличивают незавершёнку. Достаточно защищённый запуск по ограничению может дать сопоставимый выход с меньшими запасами. Остановка неограничивающего поста при отсутствии нужды не является сама по себе потерей throughput.

**На экране и в метриках.** В A посты дольше заняты, стопки больше; в B меньше I и средний WIP. Неполная занятость показана без красного сигнала «плохо». Проверка использует продажи и WIP, а не максимальную загрузку.

### 6.6. Урок 5. Время ограничения и обед

Связь с книгой: организация непрерывного использования ограничения во время обеда.

**Цель.** Сопоставить цену дополнительных рабочих минут на разных постах.

**Старт.** Посты 3, 8 и 3 минуты, CV = 0, буферы по 80, горизонт 3 дня. У всех обед с приостановкой. Подмена оператора стоит 0.2 за активную минуту обеда, сырьё 10 и продажа 30.

**Действие.** Сначала разрешить работу в обед второму посту; затем отдельным сравнением дать такую же возможность первому. Перед сравнением убедиться, что перед вторым постом хватает материала и после него достаточно места.

**Ожидаемый вывод.** Дополнительные минуты ограничения могут дать дополнительный выход; дополнительные минуты другого поста прежде всего увеличивают запас. Денежная выгода проверяется после доплаты, а не предполагается безусловно.

**На экране и в метриках.** В 12:00 обычные операции приостанавливаются с остатком, выбранный пост продолжает. Отчёт показывает дополнительные минуты, продажи, T, OE и NP. Если ограничение голодало в обед, разбор объясняет отсутствие ожидаемой выгоды. Дополнительный эксперимент включает обслуживание ограничения после 60 повторений длительностью 30 минут.

### 6.7. Урок 6. Обработочная и транспортная партия

Связь с книгой: уменьшение партий и ускорение движения заказов.

**Цель.** Разделить накопление полной обработочной партии и частоту передачи готовых изделий.

**Старт.** Три последовательных поста со временем повторения 2, 3 и 2 минуты, CV = 0. Каждый обрабатывает партии по 10 повторений рецепта 1:1. Входные ёмкости по 40. Транспортный порог 10. Источник выдаёт по 10 каждые 20 минут. Горизонт 2 дня.

**Действие.** Сначала изменить только транспортный порог первого и второго постов с 10 на 1. Затем изменить обработочную партию второго поста с 10 на 1. Отдельный вариант переводит первый пост в одновременную сушку: 10 изделий за цикл 20 минут.

**Ожидаемый вывод.** Ранняя передача из первого поста не позволяет второму с обработочной партией 10 стартовать без полного комплекта. Уменьшение его обработочной партии позволяет начинать раньше. В одновременной сушке уменьшение транспортного порога не даёт выпуска до конца цикла.

**На экране и в метриках.** Отмечаются первый выход, первый старт следующего поста, накопление комплекта, lead time и незавершёнка. Средняя физическая мощность при одинаковом суммарном времени отдельно подписана. Не обещается универсальный рост throughput от любой меньшей партии.

### 6.8. Урок 7. Контроль до ограничения

Связь с книгой: перенос проверки качества перед дорогим ограничивающим ресурсом.

**Цель.** Увидеть потерю времени ограничения на скрыто дефектные изделия.

**Старт.** Подготовка 2 минуты с p = 0.2, ограничение 8 минут без собственного брака, финиш 2 минуты. Контроль 1 минута, CV всех операций 0; контроль находится после ограничения. Буферы по 40, источник каждые 2 минуты, горизонт 5 дней.

**Действие.** В B перенести тот же контроль между подготовкой и ограничением, сохранив stationId, источник дефекта, seed и затраты. Для проверки гипотезы в следующем прогоне перенести источник дефекта на само ограничение.

**Ожидаемый вывод.** Раннее обнаружение дефекта подготовки защищает ограничивающее время. Оно не защищает от дефекта, появляющегося позднее на самом ограничении.

**На экране и в метриках.** До контроля все фишки выглядят одинаково; при обнаружении появляется отметка списания. Сравниваются годные продажи, сырьевой брак, минуты ограничения на списанные изделия и NP. Плановая мощность контроля выше потока, чтобы он сам не стал случайной причиной исходного результата.

### 6.9. Урок 8. Сборка нескольких потоков

Связь с книгой: зависимость выпуска от своевременной готовности всех необходимых компонентов. Конкретная конфигурация является авторским упражнением.

**Цель.** Понять, что избыток одного компонента не заменяет недостающий второй.

**Старт.** Пост корпусов: `1 R1 → 1 корпус`, 4 минуты. Пост деталей: `1 R2 → 2 детали`, 6 минут. Сборка: `1 корпус + 2 детали → 1 изделие`, 5 минут. CV ветвей 0.4, сборки 0. Вход сборки: 40 корпусов и 80 деталей. Выходы ветвей 0. Сырьевые источники обеспечивают обе ветви. Горизонт 5 дней.

**Действие.** Сначала ускорить производство корпусов с 4 до 2 минут. Затем вернуть базу и сократить время изготовления пары деталей с 6 до 4 минут. Дополнительно изменить соотношение входных ёмкостей и защитный запас.

**Ожидаемый вывод.** В исходной конфигурации детали ограничивают комплектный выпуск. Ускорение корпусов в основном увеличивает их запас; ускорение деталей позволяет выйти к ограничению сборки.

**На экране и в метриках.** У сборки две отдельные стопки и надпись «нет 2 деталей», даже если корпусов много. Счётчик готовых комплектов и нагрузка ветвей показывают отличие числа деталей от числа готовых изделий. Глобальный закон Литтла для суммы разнородных штук отключён с объяснением.

### 6.10. Урок 9. Один материал, несколько потребителей

Связь с книгой: подчинение локальных решений системной потребности. Разветвлённая конфигурация является авторским упражнением.

**Цель.** Исследовать конкуренцию за общий материал, приоритеты и буферы.

**Старт.** Штамповка: `1 лист → 1 заготовка`, 4 минуты. Пост A: `1 заготовка → 1 A`, 3 минуты, приоритет 10, вход 100. Пост B: `1 заготовка → 1 B`, 3 минуты, приоритет 0, вход 10. Сборка: `1 A + 1 B → 1 комплект`, 2 минуты, входы по 100. CV = 0, источник листов каждые 4 минуты. Горизонт 3 дня. Конечный продукт только комплект.

**Действие.** Наблюдать, как A забирает все поступающие заготовки, пока его ветвь имеет место. Затем ограничить вход сборки для A до 5 и вход A до 5, чтобы ветвь A перестала поглощать весь общий материал. Изменить приоритеты и выходной буфер штамповки отдельно. Дополнительный режим выпускает заготовки одновременными партиями по 10.

**Ожидаемый вывод.** Высокоприоритетный потребитель может лишить вторую ветвь материала, хотя обе нужны для продаж. Простой обмен приоритетов способен лишь поменять голодающую ветвь. Разумные лимиты запасов позволяют накопить оба компонента; большой общий выходной буфер сам по себе не создаёт справедливого распределения.

**На экране и в метриках.** Видны стрелки распределения, накопленные A, отсутствие B и голодание сборки. Отчёт содержит компоненты, комплекты, приоритеты и причины отказов в передаче. Урок намеренно демонстрирует ограничение простого приоритета; будущая политика распределения по комплектной потребности может улучшить его.

### 6.11. Урок 10. DBR, переналадки и миграция ограничения

Связь с книгой: организация потока вокруг ограничения и повторение пяти шагов фокусирования.

**Цель.** Пройти цикл поиска, использования, подчинения, расширения и повторного поиска.

**Старт.** Пост подготовки выполняет два рецепта из листа: `1 лист → 1 боковина` за 3 минуты и `1 лист → 3 двери` за 6 минут. Его цикл: одна партия боковины, одна партия дверей, переналадка 2 минуты при смене. Сборка: `1 боковина + 3 двери → 1 кузов`, одновременный цикл 16 минут. Финиш кузова 12 минут. CV подготовки 0.3, остальных 0. Источник листов по 1 каждые 3 минуты; входы рассчитаны на 0.5 смены, горизонт 8 дней. Исходная политика push.

**Действие.** Найти сборку как плановое ограничение. Защитить её вход, проверить обслуживание и обед. Перейти к DBR на сборке с B = 64 рабочие минуты и лимитом 8 открытых слотов. План подготовки соответствует одному комплекту на цикл. Затем сократить сборку до 10 минут, повторно оценить систему и перенести drum на подготовку, если она стала ограничением.

Номинальное L перед сборкой составляет 13 минут полного установившегося цикла подготовки и при необходимости увеличивается до запуска. В исходном сравнении обслуживания и брака нет; обслуживание включается отдельным экспериментом. При переносе drum на подготовку новый drum имеет два слота разных рецептов на один конечный кузов; продуктовый цикл и лимит заданий проверяются заново. L сырьевого источника перед новым drum может быть нулевым, если требуется лишь мгновенная передача листа из доступного склада.

**Ожидаемый вывод.** Подготовка требует в установившемся цикле 3 + 6 + 2 + 2 = 13 минут на комплект; исходная сборка требует 16, финиш 12. После сокращения сборки до 10 ограничение переходит на подготовку. Ускорение прежнего drum дальше не решает новую задачу. Более редкие переналадки могут повысить мощность подготовки, но увеличат ожидание комплектов, что можно исследовать изменением плана.

**На экране и в метриках.** Отдельные стопки боковин и дверей, очередь слотов drum, покрытие в рабочих минутах, красные зоны нехватки, фактическое опоздание, выход и WIP. Пять шагов показаны как последовательность наблюдений и экспериментов. Для повторного drum на подготовке его план содержит обе разновидности выхода, а расчёт защищённости проверяет ближайшие рецепты, не сумму несопоставимых штук.

### 6.12. Условия приёмки уроков

Каждый урок поставляется с русским и английским текстом, исходным конфигом, фиксированным seed, рекомендуемым горизонтом и конфигурацией ожидаемого изменения. Числовые ожидания для вариативных уроков выводятся только после проверки реализации. До этого нет выдуманных процентов выигрыша.

Урок считается технически готовым, если исходник проходит валидатор, его можно открыть из JSON и URL, результаты повторяются, целевой эффект наблюдаем на эталонном сравнении, а разбор объясняет условия его возникновения. Обязательные уроки 8 и 9 проверяют соответственно слияние и разделение потоков. Все десять уроков входят в целевой MVP, хотя разрабатываются последовательно.

### 7.1. Выбор технологий

| Область | Предложение | Причина |
|---|---|---|
| Язык | TypeScript со строгой проверкой | Явные типы состояний, конфигурации и событий |
| Сборка | Node.js как инструмент разработки, Vite | Сборка локальных зависимостей и удобная разработка; Node не нужен пользователю |
| Интерфейс | React, клиентский рендеринг | Формы, панели, уроки и независимые A/B-представления |
| Схема | SVG с DOM-подписями | Небольшие графы, масштабирование, выбор постов и доступные подписи |
| Фишки | SVG с ограничением числа видимых элементов | Достаточно для учебных линий, без отдельного игрового движка |
| Графики | Собственные простые SVG-графики по общему компоненту шкал | В MVP ограниченный набор графиков; исключает тяжёлую зависимость и сетевые ресурсы |
| Валидация | Версионированная схема и чистые функции проверки | Одинаковые правила в редакторе, JSON, URL и движке |
| Тесты движка | Vitest, при необходимости генеративные проверки | Проверка чисел, событий, повторяемости и инвариантов |
| Проверка артефакта | Браузерные проверки через автоматизацию, включая file:// | Проверяет именно самостоятельный HTML, а не только dev-сервер |
| Хранение | Адаптер localStorage с памятью как запасным режимом | Полностью клиентская работа при отказе сохранения |

Выбор React является проектным решением для этого количества форм и состояний. Его официальная документация допускает самостоятельное клиентское приложение со сборщиком: [React, установка](https://react.dev/learn/installation). Версии зависимостей фиксируются lock-файлом при начале реализации; документ не задаёт предполагаемые актуальные номера.

Собственные графики ограничиваются линиями, ступенчатыми рядами, полосами состояний и таблицами. Если при реализации их стоимость окажется выше лёгкой встроенной библиотеки, допускается замена с теми же требованиями автономности и доступности. Движок от библиотеки графиков не зависит.

### 7.2. Самостоятельный HTML

Обычная production-сборка Vite предназначена для статического размещения и может создавать отдельные файлы. Настройка относительного base сама по себе не гарантирует один автономный HTML. Это различие следует из [документации Vite по сборке](https://vite.dev/guide/build).

Предлагается использовать vite-plugin-singlefile как начальный вариант встраивания JavaScript и CSS, проверив итоговый результат. Назначение плагина описано в [его исходном README](https://github.com/richardtallent/vite-plugin-singlefile/blob/main/README.md). Плагин является инструментом сборки, а не доказательством отсутствия внешних запросов.

Критерий артефакта: один `dist/index.html`, в котором встроены скрипты, стили, словари RU/EN, уроки и необходимые изображения. Нет внешних script src, stylesheet href, загрузки модулей из соседних файлов, CDN, сетевых шрифтов, fetch уроков или обязательных sourcemap. Используется системный шрифт. Динамическое разбиение на chunks отключено либо полностью встроено и проверено.

Приложение при запуске не требует service worker, регистрации origin, разрешения файловой системы или Web Worker. Исходный код может использовать модули при разработке; финальный runtime должен выполняться из встроенного bundle без разрешения внешнего module graph. Фактический формат inline-скрипта проверяется в целевых браузерах, а не определяется предположением о `base: './'`.

Для GitHub Pages выкладывается тот же HTML. Отсутствие сетевых ресурсов позволяет работать на произвольном пути репозитория. URL-hash содержит данные конфигурации, поэтому не требует серверного роутинга. Деплой не выполняется в рамках этапа концепта.

### 7.3. Разделение модулей

```text
domain
  определения конфигурации, количества, стоимости и версии схем
validation
  проверки структуры, маршрутов, комплектов и возможностей DBR
engine
  очередь событий, календарь, посты, RNG, материальный учёт
policies
  push, план drum, заявки rope, расчёт покрытия
metrics
  интегралы, выход, стоимость, происхождение и отчёт
lessons
  встроенные конфигурации, тексты RU/EN, условия упражнений
persistence
  память, localStorage, миграции, JSON, сжатый hash
ui
  редактор, схема, графики, обучение и сравнение
runner
  выполнение порциями, преобразование скорости в модельное время
```

Движок не импортирует React, DOM, localStorage, системные часы и сетевые API. Нужные данные приходят аргументами. Публичные операции: создать прогон; обработать ближайшую временную отметку; продвинуться до модельного времени или лимита событий; получить снимок и сводку. Команды UI переводятся runner в эти операции.

Два экземпляра движка не разделяют изменяемое состояние и счётчики RNG. Инициализация не меняет переданный конфиг. Снимок содержит только данные, пригодные для сериализации, без ссылок на DOM или функции. Возможный Web Worker получает тот же RunConfig и возвращает снимки, не меняя вычислительных правил.

В MVP runner выполняется в основном потоке короткими порциями с уступкой управления UI. Перенос в Worker допускается после замеров; для file:// потребуется встроенный worker из Blob и обязательный запасной режим без него. Отсутствие Worker не блокирует запуск приложения.

### 7.4. Производительность и память

Предварительная целевая нагрузка: 3–12 постов в уроках, до 30 в песочнице, два прогона A/B, десятки модельных дней. Число дней само по себе не определяет стоимость: важны короткие операции, объём выпуска и происхождение материалов.

Движок агрегирует однородные учётные партии там, где сохраняются FIFO, стоимость, дефекты и происхождение. Если часть атрибутов различается, агрегирование не теряет их ради скорости. У метрик накапливаются точные интегралы, а графики используют ограниченное число отсчётов с прореживанием. Это не изменяет итоговые суммы.

Журнал ограничен по числу записей, фишки по числу отображаемых объектов. При достижении вычислительного лимита прогон останавливается с объяснением и возможностью изменить конфигурацию. Нельзя молча удалять WIP или пропускать операции. Конкретные бюджеты событий и памяти определяются измерениями раннего прототипа.

Предварительные цели приёмки UI: одна вычислительная порция занимает не более 16 мс, снимки в режиме максимальной скорости выдаются не реже одного раза в 250 мс, реакция на паузу занимает не более 250 мс на выбранном тестовом ноутбуке. Эти числа являются целями, которые измеряются и при необходимости обеспечиваются уменьшением порции или Worker. В отчёте фиксируются устройство, браузер и размер конфигурации. Длинную обработку одной временной отметки можно внутренне приостанавливать между атомарными переходами с сохранением контекста, не публикуя незавершённый снимок. UI до завершения показывает последний согласованный снимок; команда «Шаг» завершается только после всей временной отметки. Балансы соблюдаются на каждом атомарном переходе.

Хранение графиков не должно требовать бесконечного списка lead time каждого изделия. Для средних и интегралов достаточно накопителей, для отображения распределения можно использовать явно подписанную гистограмму с фиксированными корзинами. Точные квантили не обещаются, если исходные наблюдения не сохранены. Интерфейс различает прореживание изображения графика и точность итоговой суммы.

## 8. Скоуп MVP и последующие итерации

### 8.1. Целевой MVP

MVP включает редактор материалов и рецептов, последовательную и одновременную обработку, циклические планы, несколько входов, разделение потока, приоритеты, переналадки, плановое обслуживание, скрытый брак, контроль, календарь, вариативность и seeded RNG. Буферы имеют глобальные значения и настройки постов.

Политики MVP: push и учебный одноресурсный DBR с явно заданными маршрутами, согласованным продуктовым циклом и нулевым браком управляемого потока. Поддерживаются сборки до и после drum и общий компонент двух ветвей этого цикла; независимые канаты и смешанный push/DBR отложены. Ограничения показываются до запуска. Обязательны пауза, шаг, скорость, повтор, новая конфигурация на основе результата и A/B с общим seed. Настройки симуляции после старта заблокированы.

Обязательны десять описанных уроков, песочница, схема, графики, денежные и потоковые метрики, режим поиска ограничения, localStorage с миграциями и запасным режимом, JSON, URL-код и автономный HTML. Самостоятельное обучение требует объяснений, а не только готовых конфигов.

### 8.2. Порядок разработки внутри MVP

| Этап | Результат | Условие перехода |
|---|---|---|
| 1. Основа модели | Детерминированная линия, количества, календарь, события, буферы | Аналитические примеры и материальный баланс проходят |
| 2. Сложные потоки | Рецепты, сборка, разделение, планы, два режима партий | Нет потери материала, зависания диагностируются |
| 3. Неопределённость и потери | RNG, CV, брак, контроль, переналадка, обслуживание | Повторяемость и правила пауз подтверждены |
| 4. Управление | Push, план drum, rope, метрики и сравнение | Различия политик воспроизводимы, ограничения DBR явны |
| 5. Учебный UI | Редактор, схема, уроки, RU/EN, доступность | Студент может пройти урок без внешних объяснений |
| 6. Поставка | Хранение, JSON, URL, один HTML | file:// и статический хостинг проверены без сети |

Этапы не объявляются отдельными урезанными MVP. Сборка и разделение обязательны для целевой первой версии. Код начинается только после завершения текущего документального этапа и отдельного поручения на реализацию.

### 8.3. После MVP

Следующие возможности рассматриваются отдельно: ограниченный спрос и запас готовой продукции; CONWIP; случайные поломки MTBF/MTTR; альтернативные автоматические правила выбора рецептов; распределение по комплектной потребности; автоматическое пополнение потерь от брака; несколько ограничений; матрица переналадок; история в IndexedDB; серии seeds и доверительные интервалы; Worker при подтверждённой необходимости.

Автоматические серии seeds здесь означают пользовательский инструмент в интерфейсе. Разработческие серии для калибровки и приёмки уроков обязательны уже в MVP. Совместное применение DBR с ненулевым браком требует сначала определить пополнение потерь и освобождение сорванных заданий.

К ещё более поздним задачам относятся ресурсы людей с конкурирующими потребностями, многосменный календарь, возвраты и переделка брака. V/T-заводы как специальная методология, реалистичная логистика и оптимизационные солверы находятся вне текущего направления. Наличие простого разветвления не означает полноценную модель V-завода.

## 9. Валидация модели и критерии готовности

### 9.1. Принципы проверки

Проверяется сначала независимый движок, затем соответствие интерфейса его данным и автономный артефакт. Для стохастических случаев инварианты проверяются на каждом seed, а статистические ожидания на серии. Один красивый прогон не заменяет проверку правил.

Тесты привязываются к поведению и числовым результатам, а не повторяют внутренние функции реализации. Состояния и версии схем включаются в тестовые конфигурации. Изменение алгоритма, влияющее на результат, сопровождается версией и обновлением эталонов с объяснением.

Строгие пределы проверяются по фактическим длительностям и доступному времени, а сравнение с расчётной средней мощностью является статистическим.

### 9.3. Повторяемость, RNG и A/B

Одинаковые конфиг, версии и seed должны давать одинаковые события, суммы и состояния после каждого шага. Сравниваются обычный пошаговый запуск, продвижение большими интервалами, разные скорости и чередование двух движков. UI, язык и размер окна результата не меняют.

Для генератора проверяются известные значения на фиксированных ключах. Для распределений отдельно проверяются положительность, границы и приблизительные моменты на большой выборке с разумным допуском. Не требуется, чтобы среднее десяти операций точно совпало с μ. Переименование поста и перестановка его отображения не меняют поток случайности.

Отдельно проверяются различающиеся sampleIndex одного выпуска и одинаковые результаты эталонных численных преобразований в Chrome, Firefox и Safari. Вероятность брака на штуку не должна случайно превратиться в одну вероятность на всю партию. Вырожденные равномерное и треугольное распределения не приводят к делению на ноль.

В A/B изменение времени только одного поста не меняет базовые случайные значения других постов на тех же номерах операций. При изменении числа операций тестируется согласованное ограниченное соответствие, а не невозможное равенство всех деталей.

### 9.4. Балансы и временные интегралы

Для каждого события проверяются неотрицательные количества, лимиты буферов и невозможность одновременной обработки двух партий одним постом. Поскольку рецепты преобразуют типы и количество, простое равенство суммы входных и выходных штук неверно. Проверяются проводки рецептов, начальные остатки, выпуск, потребление, списание и остатки по каждому materialId.

Стоимостный баланс проверяется по формуле раздела 3.16, включая дробное сырьё, сборку, разделение и брак. Сумма времён взаимоисключающих состояний равна наблюдаемому интервалу. Для доступного рабочего времени сумма обработки, голодания, блокировки, наладки, обслуживания и ожидания drum равна знаменателю загрузки.

Закон Литтла проверяется на подходящей линии через точное интегральное тождество, затем через стационарное приближение с краевой поправкой. Сборка и превращение 1:10 не должны показывать ложное сообщение «закон нарушен».

### 9.5. Проверки DBR

До разрешения слота сырьё его заявки не запускается. Один слот не создаёт повторных закупок при повторной попытке из-за полного входа. Отложенное разрешение не теряется. Лимит открытых заданий соблюдается, плановые излишки не заказываются второй раз.

Для сборки отсутствие одного компонента даёт нулевую защищённость соответствующего ближайшего слота, независимо от избытка другого. Для разделения материал не обещается одновременно двум ветвям. Drum не стартует раньше слота, позднее завершение не стирает опоздание из плана, а неподдерживаемая топология получает явную ошибку валидации.

Сравнение с push выполняется при одинаковых мощностях, seed, календаре и горизонте. Цель урока о меньшем WIP проверяется на конфигурации с достаточной защитой, а не объявляется универсальным превосходством любой настройки DBR. Малый B должен воспроизводимо показывать риск голодания.

Обязательны четыре конфигурации: линейная; сборка перед drum; сборка после drum с боковой сырьевой ветвью; один полуфабрикат для двух ветвей общего конечного изделия. Проверяется, что L и B не подменяют друг друга, исходный запас не заказывается повторно, связанная группа слотов помещается в лимит и после закрытия слота разрешается ожидающая заявка. Интервал источника одинаково ограничивает push и DBR.

На конфигурации с ненулевым браком выбор DBR даёт конкретную ошибку применимости. Это не приводит к незаметной смене политики. Избыточный B относительно физической ёмкости даёт предупреждение, а невозможность минимального комплекта ошибку. Ранняя переналадка до времени обработки слота и поздняя из-за нехватки материалов различаются в журнале.

### 9.6. Проверки интерфейса, хранения и поставки

| Область | Обязательная проверка |
|---|---|
| Блокировка настроек | После старта недоступны изменения длительности, seed, рецептов, буферов и календаря; новая копия редактируема |
| Глобальные буферы | Наследование обновляет только наследуемые поля; принудительное применение явно сбрасывает собственные значения |
| RU/EN | Все встроенные уроки и сообщения переведены; переключение не сбрасывает прогон |
| JSON | Экспорт/импорт сохраняет нормализованный конфиг и результат; неизвестная версия не повреждает библиотеку |
| URL | Сжатие/распаковка сохраняет конфиг; испорченный и слишком большой payload безопасно отклоняется |
| Storage | Запрещённый доступ, нулевая квота и переполнение не мешают симуляции; экспорт остаётся доступен |
| Миграции | Старый формат мигрирует на копии, ошибка не уничтожает исходные данные |
| file:// | Готовый HTML открывается при отключённой сети, уроки и A/B работают, нет обязательных внешних запросов |
| Статика | Тот же файл работает в подкаталоге GitHub Pages или эквивалентного тестового статического сервера |
| Доступность | Управление клавиатурой, подписи состояний, уменьшение движения, таблицы графиков |
| Производительность | Максимальная скорость оставляет отзывчивую паузу; большие стопки не создают по DOM-узлу на каждую штуку |

Целевые браузеры для приёмки: актуальные стабильные Chrome/Edge, Firefox и Safari на момент реализации. Особое внимание Safari и file://. Конкретные версии и результаты записываются в отчёт проверки поставки. Если API недоступен, проверяется заявленный запасной режим.

### 9.7. Готовность концепта и готовность продукта

Концепт считается завершённым, когда согласованные правила сведены в единый документ без написания приложения, есть численные примеры, интерфейсы, уроки, ограничения и план проверки. Наличие этого документа не означает, что ожидаемые стохастические эффекты уже измерены.

Продукт считается готовым после выполнения целевого MVP, проверки всех уроков, документирования версий и прохождения автономной поставки. Проверки движка и HTML входят в будущую разработку, их нельзя выдавать за выполненные на этапе концепта.

## 10. Риски, ограничения и открытые вопросы

### 10.1. Риски модели

| Риск | Следствие | Мера |
|---|---|---|
| Слишком много механизмов сразу | Студент не видит причину эффекта | Уроки включают по одному механизму, расширенные поля скрыты по умолчанию |
| Двойной запас входа и выхода | Улучшение приписывается новой политике вместо большей ёмкости | Показывать суммарный запас маршрута, фиксировать остальные параметры в A/B |
| Жёсткий приоритет | Ветвь может голодать постоянно | Показывать причину, учить лимитам запасов; не добавлять скрытую справедливость |
| Жёсткий план рецептов | Можно заблокировать выпуск ожиданием неподходящего комплекта | Проверка плана, видимое ожидание; автоматический выбор отложен |
| DBR для произвольной сети | Потребуется полноценное планирование | Один drum, явные маршруты и конечный продуктовый состав, строгая проверка применимости |
| Одинаковый seed трактуется слишком широко | Некорректные выводы при изменении структуры | Независимые ключи RNG, список различий, пояснение границ соответствия |
| Конечный горизонт | Средний lead time завершённых скрывает старый WIP | Показывать незавершёнку, её возраст и краевую поправку |
| Агрегирование разнородных штук | Ложная проверка мощности или закона Литтла | Метрики по материалам и согласованным границам |
| Брак в сложной сборке | Можно потерять стоимость или неверно распространить дефект | Учёт комплектов и происхождения, балансовые проверки |
| Положительное распределение с длинным хвостом | Один цикл может занять несколько смен | Допуски параметров, видимый остаток, разбор конечного горизонта |
| Анимация выглядит как доставка | Пользователь делает вывод о транспортной мощности | Подпись мгновенной передачи, отсутствие её в расчётном времени |

### 10.2. Технические риски

Автономный HTML проверяется отдельным критерием, поскольку обычная SPA-сборка не гарантирует file://. Запрещаются обязательные динамические загрузки словарей, уроков и шрифтов. Ссылки на документацию в концепте не являются runtime-зависимостями приложения.

localStorage локального файла может быть недоступен или привязан к конкретному пути. Поэтому отсутствие сохранения является поддерживаемым режимом, а JSON обязательным средством переноса. Сжатый hash ограничен практическими возможностями обмена; длинный конфиг передаётся файлом.

Подробное происхождение, дефекты и слишком мелкие операции могут увеличить память. Сначала измеряются сценарии целевой нагрузки, затем выбираются безопасные лимиты и способ агрегирования. Worker не используется как оправдание неограниченной модели.

Редактирование сохранений в двух вкладках может привести к конфликту. В MVP записи имеют revision и время обновления; при обнаружении несовпадения предлагается сохранить копию, а не молча перезаписать. Полноценная синхронизация между вкладками и устройствами не требуется.

### 10.3. Открытые инженерные проверки

Следующие вопросы не требуют нового согласования предметной модели до начала проектирования, но должны быть проверены реализацией:

1. Достаточен ли предел точности 10⁻⁶ для всех встроенных рецептов и стоимости? Если нет, меняется формат количества с миграцией, а не добавляется плавающая ошибка.
2. Какие seeds и горизонты дают ясные учебные эффекты без чрезмерной длительности? Эталонные конфиги фиксируются после серии проверок.
3. Достаточны ли консервативные L ветвей и общий B для сборочных уроков при заданном порядке рецептов? Отдельные L уже предусмотрены, но точность оценки очередей не обещается. Если требуется оптимизация маршрутового расписания, это отдельное расширение, а не скрытое усложнение MVP.
4. Какой лимит событий и объектов сохраняет отзывчивость на обычном студенческом ноутбуке? Бюджет определяется измерением и отражается в UI.
5. Можно ли обойтись основным потоком при двух прогонах? Worker добавляется при подтверждённом выигрыше и сохранении file://.
6. Каковы итоговый размер HTML и время открытия со всеми переводами? Уроки хранятся как данные, повторяющиеся тексты и графические ресурсы не дублируются без необходимости.

### 10.4. Решения, принятые в этом концепте

Ниже перечислены проектные решения в пределах предоставленного выбора, чтобы они были доступны для последующего пересмотра:

| Решение | Принятое поведение |
|---|---|
| Начальная настройка рецепта | Первый рецепт без переналадки, если начальное состояние не задано иначе |
| Ожидание рецепта | Очередная строка плана не пропускается |
| Нехватка места после обработки | Частичная выгрузка, остаток удерживает пост |
| Глобальные буферы | Наследование, переопределения, отдельная явная команда применения ко всем |
| Обед | По умолчанию приостановка; отдельная платная подмена для учебного эксперимента |
| Ночь | Всегда приостановка в MVP |
| Обслуживание | После текущей обработочной партии и её выгрузки, до следующей |
| Дефекты | Скрытые, обнаружение на контроле гарантировано, переделки нет |
| Продажа | Годный конечный продукт продаётся немедленно, спрос неограничен |
| Деньги брака | Сырьевая стоимость списания относится в OE по учебному соглашению |
| Закон Литтла | Только согласованные единицы и границы, с учётом конечного окна |
| Горизонт | Определяется уроком или пользователем до запуска, общего числа дней нет |

Если опыт студентов покажет, что какой-либо механизм мешает объяснению, сначала упрощается конкретный урок. Базовые правила не меняются скрыто между уроками. Любая будущая смена семантики должна быть отражена в версиях модели, конфигураций и объяснениях.
