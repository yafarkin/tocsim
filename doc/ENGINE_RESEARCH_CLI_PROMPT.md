Подготовлено 15.11.2026 по запросу Евгения Яфаркина. Документ является подробным prompt для следующей работы в репозитории TOC. Создание документа не означает, что описанные функции уже реализованы или что все этапы разрешено выполнять без согласования.

## Поручение исполнителю

Ты работаешь в репозитории TOC. Доработай публичный движок `@toc/engine` и его CLI так, чтобы исследователь мог одним документированным вызовом оценить срок выполнения заданного объёма продукции и провести воспроизводимое сравнение сценариев. Результат должен включать отдельные прогоны, перцентили срока и запас относительно детерминированной базы. Для этих операций пользователю не должен требоваться собственный цикл с `Simulation.step()`.

Сначала прочитай `AGENTS.md`, `doc/SESSION_HANDOFF.md`, актуальные разделы `doc/CONCEPT.md`, `doc/BUILD_PLAN.md`, `tasks.md` и `doc/ENGINE_API.md`. Проверь фактический код. Сведения ниже описывают состояние на дату подготовки и могут устареть. Не восстанавливай старую реализацию поверх новых изменений.

Оцени объём и представь последовательность частей с результатами и проверками. Соблюдай правило проекта о работе по одной согласованной задаче. Предлагаемое разбиение приведено ниже. После согласования очередной части доводи её до проверенного результата. Не сокращай весь запрос до добавления одного флага.

## Практическая цель

В исследовании сравниваем время выполнения одного и того же заказа при неизменных средних длительностях операций. Меняем только коэффициент вариации CV и пост, на котором возникают колебания. Основной показатель первой работы есть P85 срока заказа в рабочем времени. Запас времени равен разности P85 и детерминированного срока при нулевых CV.

Дальняя исследовательская цель состоит в получении упрощённой оценки срока без повторной симуляции. В этой технической задаче требуется инструмент для проведения и проверки экспериментов. Не реализуй произвольную формулу прогноза и не заявляй научную новизну Монте-Карло.

Пользователь ожидает небольшое влияние вариативности распила, поскольку распил в среднем быстрее сборки. Он допускает, что затяжной распил иногда оставляет сборку без досок. Это исходная гипотеза, а не ожидаемый результат, под который нужно подстроить алгоритм.

## Проверенное текущее состояние

В `packages/engine/src/cli.ts` поддержаны обычный прогон конфигурации и `--bottleneck`. Вход читается из файла либо stdin. JSON API и CLI используют общий движок. Поиск уже находится в `packages/engine/src/bottleneck-search.ts`, веб вызывает ту же реализацию.

Обычный CLI вызывает `runSimulationJson`, доходит до горизонта и возвращает снимок, отчёты и историю. История в `flow-history.ts` имеет равномерную сетку и ограничена 2048 точками. Время первой точки, где видны четыре упаковки, может быть позже фактического события. История предназначена для графика и не является точным журналом завершения заказа.

Нынешний поиск сокращает времена операций одного поста на 10 % и сравнивает проданный выпуск по продуктам в конце горизонта. Для случайных условий он проверяет три парных seed. Эти три прогона не заменяют серию для оценки P85.

На исходной лесопилке обычный поиск вернул `outcome: "noGain"`, пустой `stationIds` и четыре упаковки во всех вариантах. Такой результат корректен для его критерия. Заказ ограничен 60 брёвнами, исходный вариант уже перерабатывает весь запас задолго до конца смены. Более раннее завершение нельзя обнаружить по конечному количеству упаковок.

Тем самым изменено ограничение линии. Расширение редактора, импорт `toc-process` и настройки источника в UI являются отдельной задачей.

## Часть 1. Точная метрика завершения заказа

### Входной контракт

Добавь отдельный публичный контракт запроса измерения завершения. Предпочтительно оставить физическую модель в существующем `EditorConfig`, а описание измерения вынести в оболочку запроса. Конкретные имена типов выбирай по правилам проекта.

Для первой версии достаточно одной цели, которая состоит из одного или нескольких конечных материалов с положительными целевыми количествами. Все позиции цели должны быть достигнуты одновременно по накопленным принятым количествам. Разные материалы нельзя складывать в одно число без модели эквивалентности.

Зафиксируй семантику количества. Пользователь передаёт обычную десятичную строку количества, например `"4"` упаковки. Внутренние миллионные доли не должны требоваться во входном файле пользователя. Проверь формат, положительность, точность, диапазон, дубли и существование материала. Материал должен быть допустимым конечным продуктом с учётом существующего контракта маршрутов.

Цель относится к совокупному принятому выпуску от начала прогона. Это пока не диспетчеризация нескольких именованных заказов с конкурирующими приоритетами. Входящие промежуточные запасы сами по себе не считаются выполненным заказом.

### Семантика измерения

Нужен первый момент времени, в который все целевые количества достигнуты. Проверяй условие после завершения атомарной отметки планировщика. Если несколько событий имеют одинаковое время, сначала должны быть применены согласованные изменения этой отметки.

Учитывай принятый годный продукт на выходной границе линии. Производство на последнем посту, нахождение в выходном буфере и приём рынком могут быть разными событиями. При браке или задержке передачи преждевременно завершать заказ нельзя. Если одна передача пересекла целевое количество, момент такой передачи является моментом достижения цели.

Возвращай календарное и рабочее время в целых миллисекундах от начала прогона. Рабочее время считай по календарю движка, а не вычитанием одного часа обеда вручную. Проверяй переходы через обед и несколько смен. Используй понятие рабочего времени линии из существующего `observation.workMs`. При замещении на обед явно документируй, что это время общего календаря, а не сумма отработанных ресурсов.

Точный момент не извлекай из прореженной истории графика и не интерполируй между точками. Реализуй измерение рядом с существующим выполнением событий либо общим наблюдателем, не дублируя правила движения материалов.

### Завершённые и незавершённые прогоны

Результат должен явно различать достижение цели и недостижение к горизонту. Для достигнутой цели возвращай времена. Для недостигнутой цели возвращай `null` вместо времени и фактически достигнутые количества. Не записывай горизонт как время завершения.

Горизонт является установленной до запуска границей. Не продлевай его автоматически до успеха. Если событий больше нет, а цель не достигнута, сохрани отдельную понятную причину, насколько её позволяет определить движок. Нельзя объявлять математическую невозможность по эвристике недостаточного прогресса.

Для отдельного измерения допустимо завершить вычисление после достижения цели, если это явно отражено в контракте. Обычный режим CLI должен по-прежнему доходить до полного горизонта. Не выдавай промежуточный снимок за окончательные финансовые отчёты смены.

### API и формат

Предоставь типизированную функцию движка, безопасный JSON-фасад и CLI-вызов. DTO размести в `packages/engine/src/contract` по правилу одной сущности на файл. Опиши все поля и единицы через TSDoc. Структуры должны корректно сериализоваться в JSON без необработанного `bigint`.

Для компактного результата нужны версия схемы, версия движка, версия RNG, хеш расчётных условий, параметры цели, seed, статус достижения и оба времени. Исходные объекты не мутировать.

## Часть 2. Серии и сравнение сценариев

### Область первой версии

Добавь запуск набора явно описанных сценариев и seed в одном процессе CLI. Не запускай отдельный Node-процесс на каждый seed внутри нового batch-режима. Каждый прогон должен иметь собственное состояние симуляции. Последовательной обработки достаточно, если она приемлема по скорости. Параллелизм не является обязательным требованием и не должен менять результаты.

Для первой версии используй список полных конфигураций либо простую общую базу с типизированными изменениями CV для конкретной строки плана. Не вводи универсальный язык произвольных JSON-патчей и не исполняй JavaScript из входного файла. Полные конфигурации являются приемлемым простым решением.

Список seed должен быть явным или задаваться проверяемым диапазоном. Определи поведение повторов seed. Предпочтительно отклонять их как ошибку запроса, чтобы они не создавали видимость большего числа независимых наблюдений. Проверь границы seed и количество прогонов. Порядок результата должен быть стабильным.

До начала серии валидируй весь запрос, конфигурации, цели и статистические параметры. Сохраняй возможность воспроизведения каждого отдельного прогона из запроса и строки результата.

### План лесопильного эксперимента

Нужны сценарии CV = 0; 0,25; 0,5; 1. В одной группе меняется только CV распила s3, в другой только CV сборки s4. Средние времена остаются 2 и 8 минут соответственно. Применяется предусмотренное движком логнормальное распределение. Остальные параметры должны совпадать.

Для каждого ненулевого CV используй seed от 0 до 999. Одинаковые seed между сценариями дают парное сравнение. Не называй разные сценарии независимыми выборками. Сохрани ID постов и рецептов, поскольку они участвуют в генерации длительностей. CV = 0 можно вычислить один раз и явно обозначить как общую детерминированную базу. Не представляй такой результат как тысячу независимых наблюдений.

Предельный горизонт для всех сценариев составляет десять смен, то есть 4800 рабочих минут. В текущем календарном контракте длительность равна `9 * 86400000 + 32400000` миллисекунд. Проверь соответствие этой формулы текущему контракту.

### Статистика

По каждой группе сохраняй число запланированных, выполненных, завершивших цель и не завершивших цель прогонов. Ошибки входа и внутренние ошибки вычисления не являются наблюдениями о времени заказа.

Для полностью завершившейся группы вычисляй среднее, минимум, максимум, P50, P85 и P95. Метод перцентиля фиксируется явно: сортировка по возрастанию и элемент с номером `ceil(p*N)`, начиная с 1. Храни точные целые миллисекунды для исходных времён и не округляй их перед сортировкой. Отображение минут может быть отдельным преобразованием.

Параметр `p` должен быть в интервале `(0, 1]`. Проверяй пустые группы. Среднее вычисляй без переполнения суммы безопасного целого; применяй существующие средства точной арифметики или устойчивое накопление с документированной точностью.

Если часть прогонов не завершилась к общему горизонту, не вычисляй перцентили только по успешным. Используй исходное N. Если требуемый ранг попадает в завершившуюся часть, соответствующий эмпирический перцентиль можно вернуть с явным статусом цензурирования остальных результатов. Иначе верни `null` и признак, что уровень не достигнут в пределах наблюдения. Полное среднее и максимум при незавершённых прогонах не известны, поэтому не подменяй их условным средним или горизонтом. Отдельное условное среднее возможно только с однозначным названием и не требуется первой версии.

Запас для выбранного перцентиля равен `quantileWorkMs - baselineCompletionWorkMs`. Не обрезай отрицательный результат до нуля. Если база не завершена или перцентиль не определён, запас тоже не определён. Рядом сохрани идентификатор базы и её исходное время.

Долю завершений к заданному сроку можно добавить как простой отдельный показатель. Если срок выходит за общий горизонт наблюдения, нельзя считать все незавершённые опоздавшими именно к этому сроку. В первой версии проще отклонять такой запрос.

Интервалы неопределённости перцентилей можно выделить в следующую часть. Если реализуешь их в согласованном объёме, используй документированный метод и укажи допущения. Не смешивай интервал оценки P85 с диапазоном сроков отдельного заказа. Сравнение первых и последних 500 наблюдений является проверкой чувствительности и не доказывает сходимость.

### Выход серии и ресурсы

По умолчанию возвращай компактные строки прогонов и агрегаты, без истории графика каждого прогона. В текущем CLI один ответ лесопилки составляет несколько мегабайт, что неприемлемо для тысяч запусков. Компактный режим не должен создавать и удерживать полную графическую историю, если она не нужна для расчёта. Отключение коллектора не должно менять события, RNG или накопители отчётов.

Для каждой строки нужны scenarioId, seed, calculationHash, статус и времена. В сводке нужны метод перцентилей, N, цель, горизонт, версии и параметры сравнения. Можно возвращать общий JSON с массивом строк. CSV допускается как дополнительный документированный экспорт, но не обязателен вместо машинного JSON.

В stdout CLI должен быть только результат. Прогресс, если нужен, выводи в stderr. Предусмотри понятное завершение по SIGINT и не выдавай оборванную серию как полную. Достаточно ненулевого exit code и отсутствия успешной сводки. Если поддерживается частичный результат, явно обозначь его и перечисли выполненные прогоны. Возобновление и распределённый запуск в первую версию не входят.

## Часть 3. Поиск влияния поста на срок заказа

Сохрани существующий `--bottleneck` с его прежним критерием выпуска. Добавь отдельный явно выбираемый критерий завершения заказа. Вывод должен говорить о посте, ускорение которого сильнее улучшило выбранный показатель при заданных условиях. Не объявляй найденный пост универсальным постоянным ограничением или точным критическим путём.

Для детерминированной модели сравнивай время достижения одной цели в базе и после сокращения времени операций одного поста на 10 %. Для случайных условий сравнивай P85 либо другой явно заданный перцентиль по согласованному набору парных seed. Три seed прежнего поиска не подходят для оценки P85. Новый режим должен использовать механизм серии и требовать достаточный явно выбранный план, не скрытый произвольный размер выборки.

Применяй уже принятую семантику изменения распределений. При сокращении среднего логнормальной операции CV сохраняется. Для остальных поддерживаемых распределений используй общую существующую реализацию преобразования. Физические вместимости буферов фиксируются до изменения длительности, как в текущем поиске. Конфигурации остаются независимыми.

Возвращай базовое время или перцентиль, значение для каждого поста, разность в миллисекундах, относительную разность при ненулевой базе и список лучших кандидатов. Точное равенство в целочисленных миллисекундах должно давать равных кандидатов. Если введён допуск, он должен быть явным параметром и не маскировать неопределённость выборки.

Ускорение поста и уменьшение его CV являются разными воздействиями. В поиске по ускорению меняется длительность, а в нашем основном эксперименте меняется CV. Не смешивай результаты этих двух процедур.

Если исходный вариант или кандидат не достигает цели, не подставляй бесконечность в JSON и не вычисляй фиктивное улучшение. Сохрани статусы и доступные сравнения. Если после ускорения цель стала достижимой в горизонте, отрази факт отдельно от конечной числовой разности неизвестного исходного времени.

Для исходной детерминированной лесопилки ожидается, что сокращение сборки с 8 до 7,2 минуты уменьшит срок четырёх упаковок с 178 до 162 минут. Проверь это независимым расчётом расписания до закрепления в тесте. Старый поиск по выпуску должен по-прежнему возвращать `noGain`, поскольку обе версии дают четыре упаковки за смену.

## Предлагаемый вид CLI

Названия флагов ниже являются предложением контракта, а не описанием существующих команд:

```sh
node packages/engine/dist/cli.js --completion completion-request.json > completion-result.json
node packages/engine/dist/cli.js --experiment experiment-request.json > experiment-result.json
node packages/engine/dist/cli.js --bottleneck-completion search-request.json > search-result.json
```

Поддержи файл, `-` и stdin без пути согласованно с существующим CLI. Неизвестные или несовместимые режимы должны давать `usage`. Ошибки должны иметь существующую форму `{ok:false,error:{code,path,objectId,messages:{ru,en}}}`. Успех имеет вид `{ok:true,result:...}` с версией нового контракта. Не выводи stack trace вместо формальной ошибки.

Пример семантики запроса точного завершения:

```json
{
  "schemaVersion": 1,
  "config": "Здесь полный объект EditorConfig, не строка пути",
  "target": {
    "products": [{"materialId": "packs", "quantity": "4"}]
  }
}
```

В документации замени условный текст полноценным исполняемым fixture. Если выбираешь вложенный объект конфигурации, не интерпретируй строку автоматически как путь. Файловые удобства должны оставаться в CLI-слое и иметь отдельный контракт. JSON API движка не должен зависеть от файловой системы.

## Архитектура, совместимость и версии

Общая расчётная реализация принадлежит `packages/engine`. CLI отвечает за аргументы, ввод и сериализацию. Веб при дальнейшем подключении должен использовать тот же публичный API. Не копируй алгоритм в `src/runner` и не создавай отдельную реализацию симуляции для исследования.

Сохрани прежние режимы запуска и старые входные конфигурации. Не меняй принятую обработку календаря, рецептов, округлений, маршрутов и случайных последовательностей ради нового отчёта. Исследовательская серия должна воспроизводить прежние результаты при тех же условиях.

Выбери версию схемы каждого нового DTO. Обоснуй необходимость изменения версии фасада или движка по фактическому изменению поведения. Не меняй `EditorConfig` и формат `toc-process`, если задача решается отдельной оболочкой запроса. Не обновляй расчётную версию только из-за нового документа.

Проверь обработку ошибок и лимитов. Произвольное число сценариев, огромный диапазон seed и невозможные количества не должны приводить к неявному зависанию или переполнению. Используй разумные документированные ограничения, а не молчаливое усечение.

## Обязательные проверки

### Точное завершение

Проверь цель, достигнутую на точном событии между точками истории, и ту же цель при отключённой истории. Времена должны совпадать. Проверь пересечение обеда, конца смены и нескольких дней. Проверь перескок целевого количества одной передачей и несколько целей по разным продуктам.

Проверь нехватку сырья, слишком короткий горизонт, отсутствие дальнейших событий, брак, остаток в выходном буфере и события на одной отметке. Недостигнутые цели не должны получать фиктивное время. Некорректные цели должны отклоняться до расчёта.

Проверь совпадение API, JSON API и собранного CLI. Запусти реальный CLI из файла и stdin. Проверь код завершения, чистый JSON stdout и неизменность исходной конфигурации.

### Серии

Проверь ручные наборы времён для метода ближайшего ранга, включая границы p и совпадающие времена. Проверь смешанную группу с незавершёнными прогонами. Отдельно проверь ситуацию, когда P85 уже наблюдаем, хотя часть поздних прогонов цензурирована, и ситуацию, когда требуемый ранг ещё не наблюдаем.

Проверь повторяемость одного seed, одинаковые результаты при перестановке сценариев, отсутствие переноса состояния между прогонами и корректную привязку строки к scenarioId. При параллельной реализации добавь сравнение с последовательным запуском.

На лесопилке сравни точный результат с независимой рекуррентной проверкой расписания. Можно использовать тот же генератор длительностей движка, но в отчёте честно укажи, что это независимая проверка расписания, а не RNG.

Историческая серия сборки от 08.11.2026 даёт следующие P85 для seed от 0 до 999: 186,69 минуты при CV 0,25; 195,81 при CV 0,5; 213,34 при CV 1. Числа здесь округлены. Для точной проверки сравни исходные целые миллисекунды с сохранённым `вариативность/runs.json`. Не сравнивай округлённое значение как точную константу.

Сравнение по распилу, запущенное во время подготовки задания, не задаёт эталон в этом документе. Не придумывай его итог и не утверждай, что исходная гипотеза подтвердилась, пока нет проверенных результатов.

### Поиск по сроку и регрессии

Проверь детерминированную лесопилку, равных кандидатов, отсутствие улучшения, недостижимую цель и случайные парные сценарии. Старые результаты поиска по выпуску должны остаться прежними. Сохрани существующие тесты прогресса, отмены и веб-вызова общего поиска.

Выполни проверки, предписанные репозиторием для изменённой части, затем полный `npm run ci`. Отдельно сделай пользовательскую приёмку через собранный CLI на fixture лесопилки. Не заменяй проверку CLI прямым вызовом внутренней функции.

Зафиксируй фактическое время и размер результатов серии, использованную машину и число прогонов. Не обещай заранее конкретное ускорение. Критерий экономии состоит в отсутствии тысяч процессов Node и многомегабайтной истории на каждый компактный результат.

## Документация и результат работы

В `doc/ENGINE_API.md` добавь ссылки на новые DTO, семантику времени, целей и статусов, команды и форматы ошибок. Приведи полностью исполняемые примеры для одиночного заказа, серии и поиска по сроку. Объясни различие между выпуском за горизонт и временем завершения фиксированного объёма.

Сохрани компактные входные fixtures и воспроизводимый протокол приёмки в репозитории. Большие результаты исследования не добавляй в Git без необходимости. Документируй, где они находятся и как повторить вычисления. Обновляй задачи и передачу контекста по правилам проекта. Отмечай завершёнными только реально проверенные части.

Готовый результат должен позволять пользователю запустить одну команду для серии с вариативностью распила и сборки и получить проверяемую таблицу P50, P85, P95 и запаса времени. Внешний скрипт допустим для последующего построения графика, но не должен вычислять скрытый момент завершения через внутренний API.
