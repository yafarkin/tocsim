## Результат и границы

Simulation.getHistory() и RunnerView.history возвращают ограниченную историю количеств. Графики и новые элементы интерфейса в № 86 не добавлены. Сбор не требует DOM, сети или localStorage. Он не меняет производственные события, RNG или расчёт точных итогов.

История имеет schemaVersion 1, engineVersion, rngVersion и calculationHash. Движок 0.31.0, Snapshot 22, RunnerView schemaVersion 3. Приложение 0.1.0, конфигурация schemaVersion 1 и RNG counter32-fixed-distributions-2 прежние. Snapshot не содержит ряд, чтобы его не копировать в каждом транзакционном черновике. Загрузки сохранённых прогонов и старых RunnerView нет, миграция несуществующего сохранения не добавлена.

Граница `line-excluding-warehouse` включает физический материал в input/reserved/held/output. Сырьевой склад вне линии. `scope=per-material` означает отдельную сопоставимую единицу каждого материала; строковые количества выражены в целых микроединицах, для показа в штуках делятся на 1 000 000. Материалы сборки и результаты 1:10 не складываются в якобы одинаковые изделия. Допустимость общей CFD для сохраняющего единицу участка определяется в № 37 по конфигурации. Все необходимые физические места и отдельные выходы доступны уже сейчас.

## Контракт

`initial` содержит состояние на нулевой отметке до поступлений и диспетчеризации, с phase=initial. Начальный запас дан как начальное состояние, история до старта не придумывается. `points` содержат отсчёты после обработки всей соответствующей отметки, с phase=settled. До запуска points содержит только начальное состояние. После обработки нулевой отметки точка 0 показывает уже поступившее/зарезервированное, а initial сохраняет исходный запас отдельно. Не следует складывать initial и текущий запас как два физических остатка.

Каждая точка содержит timeMs календарного модельного времени, workMs общего рабочего времени от старта и values. Рабочая шкала исключает обед и ночь даже при подмене поста. Во время пауз workMs может совпадать у нескольких последовательных точек; порядок задаёт timeMs.

`values.materials` содержит по каждому материалу следующие поля.

| Поле | Значение |
|---|---|
| input | Входные очереди внутри линии |
| reserved | Входы текущей операции и зарезервированных будущих повторений |
| held | Уже созданный результат на постах до передачи |
| output | Материал в выходных буферах |
| wip | Сумма четырёх непересекающихся физических мест |
| released | Накопленное фактическое поступление из источников, включая запуск со склада |
| produced | Накопленное создание материала производственными рецептами |
| consumed | Накопленное потребление материала рецептами, то есть выход из потока этого материала при преобразовании |
| delivered | Накопленная годная передача в готовую продукцию, равна sold |
| scrapped | Накопленные обнаруженные списания, отдельный выход, не часть delivered |

`values.places` содержит непустые строки ownerId/materialId/location/quantity. Непоказанное допустимое место имеет количество 0. Порядок стабилен по ID и месту. Стадии заданы в `stages`, владелец и материал связываются с RunConfig для подписи. Так доступны очереди отдельных постов, физический резерв партии, удержанный выпуск и буфер. Будущие результаты незавершённой операции не создаются ради графика.

На каждой точке для одного материала выполняется баланс:

`initial.wip + released + produced = wip + consumed + delivered + scrapped`.

Все компоненты имеют ту же границу и материал. Перемещение между постами баланс не меняет. Контроль сохраняет материал, а обнаруженный брак уходит в scrapped. Строка produced сама по себе не означает годный выпуск. Сборка и раскрой отражаются потреблением исходного материала и созданием другого, каждый в своём ряду. Стоимость, происхождение, скрытые defective/defectSourceIds и полный журнал в точку не копируются. Скрытая годность WIP не раскрывается.

## Отсчёты и память

`sampling.kind=uniform-model-time`. Интервал равен `ceil(durationMs / 2046)`, вычисляется через bigint. Регулярные точки лежат на сетке 0, intervalMs, 2 × intervalMs и далее до фактического времени. Текущая отметка добавляется в выдаваемый ряд, если она вне сетки. Она не закрепляется как отсчёт следующего кадра. На остановке или ошибке последняя точка соответствует последней согласованной отметке. Конец полного горизонта всегда присутствует.

`MAX_FLOW_POINTS=2048` ограничивает points, initial хранится отдельно. Бюджет от числа событий и кадров не растёт. Объём одной точки зависит от числа материалов и занятых мест конфигурации, а не от числа отдельных изделий. Если количества не менялись, точки могут ссылаться на один замороженный набор values. Сериализация разворачивает эти ссылки, поэтому размер JSON больше фактического объёма разделяемых объектов. Полные снимки на каждую точку не хранятся.

FlowHistoryCollector получает только успешно завершённые отметки. Перед новой отметкой он заполняет пропущенные точки сетки предыдущими количествами. При точном совпадении сетки и события записываются новые количества после всех фаз, включая приёмку/списание и новый запуск. В промежутке без событий количества не меняются, поэтому продвижение до времени кадра даёт ту же сетку без дополнительных производственных событий. Simulation.advanceTo проходит через те же step, затем продвигает оставшийся промежуток без событий. Допустимость цели проверяется до начала работы.

Изображение сокращено по времени. Пик, возникший и исчезнувший между отсчётами, может быть пропущен. № 37 должна подписать разрешение ряда и не выдавать эти точки за полный журнал всех изменений. Интегралы stockTime/station time и средние flowTime/stockAge не восстанавливаются по изображению и остаются точными. История не служит источником денежных итогов или проверки точных интегралов.

getHistory кеширует выдачу по текущему снимку. Точки, вложенные значения и список заморожены, прошлые выдачи не меняются. RunnerView замораживает уже неизменяемые model/history поверхностно и отдельно замораживает новые transfers/error. Он не обходит весь накопленный ряд заново при каждом кадре. Повтор создаёт новую Simulation и новую историю с той же конфигурацией и выбранной скоростью просмотра.

## Проверки № 86

Прошли 898 тестов в 47 файлах, TypeScript, build/check:dist и git diff --check. flow-history.test.ts содержит 22 проверки, runner.test.ts дополнен восемью проверками истории.

Проверены начальный запас до/после нулевых событий, точное совпадение сетки с завершением/передачей/новым запуском, промежутки без событий, текущая отметка вне сетки, остановка, полный горизонт и ошибки. Ошибка нового поступления на одной отметке с завершением откатывает весь результат отметки; история сохраняет предыдущую точку и не включает промежуточный выпуск. Низкоуровневый EventScheduler по-прежнему владеет транзакцией.

Для всех восьми примеров каждая текущая конечная точка на шаге сверена со stocks, stockAge, flowReport и counters. Проверены балансы материалов, сумма мест, резерв/held, сборка, разделение, партии, начальные запасы, склад и списания. Выборочные внутренние отсчёты независимо сверены с Simulation.advanceTo той же отметки. Прямой прогон, шаги, дробные продвижения и перестановка входных массивов дают одинаковую историю. Прикрытие скрытых признаков качества не меняет ряд.

Runner проверен на всех восьми примерах при скоростях 60/300/1800/max, с паузой, шагом и повтором. История и JSON совпадают с прямым прогоном. Изменение скорости на паузе сохраняет ссылку на ту же историю. Прежние проверки скоростей, событий и итогов сохранены.
